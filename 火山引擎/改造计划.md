# 火山引擎 Data Agent 100% 复刻落地报告 v3.0

## 1. 文档定位

本报告不是“脑补版组件清单”，而是基于以下素材逐张阅读后形成的落地方案：

- `火山引擎/中间区.png`
- `火山引擎/右侧区 (1).png`
- `火山引擎/右侧区 (2).png`
- `火山引擎/分割图片_中间区/中间区 (1).png` 到 `中间区 (10).png`
- `火山引擎/分割图片_右侧区 (1)/右侧区 (1).png` 到 `右侧区 (21).png`
- `火山引擎/中间区.md`
- `火山引擎/右侧区.md`
- `火山引擎/其他AI分析.md`
- 当前工程代码：`frontend/src/views/SmartAsk.vue`、`frontend/src/components/smartask/*`、`frontend/src/state/smartAskSession.js`

本报告目标只有一个：指导当前项目把 `SmartAsk` 页改造成和截图高度一致的火山引擎 `Data Agent` 页面。

## 2. 先说结论

当前 `改造计划.md` 的方向有几个明显偏差，必须先纠正：

1. 真实页面没有右侧 `Tab` 切换。
2. 真实页面没有深色 SQL 代码块，SQL 和 Python 代码都在浅色白底卡片中展示。
3. 左侧 AI 回复不是“满屏卡片流”，而是“身份行 + 状态芯片 + 文本计划 + 单个大执行摘要卡 + 附件卡 + 底部 CTA 条”。
4. 顶部也不是“机器人头像 + 数据集徽章 + 申请试用”的中台头部，而是更接近火山引擎体验中心的 `DataAgent` 工作区页头。
5. 右侧不是“执行详情 / 数据预览 / 汇总报告”三页签，而是一条从开始到结束完整展开的执行事件时间线，最终报告本身也作为时间线中的一个阶段展示。
6. 当前前端状态流是“前端自造 phase 模拟 + 补一点后端结果”，而目标页面是“真实工具执行事件流驱动 UI”。

如果继续沿着旧文档做，最终页面会“像一个问数系统”，但不会“像火山引擎这个 Data Agent”。

## 3. 图片顺序阅读后的事实基线

### 3.1 中间区图片结论

按 `中间区 (1)` 到 `中间区 (10)` 顺序阅读，左侧主区可以确认出 7 个真实阶段：

1. 欢迎态。
2. 用户问题气泡出现。
3. AI 身份行出现。
4. `思考完成` 状态芯片出现。
5. 执行计划正文直接输出，不是独立描边大卡。
6. `Agent 执行完毕` 后出现一个大执行摘要卡，卡内是沿纵向时间线展开的文本日志。
7. 分析完成后出现两个附件卡和一个底部大 CTA 条，CTA 条文案为“本月公司经营表现分析”，右侧有 `查看下一个` 和 `申请试用`。

### 3.2 右侧区图片结论

按 `右侧区 (1)` 到 `右侧区 (21)` 顺序阅读，右侧执行面板可以确认出 6 个真实规律：

1. 右侧始终是一条单列时间线，没有 tab。
2. 每个事件节点都是浅灰外卡 + 白色内卡结构。
3. 工具标题会随步骤变化，如：
   - `选择数据表并执行SQL语句查询数据`
   - `复杂查询pandas代码到SQL转换`
   - `使用python语言进行数据处理和运算`
   - `更新事实&计划`
   - `总结报告`
4. 执行异常不是覆盖原节点，而是保留 `SQL纠错 / SQL重新生成 / 重新执行` 的完整痕迹。
5. 图表和表格是事件卡的一部分，属于“原始执行结果预览”，不是最终报告视图。
6. 最终报告也不是跳到新页面，而是在 `总结报告 -> 生成最终报告` 节点里嵌入一个完整报告预览卡。

## 5. 左侧区域真实还原规范

### 5.1 顶部工作区头部

不是现在工程中的 `经营分析顾问 + 数据集徽章 + 申请试用` 头部。

### 5.2 欢迎态

### 5.3 用户问题气泡

从截图直接可见：

- 用户问题是浅灰色胶囊气泡，不是高饱和蓝色气泡。

### 5.4 AI 身份行

- 结构：头像 + `经营分析顾问`

### 5.5 状态芯片

左列第一个关键识别元素是 `思考完成` 芯片。

真实样式特点：

- 小型圆角胶囊
- 左侧有思考/灯泡样式图标
- 右侧有下拉箭头

落地建议：

- 把当前 `ThinkingCard.vue` 一拆为二：
  - `ThoughtStatusChip`
  - `ExecutionDigestCard`

### 5.6 执行计划正文

执行计划并非独立大卡，而是直接输出在左列正文流中：

- 有“好的，根据你的问题，我制定了以下执行计划：”
- 按步骤 1-6 输出
- 步骤中夹带灰底代码标签，如 `execute_one_sql`、`code_interpreter`、`final_answer`

落地建议：

### 5.7 执行摘要卡

这是左列最重要的大块区域，真实结构如下：

这意味着左侧不是“迷你版右侧面板”，而是“对右侧事件流的摘要重排”。

### 5.8 附件区

截图中完成态后出现两个附件卡：

- `公司近30日经营分析报告.HTML`

样式特点：

- 单行胶囊卡
- 左侧文件图标
- 白底、浅边框

### 5.9 底部大 CTA 条

完成态底部不是输入框，而是结果承接条：

- 左侧真人头像

## 6. 右侧区域真实还原规范

### 6.1 右侧头部

真实结构：

- 标题：`执行事件详情`
- 关闭按钮：右上角 `x`

  - 右侧：`Agent 执行完成`

当前工程的 `TabNav.vue` 在目标界面中没有存在必要，应下线。

### 6.2 时间线整体结构

真实结构不是树形折叠面板，而是单列时间线：

- 一条竖向主线贯穿到底
- 每个节点一个外卡
- 外卡顶部是事件标题行
- 内部可含一个或多个白色内容盒

建议数据结构：

```ts
type AgentTimelineEvent = {
  id: string
  toolType: 'sql' | 'python' | 'fact' | 'report'
  title: string
  status: 'completed' | 'running' | 'error'
  summary?: string
  thought?: string
  codeBlocks?: Array<{ language: 'sql' | 'python'; title?: string; code: string }>
  charts?: Array<ChartSpec>
  tables?: Array<TableSpec>
  markdown?: string
}
```

直接可见特征：

- 左侧小图标方块
- 中部标题
- 右侧圆角状态胶囊 `已完成`
- 背景很轻

标题样例：

- `更新事实&计划`
- `总结报告`

### 6.4 内容盒样式

真实内容盒全部偏轻：

- 白底
- 细边框
- 12px 到 16px 圆角
- 内边距较大
- 文本以段落为主

当前工程的深色 `SqlBlock.vue` 与截图完全不符，必须重做成浅色语法高亮卡。

### 6.5 SQL / Python 代码块

直接观察到的真实规律：

- 白底
- 代码关键字有彩色高亮
- 支持横向滚动
- 与 surrounding 卡同属浅色体系

这说明设计语言更像“文档内嵌代码片段”，不是“开发者终端窗口”。

### 6.6 图表类型

截图中真实出现的图表包括：

- 近 30 日趋势组合图：蓝柱 + 绿线
- 城市分布饼图：多分类饼图
- 佣金水平分布饼图：三分类饼图
- 股票 Top5 柱状图
- 报告内复用同类图表

落地要求：

- 右侧事件卡中的图表是“原始执行结果图”
- 最终报告中的图表是“排版后的报告图”
- 两者数据可能同源，但排版层不能共用一个 DOM 组件直接硬塞

### 6.7 表格风格

截图中的表格特征：

- 浅灰表头
- 细表格线
- 无重阴影
- 字体偏小
- 行高紧凑

并且很多表格是“原始查询结果表”，字段名直接暴露原业务字段。

### 6.8 错误与重试链路

这一点是旧方案完全没写到、但截图非常明确的地方：

- 某个 SQL 执行失败后，会新增 `SQL纠错`
- 然后会新增 `SQL重新生成`
- 再次 `开始执行SQL`
- 最终 `SQL执行结束`

因此右侧时间线必须保留失败痕迹，不能只展示最终成功结果。

### 6.9 事实更新节点

截图中至少出现多次 `更新事实&计划` 节点，内部内容是长篇 Markdown/富文本，不是短提示。

这是整个 agent “自我总结”和“下一步规划”的核心特征，必须保留。

### 6.10 总结报告节点

最终阶段是独立工具流：

- `生成初版报告`
- `报告智能纠错`
- `报告智能润色`
- `生成最终报告`

最终报告会直接嵌在 `生成最终报告` 节点里，不是跳转 tab。

## 10. 前端数据模型重构建议

当前页面不能再使用“消息 + 少量附属 data”的简单模型。

建议改成两层数据：

### 10.1 左列叙事模型

```ts
type NarrativeBlock =
  | { type: 'welcome' }
  | { type: 'user-question'; text: string }
  | { type: 'assistant-identity' }
  | { type: 'thought-chip'; text: string }
  | { type: 'plan-text'; markdown: string }
  | { type: 'execution-digest'; items: DigestItem[] }
  | { type: 'attachments'; files: AttachmentItem[] }
  | { type: 'completion-cta'; title: string; subtitle: string }
```

### 10.2 右列事件模型

```ts
type TimelineEvent =
  | { kind: 'tool'; tool: 'sql' | 'python'; title: string; status: string; blocks: ContentBlock[] }
  | { kind: 'fact-update'; title: string; markdown: string; status: string }
  | { kind: 'report-stage'; title: string; markdown?: string; reportHtml?: string; status: string }
```

### 10.3 最关键的原则

左列和右列不是两套后端返回。

正确做法：

1. 后端返回统一事件流。
2. 前端把事件流直接渲染成右侧时间线。
3. 前端再从事件流派生左侧摘要内容。

这样才能保证“左侧摘要”和“右侧细节”永远同步。

## 11. 推荐的后端适配方式

如果后端已有细粒度事件，前端直接消费。

如果后端暂时只有最终结果，建议先做一层前端 adapter mock，字段至少包含：

