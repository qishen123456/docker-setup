# SmartAsk 已确认效果基线

本文档用于记录当前已经确认可接受、后续修改时应尽量保持不变的问数行为与界面效果。

使用方式：
1. 改代码前，先阅读与本次改动相关的条目。
2. 修改时尽量只影响对应范围，不扩大到其他流程。
3. 修改后至少用本文档中的代表问题做一轮最小回归验证。

注意：
- 本文档记录的是“已确认行为”，不是设计草案。
- 如果后续产品口径发生变化，应先更新本文档，再改代码。
- 优先保护“基础问数流程”和“已经确认通过的展示效果”。

## 1. 组织下钻类

### 1.1 单对象默认带一层下级

适用范围：
- 商用事业部组织树问数
- 单对象查询
- 非末端节点

代表问题：
- `东部分公司的业绩怎么样了`
- `华南业务部的业绩如何`
- `某代表处的表现怎么样`

已确认行为：
- 如果只问一个对象，且该对象不是最末端节点，则默认返回：
  - 本节点
  - 该节点的直接下一层下级
- 不应只返回本节点 1 行

末端例外：
- 如果对象已经是 `业务代表`，则只返回本节点，不再继续下钻
- 末端个人节点（业务代表/个人）不展示“下一级 X 个业务代表”，应展示个人业绩指标（总任务金额、年度开单金额、达成率、剩余任务金额）

不允许行为：
- 问单一个分公司，只返回分公司本身
- 问单一个业务部，只返回业务部本身
- 递归已经查出下级，但最终结果又被过滤回 1 行

当前修复点：
- [backend/four_agent_ask.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/four_agent_ask.py)
- [backend/report_spec_builder.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/report_spec_builder.py)
- [frontend/src/components/smartask/ResultDigestCard.vue](/D:/1.智能问数项目/本地测试版2.0/smartask/frontend/src/components/smartask/ResultDigestCard.vue)

最小验证：
- 返回结果中必须包含目标节点本身
- 返回结果中必须至少包含 1 个上级为该节点的下级行

### 1.2 多对象对比不应误走单对象下钻

代表问题：
- `东部分公司和南部分公司的业绩对比`

已确认行为：
- 多对象问题应保留并列对比语义
- 不应误套到“单对象默认带一层下级”规则

### 1.2.1 跨数据集对比必须使用主体总览口径

代表问题：
- `消费者和商用的对比`
- `商用事业部和消费者事业部的总任务金额对比`

已确认行为：
- 当问题明确命中多个数据集主体并进入跨数据集对比时，展示和摘要必须比较各主体本身的总览指标，不得复用单个数据集内部 `comparison_nodes` 的集合 KPI
- `消费者事业部` 应取其主体根节点行；`商用事业部` 应取其主体根节点行；口径层级必须一致
- 若某数据集内部 comparison KPI 是“13个分公司汇总”或“分公司/业务部混合集合汇总”，这些值不能直接拿来做跨数据集第一屏结论
- 前端左侧卡片、跨数据集结论摘要、后续分析都应优先读取后端注入的 `cross_dataset_subject_overview`

不允许行为：
- 把消费者的“13个分公司累计达成率 45.36%”与商用的“10个分公司/业务部混合集合达成率 47.51%”直接比较成事业部对比结论
- 仅因为 `report_spec.kpis` 里已有 `compare-overall-rate`，就把它当成跨数据集总览

当前修复点：
- `backend/smartask_advanced/service.py`
- `frontend/src/views/SmartAsk.vue`
- `backend/tests/test_advanced_cross_dataset.py`

### 1.2.2 跨数据集对比执行必须拆成逐数据集主体查询

代表问题：
- `商用和电商的对比`
- `电商和商用的业绩对比`

已确认行为：
- 当问题明确命中多个数据集主体并进入跨数据集对比时，执行阶段必须把原问题拆成“每个数据集各自的主体查询”，例如：
  - `商用事业部` 数据集执行 `商用事业部的业绩`
  - `电商事业部` 数据集执行 `电商事业部的业绩`
- 不允许把整句 `商用和电商的对比` 原样塞回任一单数据集执行，否则单数据集会把另一个事业部名称误当成内部成员、筛选项或无效条件
- `public` 模式数据集只要能被 `dataset_node_index.json` 命中真实组织节点，也应参与这类跨数据集对比，不要求强制切成 `org_tree`
- 最终顶层 `route.intent` 仍应保持 `comparison`，并保留 `advanced_execution_question.queries` 作为可追踪的逐数据集执行明细

不允许行为：
- 进阶流程虽然识别出跨数据集对比，但执行时又退回 `preferred_dataset_override` 的单数据集 ask
- 电商数据集收到 `商用和电商的对比` 这类整句问题后，错误返回 0 行或“未查询到匹配数据”
- 只有商用结果出来，电商结果为空，导致页面看起来像“还是没问出来”

当前修复点：
- `backend/smartask_advanced/service.py`
- `backend/organization_route_resolver.py`
- `backend/tests/test_advanced_cross_dataset.py`
- `backend/tests/test_route_and_permission_guards.py`

### 1.3 具体节点 + 目标子层级走 drilldown

代表问题：
- `江浙沪分公司的城市分公司`
- `山东分公司的业务代表`

已确认行为：
- 具体节点名 + 目标子层级 → `intent=drilldown`，`output_mode=children_first`
- 返回该节点下指定层级的子节点
- 若问题同时包含排名/TopN 词（如“前三”“排名”），优先走 ranking，不应被本规则覆盖

当前修复点：
- `backend/four_agent_ask.py`

### 1.4 电商根节点默认展示直接下级

代表问题：
- `电商事业部的业绩`

已确认行为：
- 普通问“电商事业部的业绩”时，应展示电商事业部的直接下级 `业务部`，当前应返回 `国内业务部`、`直营零售部`、`跨境业务部`
- 后端 SQL 应限定 `层级级别 = '业务部'`，不应只返回 `事业部` 汇总单行
- `report_spec.scope.focusNodeIsLeaf` 应为 `false`，左侧卡片应按下级列表展示
- 用户明确说 `整体`、`总体`、`总览`、`汇总`、`全部` 时，才允许理解为事业部整体汇总口径

不允许行为：
- 把 `电商事业部` 根节点误判为叶子节点，导致左侧卡片没有下级
- 因路由或意图重写把普通根节点业绩问法固定到 `事业部` 层级

当前修复点：
- `backend/four_agent_ask.py`
- `backend/tests/test_ecommerce_filter_intent.py`
- `backend/smartask_report_history_store.py`

## 2. 排名 / TopN 类

### 2.1 未明确数量时，不要默认 Top3

代表问题：
- `消费者城市分公司排名`
- `各分公司业绩排名`

已确认行为：
- 用户只说“排名 / 排行”，但没有明确 `TopN`、`前 N`、`后 N`、`倒数 N` 时，应返回全量排序结果
- 不应自动截成 Top3

允许默认截断的前提：
- 用户明确说了 `Top3`
- 或明确说了 `前 3`、`后 3`、`倒数 3`

当前修复点：
- [backend/four_agent_ask.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/four_agent_ask.py)

### 2.2 排名类问题优先保持排名语义

代表问题：
- `业务部业绩排名`
- `分公司业绩排名`

已确认行为：
- 排名类问题应优先走排名场景
- 不应被错误改造成普通详情或单对象分析

### 2.3 电商业务承接人排名应命中承接人层级

代表问题：
- `看下前三的业务承接人`
- `电商事业部业务承接人业绩排名`

已确认行为：
- “业务承接人”“承接人”“负责人”“任务承接人”应被识别为电商数据集的“承接人”层级（物理层对应 `业务经理` / `负责人`）
- 排名结果应以具体负责人个人为节点，而不是业务部或业务承接角色
- 展示标题应为 `排名前3的承接人` 或等价清晰文案，不应出现重复、截断或歧义

不允许行为：
- 把“业务承接人”识别为“业务部”并返回业务部排名
- 把“业务承接人”识别为“业务代表”导致命中商用/消费者数据集或电商业务承接角色层级
- 标题生成出现 `的业务承接人的业务承接人` 这类重复文本
- 因路由确认后 refined_query 被改写成“XX业务部的业绩”，就把原问题中的“业务承接人”层级覆盖为“业务部"
- 排名/TopN 问题在 confirm 后被改写成“XX的业绩”，导致 `top_n` 丢失、返回全部、标题变成 `的业务承接人的业绩`
- 排名/TopN 问题在 ask 阶段就被组织主体解析器改写成“XX的业绩”，导致后续整条链路丢失数量词

当前修复点：
- [backend/four_agent_ask.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/four_agent_ask.py)

最小验证：
- 返回结果中 `层级` 列为 `承接人`
- 返回结果中 `节点名称` 为具体人名（如 `黄超`、`刘志伟` 等）
- 展示标题不含重复片段
- 用户明确说 `前三` / `前3` / `Top3` 等时，返回行数应为 3，SQL 应含 `LIMIT 3`
- 路由确认后，`question` 应仍为用户原话，不应被改写成 `XX的业绩` 导致 `top_n` 丢失

### 2.4 层级 Overview 统一走 ranking/list 模式

代表问题：
- `城市分公司的业绩`
- `城市分公司的业绩咋样`
- `业务部的业绩情况`

已确认行为：
- 纯层级词 + 业绩/情况/咋样/如何，无数值/对比/排名/聚合关键词 → `intent=ranking`，`top_n=0`
- 返回该层级全部节点，按默认指标（通常为达成率）排序
- 不应走单对象下钻，也不应走对比
- answerSummary 使用中性文案（如“共 N 个…”），避免“本次对比”等字眼
- 即使问题中同时出现具体人名和角色/层级词 + Overview 词（如 `商用业务代表靳锋 的业绩情况`），仍按层级 Overview 处理，不提取单个人名做过滤

当前修复点：
- `backend/four_agent_ask.py`
- `backend/report_spec_builder.py`

### 2.5 排名/TopN 问题不应被下钻分支拦截

代表问题：
- `看下前三的城市分公司`
- `前5的业务代表`

已确认行为：
- 问题中含 `前/后/TopN/最高/最低/最好/最差/最大/最小` 等排名词时，应走 ranking
- 即使 LLM 把“前三的城市分公司”解析成多个分公司实体，ranking 语义也应优先于“具体节点+目标子层级”的 drilldown 规则
- 不应出现 `answerMode=drilldown` 但用户明显在问排名的情况

当前修复点：
- `backend/four_agent_ask.py`

### 2.6 口语化排名数量由 LLM 拆解，并受事实索引与规则校验

代表问题：
- `消费者事业部，业绩排名垫底的 3 家分公司`
- `消费者事业部垫底的5个城市分公司`
- `倒数前三的分公司`
- `垫底的三个分公司`
- `垫底的3个分公司`

已确认行为：
- 大模型负责自然语言结构化拆解，并输出 `ranking_params`（`top_n` / `rank_sides` / `direction` / `metric_hint`）
- `dataset_node_index.json` 是真实节点、层级、别名、叶子判断的事实底座；模型拆解出的目标层级/节点必须能被事实底座或数据字典校验
- 规则不应主导理解口语化数量，规则只用于 schema 校验、范围校验、冲突裁判与安全兜底
- 最终 `top_n` 受 `0-20` 范围校验；明确数量优先于“垫底/最差/最低”等无数量默认 1 的业务约定
- `垫底/落后 + 的 + 数字/中文数字 + 个/家/名/位` 属于明确数量，必须解析出对应 `top_n`，例如 `垫底的三个分公司` -> `top_n=3`
- 非排名问题不受 ranking 参数影响，原有意图（detail/filter/comparison/aggregate 等）保持不变
- 不应依赖 `backend/data/dataset_dimension_profiles.json` 才能识别 `垫底的5个` 这类 TopN 数量；该旧画像缺失时，排名数量口径也必须保持一致

当前修复点：
- `backend/four_agent_ask.py`
- `backend/tests/test_query_intent_metrics.py`
- `backend/smartask_report_history_store.py`

历史快照约束：
- 历史分析不能恢复明显过期的旧口径快照，例如“垫底的5个”旧记录里 `query_intent.top_n=1`、或“电商事业部的业绩”旧记录里 `focusNodeIsLeaf=true` 但节点索引已有下级
- 服务端历史读取和保存都必须用 `config/dataset_node_index.json` 与原问题显式 TopN 数量做校验，过期快照应被剔除/拒收，避免浏览器 localStorage 把旧记录回灌

### 2.7 "最X" 没有数量时默认取 1 条

代表问题：
- `业绩最差的业务代表` → 默认返回倒数第 1
- `业绩最好的分公司` → 默认返回正数第 1
- `垫底的分公司` → 默认返回倒数第 1

已确认行为：
- 问题含 `最好/最差/最高/最低/最大/最小/垫底` 等明确极端方向词，但没有数字时，`top_n=1`
- 纯"排名/排行"没有数量时，仍返回全量排序结果（`top_n=0`），不受影响
- 明确数量时按数量执行

当前修复点：
- `backend/four_agent_ask.py`
- `backend/tests/test_query_intent_metrics.py`

### 2.8 问数语义底座以节点索引为准，旧维度画像不作为事实源

代表问题：
- `云贵分公司的业绩`
- `消费者事业部垫底的5个城市分公司`
- `上海那边业绩如何了`

已确认行为：
- `config/dataset_node_index.json` 承担真实节点、层级、别名、叶子节点判断；它由当前数据自动生成或在飞书同步成功后按受影响数据集重建
- 大模型承担自然语言拆解：识别排名/筛选/下钻/对比/聚合、目标层级、数量、方向、指标
- 规则承担校验：模型输出 schema、数值范围、节点/层级是否存在、SQL 安全、权限边界、明显冲突裁判
- `backend/data/dataset_dimension_profiles.json` 属于旧的语义画像增强，不是最新事实源；缺失或旧版本不应改变排名、下钻、叶子节点等核心口径
- 若后续恢复或重建维度画像，只能作为别名/集合口径增强，不能覆盖 `dataset_node_index.json` 的真实节点关系

不允许行为：
- 因为旧 `dataset_dimension_profiles.json` 存在或缺失，导致同一问题在不同服务器返回不同 TopN 数量
- 使用旧画像中空的 members 或过期层级覆盖自动生成的节点索引
- 为了修一个口语表达而堆叠大量正则，让规则替代大模型做主要理解

### 3.3 确认后的组织节点追问，命中唯一口径时不再重复确认

代表问题：
- 第一步：`前 3 的分公司`
- 第二步：选择 `消费者事业部`
- 第三步：`看下河北分公司的业绩`
- 独立新问题：`垫底的三个分公司`

已确认行为：
- 不是“确认一次后永远不再确认”
- 如果后续追问命中了上一轮已确认数据集中的唯一组织节点口径，则应直接沿用该数据集继续问数
- 不应再次弹出商用 / 消费者 / 电商的数据集确认卡片
- 对没有明确事业部/数据集限定的通用层级排名问题，如 `垫底的三个分公司`，如果 2 个及以上数据集真实支持“分公司”层级，必须先进入数据集口径确认
- `config/dataset_node_index.json` 必须参与层级支持判断；不能因为旧画像缺失、同义词不完整或 LLM 评分偏高，把任一候选误判为唯一支持者
- 前端/会话态已经带了上一次 `selectedDatasetId` 时，若本轮问题重新形成通用层级歧义，也必须释放旧选择并确认

仍需确认的情况：
- 后续问题仍然是通用问法，没有明确新的组织节点对象
- 或后续问题再次形成多个数据集都可能成立的真实歧义

不允许行为：
- 上一轮已经选了 `消费者事业部`，下一轮问 `河北分公司` 仍然再次要求在 `商用 / 消费者` 之间确认
- 因为通用“分公司”层级重复，就覆盖掉已经确认过的会话口径
- 干净请求 `垫底的三个分公司` 被自动判到某一个数据集直接执行
