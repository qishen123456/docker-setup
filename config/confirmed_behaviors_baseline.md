# SmartAsk 已确认效果基线

本文档用于记录当前已经确认可接受、后续修改时应尽量保持不变的问数行为与界面效果。

使用方式：
1. 改代码前，先阅读与本次改动相关的条目。
2. 修改时尽量只影响对应范围，不扩大到其他流程。
3. 修改后至少用本文档中的代表问题做一轮最小回归验证。

注意：
- 本文档记录的是“已确认行为”，不是设计草案。
- 如果后续产品口径发生变化，应先更新本文档，再改代码。
- 优先保护“基础问数流程”和“已经确认通过的展示效果”。

## 1. 组织下钻类

### 1.1 单对象默认带一层下级

适用范围：
- 商用事业部组织树问数
- 单对象查询
- 非末端节点

代表问题：
- `东部分公司的业绩怎么样了`
- `华南业务部的业绩如何`
- `某代表处的表现怎么样`

已确认行为：
- 如果只问一个对象，且该对象不是最末端节点，则默认返回：
  - 本节点
  - 该节点的直接下一层下级
- 不应只返回本节点 1 行

末端例外：
- 如果对象已经是 `业务代表`，则只返回本节点，不再继续下钻
- 末端个人节点（业务代表/个人）不展示“下一级 X 个业务代表”，应展示个人业绩指标（总任务金额、年度开单金额、达成率、剩余任务金额）

不允许行为：
- 问单一个分公司，只返回分公司本身
- 问单一个业务部，只返回业务部本身
- 递归已经查出下级，但最终结果又被过滤回 1 行

当前修复点：
- [backend/four_agent_ask.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/four_agent_ask.py)
- [backend/report_spec_builder.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/report_spec_builder.py)
- [frontend/src/components/smartask/ResultDigestCard.vue](/D:/1.智能问数项目/本地测试版2.0/smartask/frontend/src/components/smartask/ResultDigestCard.vue)

最小验证：
- 返回结果中必须包含目标节点本身
- 返回结果中必须至少包含 1 个上级为该节点的下级行

### 1.2 多对象对比不应误走单对象下钻

代表问题：
- `东部分公司和南部分公司的业绩对比`

已确认行为：
- 多对象问题应保留并列对比语义
- 不应误套到“单对象默认带一层下级”规则

### 1.3 具体节点 + 目标子层级走 drilldown

代表问题：
- `江浙沪分公司的城市分公司`
- `山东分公司的业务代表`

已确认行为：
- 具体节点名 + 目标子层级 → `intent=drilldown`，`output_mode=children_first`
- 返回该节点下指定层级的子节点
- 若问题同时包含排名/TopN 词（如“前三”“排名”），优先走 ranking，不应被本规则覆盖

当前修复点：
- `backend/four_agent_ask.py`

## 2. 排名 / TopN 类

### 2.1 未明确数量时，不要默认 Top3

代表问题：
- `消费者城市分公司排名`
- `各分公司业绩排名`

已确认行为：
- 用户只说“排名 / 排行”，但没有明确 `TopN`、`前 N`、`后 N`、`倒数 N` 时，应返回全量排序结果
- 不应自动截成 Top3

允许默认截断的前提：
- 用户明确说了 `Top3`
- 或明确说了 `前 3`、`后 3`、`倒数 3`

当前修复点：
- [backend/four_agent_ask.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/four_agent_ask.py)

### 2.2 排名类问题优先保持排名语义

代表问题：
- `业务部业绩排名`
- `分公司业绩排名`

已确认行为：
- 排名类问题应优先走排名场景
- 不应被错误改造成普通详情或单对象分析

### 2.3 电商业务承接人排名应命中承接人层级

代表问题：
- `看下前三的业务承接人`
- `电商事业部业务承接人业绩排名`

已确认行为：
- “业务承接人”“承接人”“负责人”“任务承接人”应被识别为电商数据集的“承接人”层级（物理层对应 `业务经理` / `负责人`）
- 排名结果应以具体负责人个人为节点，而不是业务部或业务承接角色
- 展示标题应为 `排名前3的承接人` 或等价清晰文案，不应出现重复、截断或歧义

不允许行为：
- 把“业务承接人”识别为“业务部”并返回业务部排名
- 把“业务承接人”识别为“业务代表”导致命中商用/消费者数据集或电商业务承接角色层级
- 标题生成出现 `的业务承接人的业务承接人` 这类重复文本
- 因路由确认后 refined_query 被改写成“XX业务部的业绩”，就把原问题中的“业务承接人”层级覆盖为“业务部"
- 排名/TopN 问题在 confirm 后被改写成“XX的业绩”，导致 `top_n` 丢失、返回全部、标题变成 `的业务承接人的业绩`
- 排名/TopN 问题在 ask 阶段就被组织主体解析器改写成“XX的业绩”，导致后续整条链路丢失数量词

当前修复点：
- [backend/four_agent_ask.py](/D:/1.智能问数项目/本地测试版2.0/smartask/backend/four_agent_ask.py)

最小验证：
- 返回结果中 `层级` 列为 `承接人`
- 返回结果中 `节点名称` 为具体人名（如 `黄超`、`刘志伟` 等）
- 展示标题不含重复片段
- 用户明确说 `前三` / `前3` / `Top3` 等时，返回行数应为 3，SQL 应含 `LIMIT 3`
- 路由确认后，`question` 应仍为用户原话，不应被改写成 `XX的业绩` 导致 `top_n` 丢失

### 2.4 层级 Overview 统一走 ranking/list 模式

代表问题：
- `城市分公司的业绩`
- `城市分公司的业绩咋样`
- `业务部的业绩情况`

已确认行为：
- 纯层级词 + 业绩/情况/咋样/如何，无数值/对比/排名/聚合关键词 → `intent=ranking`，`top_n=0`
- 返回该层级全部节点，按默认指标（通常为达成率）排序
- 不应走单对象下钻，也不应走对比
- answerSummary 使用中性文案（如“共 N 个…”），避免“本次对比”等字眼

当前修复点：
- `backend/four_agent_ask.py`
- `backend/report_spec_builder.py`

### 2.5 排名/TopN 问题不应被下钻分支拦截

代表问题：
- `看下前三的城市分公司`
- `前5的业务代表`

已确认行为：
- 问题中含 `前/后/TopN/最高/最低/最好/最差/最大/最小` 等排名词时，应走 ranking
- 即使 LLM 把“前三的城市分公司”解析成多个分公司实体，ranking 语义也应优先于“具体节点+目标子层级”的 drilldown 规则
- 不应出现 `answerMode=drilldown` 但用户明显在问排名的情况

当前修复点：
- `backend/four_agent_ask.py`

### 2.6 口语化排名数量由 LLM 提取并受规则校验

代表问题：
- `消费者事业部，业绩排名垫底的 3 家分公司`
- `倒数前三的分公司`

已确认行为：
- 每次问数都调用 Agent1.5 做语义解析，并输出 `ranking_params`（`top_n` / `rank_sides` / `direction` / `metric_hint`）
- 后端规则优先：若规则已提取到明确数量，直接使用规则；规则未提取到时，才读取 LLM 的 `top_n`
- 最终 `top_n` 受 `0-20` 范围校验
- 非排名问题不受 ranking 参数影响，原有意图（detail/filter/comparison/aggregate 等）保持不变

当前修复点：
- `backend/four_agent_ask.py`
- `backend/tests/test_query_intent_metrics.py`

### 2.7 "最X" 没有数量时默认取 1 条

代表问题：
- `业绩最差的业务代表` → 默认返回倒数第 1
- `业绩最好的分公司` → 默认返回正数第 1
- `垫底的分公司` → 默认返回倒数第 1

已确认行为：
- 问题含 `最好/最差/最高/最低/最大/最小/垫底` 等明确极端方向词，但没有数字时，`top_n=1`
- 纯"排名/排行"没有数量时，仍返回全量排序结果（`top_n=0`），不受影响
- 明确数量时按数量执行

当前修复点：
- `backend/four_agent_ask.py`
- `backend/tests/test_query_intent_metrics.py`

### 3.3 确认后的组织节点追问，命中唯一口径时不再重复确认

代表问题：
- 第一步：`前 3 的分公司`
- 第二步：选择 `消费者事业部`
- 第三步：`看下河北分公司的业绩`

已确认行为：
- 不是“确认一次后永远不再确认”
- 如果后续追问命中了上一轮已确认数据集中的唯一组织节点口径，则应直接沿用该数据集继续问数
- 不应再次弹出商用 / 消费者 / 电商的数据集确认卡片

仍需确认的情况：
- 后续问题仍然是通用问法，没有明确新的组织节点对象
- 或后续问题再次形成多个数据集都可能成立的真实歧义

不允许行为：
- 上一轮已经选了 `消费者事业部`，下一轮问 `河北分公司` 仍然再次要求在 `商用 / 消费者` 之间确认
- 因为通用“分公司”层级重复，就覆盖掉已经确认过的会话口径

### 3.4 无层级裸节点优先走真实节点索引

代表问题：
- `上海那边业绩如何了`
- `东部那个分公司怎么样`
- `河北业绩怎么样`
- `看下上海代表处的业绩咋样了`

已确认行为：
- 对没有明确层级词、但明显是在问组织节点的口语问题，优先使用真实节点索引匹配
- 节点索引来源于各数据集当前真实节点清单，不是手工写死的别名表
- 匹配顺序应保持：
  - 先抽主体短语
  - 再查节点索引
  - 唯一命中则直接标准化为真实节点名
  - 多命中则确认
  - 未命中再回退组织树 / profile / 原有规则链路

- `上海`

- `东部`
  - 商用：`东部分公司`
- `河北`
  - 消费者：`河北分公司`

不允许行为：
- `上海那边业绩如何了` 直接拍脑袋落到某一个数据集
- 已经能从真实节点索引唯一命中的问题，仍然走模糊确认
- 节点索引已多命中的问题，被旧评分逻辑覆盖成单数据集直出

### 5.1 层级结果前端展示基线

代表问题：
- `城市分公司的业绩`（层级 Overview，ranking/top_n=0）
- `江浙沪分公司的城市分公司`（drilldown）
- `低于10%的业务代表`（filter）
- `东部分公司和南部分公司的业绩对比`（明确对比）

已确认行为：
- 返回行有明确 `parent` 时，按 `parent` 分组展示
- 分组只是视觉组织，不改变标签含义
- “相对领先/稳定推进/相对承压”等标签统一按全局达成率（`rate`）排名计算，不按组内重算，也不跟随当前 ranking 指标变化
- 达成率为 `0%` 的节点必须显示为压力/风险，不能显示为“相对领先”
- 只有问题文本中明确出现对比词（`对比/比较/差异/和…比/跟…比/与…比/vs`）时，才展示对比模板与“本次对比”文案
- ranking 模式不应误入对比作用域，导致下方排名列表消失
- 末端个人节点（业务代表/个人）应展示个人业绩指标，不应出现“下一级 X 个业务代表”

## 6. 建议的最小回归问题清单

每次改动后，不跑全量时，至少挑相关条目回归：
- `东部分公司的业绩怎么样了`
- `东部分公司的业绩？`
- `东部分公司和南部分公司的业绩对比`
- `业务部业绩排名`
- `各分公司业绩排名`
- `消费者城市分公司排名`
- `城市分公司的业绩`
- `城市分公司的业绩咋样`
- `江浙沪分公司的城市分公司`
- `看下前三的城市分公司`
- `低于10%的业务代表`
- `上海那边业绩如何了`
- `看下上海代表处的业绩咋样了`
- `东部那个分公司怎么样`
- `河北业绩怎么样`
- `看下前三的业务承接人`
- 发送任意问题后观察输入框运行态
- 确认 0% 达成率节点不显示“相对领先”
- 确认非明确对比问题不出现“本次对比”文案
- 确认末端个人节点展示个人业绩指标（例如：`商用事业部业务代表靳锋的业绩`）

## 7. 更新规则

出现以下情况时，应先更新本文档，再继续改代码：
- 产品口径变了
- 用户明确接受了新的展示方式
- 某个旧行为不再需要保护
- 某个新修复已经稳定通过，需要纳入基线
