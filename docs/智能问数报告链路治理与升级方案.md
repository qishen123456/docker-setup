# 智能问数报告链路治理与升级方案

> 目标：把“问题如何进入对应分析界面、报告模板到底有什么用、后续如何维护不同场景”这件事梳理清楚。本文先作为方案与开发计划，不直接改动主链路代码。

## 1. 当前真实链路

当前问数链路大致是：

```text
用户问题
  ↓
Agent1 路由与口径判断
  - 命中数据集
  - 判断是否需要确认
  - 给出 refined_query / decision
  ↓
数据集上下文
  - DDL
  - 数据字典
  - LLD
  - Golden SQL
  - Agent Prompt
  - report_config
  ↓
Agent2 SQL 生成
  - 结合 DDL / 字典 / report_config
  - 尽量输出标准报告列
  ↓
Agent3 SQL 复核
  - 只读校验
  - 语法与口径复核
  ↓
执行 SQL
  ↓
report_spec_builder
  - 根据问题文本、SQL 结果、report_config 动态生成 report_spec
  - 自动识别 detail / comparative / ranking / diagnostic
  - 动态构建上下级树
  ↓
前端 SmartAsk / ResultDigestCard
  - 根据 report_spec.layoutTemplate 渲染常规、对比、排名、下钻等报告
  ↓
Agent4 业务解读
  - 补充文字结论和建议
```

所以现在并没有一个地方让你手工维护：

```text
单一问数模板
对比分析模板
排名问数模板
诊断问数模板
```

这些场景目前主要由代码动态识别，核心入口在：

```text
backend/report_spec_builder.py
```

其中 `_detect_mode()` 会根据问题关键词和命中节点数量判断：

```text
comparative  对比分析
ranking      排名分析
diagnostic   诊断/风险分析
detail       常规/单体分析
```

## 2. 报告模板配置现在到底有什么用

现在的“报告模板配置”更准确应该叫：

```text
数据集报告契约
```

它不是用来维护每一种问法的模板，而是告诉系统这个数据集应该如何被报告理解。

它当前主要被三个地方使用：

### 2.1 Agent2 使用

Agent2 生成 SQL 时会读取 report_config，里面包含：

```text
nameColumn
parentColumn
levelColumn
trackColumn
metrics
analysisDimensions
sqlOutputContract
```

这会约束 Agent2：

```text
最终 SQL 应该输出哪些标准列
如果源表没有 节点名称 / 上级名称 / 层级，应该通过 SELECT 别名生成
组织链路应该怎么展开
指标列应该叫什么
```

### 2.2 report_spec_builder 使用

SQL 执行后，`report_spec_builder` 会用 report_config 来理解返回结果：

```text
哪一列是节点名称
哪一列是上级名称
哪一列是层级
哪些列是指标
达成率、金额、缺口如何格式化
风险阈值是多少
```

然后它动态生成：

```text
KPI 卡片
对比表
下钻卡片
图表数据
风险/标杆标签
layoutTemplate
```

### 2.3 前端使用

前端不是直接读 report_config 来决定全部 UI，而是更多依赖后端返回的：

```text
report_spec
```

但是前端也会在树构建、指标格式化、兜底逻辑里使用 report_config。

## 3. 当前混乱的根因

现在感觉混乱，不是因为 report_config 没用，而是因为三类东西混在一起了。

### 3.1 数据集知识

这类应该放在“数据集管理”：

```text
DDL
数据字典
LLD
Agent2 Prompt
Agent4 Prompt
Golden SQL
```

它回答的是：

```text
AI 是否懂这个数据集？
```

### 3.2 报告契约

这类应该放在“报告契约配置”：

```text
标准输出列
核心指标
层级链路
风险阈值
信号灯规则
报告写作口径
```

它回答的是：

```text
SQL 结果应该如何变成报告？
```

### 3.3 场景模板

这类不建议让你手工维护一堆配置：

```text
单体分析
对比分析
排名分析
诊断分析
下钻分析
趋势分析
```

它应该由系统根据问题动态识别。

它回答的是：

```text
这个问题应该用哪种展示方式？
```

## 4. 建议的新架构

建议把链路拆成三层，职责明确：

```text
第一层：数据集知识层
  DDL / 字典 / LLD / Agent2 / Agent4 / Golden SQL

第二层：报告契约层
  指标 / 标准列 / 层级 / 阈值 / 信号灯 / 写作口径

第三层：场景渲染层
  detail / comparative / ranking / diagnostic / trend
```

整体链路：

```text
用户问题
  ↓
场景识别器
  - detail
  - comparative
  - ranking
  - diagnostic
  - trend
  ↓
数据集知识层
  - 让 Agent2 知道怎么查
  ↓
报告契约层
  - 让 Agent2 输出标准列
  - 让后端/前端知道怎么建报告
  ↓
场景渲染层
  - 根据 scene 决定报告结构
```

## 5. 报告模板到底还要不要维护

要维护，但不应该维护得很重。

你不应该维护：

```text
东部和西部对比模板
三大业务部对比模板
九大分公司对比模板
某代表处下钻模板
排名模板
```

这些应该交给系统动态判断。

你只需要维护每个数据集稳定不变的部分：

```text
1. 核心指标有哪些
2. 指标对应 SQL 输出列叫什么
3. 组织/业务层级是什么
4. 父子关系列叫什么
5. 风险阈值是多少
6. 报告应该关注什么管理口径
```

也就是说，你维护的不是“每个问题的模板”，而是：

```text
这个数据集的报告说明书
```

## 6. 是否可以智能补齐报告配置

可以，而且建议做。

但是不能只靠 DDL。DDL 只能知道字段名和类型，不能完全知道业务含义。

更可靠的输入应该是：

```text
DDL
数据字典
LLD
Agent2 Prompt
Agent4 Prompt
Golden SQL
SQL 测试样例结果
用户确认
```

智能补齐报告配置应该生成：

```text
标准输出列
核心指标 metrics
分析层级 analysisDimensions
风险阈值建议
信号灯规则
Agent2 SQL 输出契约
Agent4 报告口径
```

但生成后必须让用户确认，不建议直接无脑覆盖。

## 7. 推荐的最小维护方式

未来你维护一个新数据集时，推荐流程：

```text
1. 数据集管理：维护 DDL
2. 数据集管理：点“智能补齐”
   - 自动生成字段字典
   - 自动生成 Agent2 / Agent4
   - 自动生成基础 Golden SQL
3. SQL 测试：跑几条 SELECT 验证真实数据
4. 报告契约配置：点“智能补齐报告配置”
   - 自动识别指标、层级、标准输出列
5. 人工确认报告契约
6. 问几个标准问题验证：
   - 单体：东部业绩怎么样
   - 对比：东部和西部对比
   - 排名：哪个分公司最好
   - 下钻：东部下面代表处情况
   - 诊断：西部为什么差
```

## 8. 开发升级方案

### 阶段一：只做可观测，不改主逻辑

目标：让你知道每个问题到底走了哪条链路。

新增“执行链路说明”：

```json
{
  "dataset_id": 3,
  "route_decision": "generate_sql",
  "scene": "comparative",
  "layoutTemplate": "comparison",
  "report_config_used": true,
  "report_config_source": "dataset_config|default",
  "scene_reason": [
    "命中多个主体",
    "问题包含 对比/比较 关键词"
  ],
  "standard_columns_detected": ["节点名称", "上级名称", "层级", "达成率"],
  "missing_contract_fields": []
}
```

前端展示：

```text
本次链路：对比分析
数据集：商用事业部
报告契约：已启用
场景判断：命中 2 个主体 + 包含“对比”
```

收益：

```text
不改变结果，只增加透明度。
风险最低。
```

### 阶段二：抽出场景注册表

目前场景识别散落在 `report_spec_builder.py` 中。

建议抽成：

```text
backend/report_scene_registry.py
```

结构：

```python
SCENES = {
    "detail": {
        "label": "单体分析",
        "triggers": [...],
        "required_contract": ["nameColumn", "metrics"],
        "layout": "detail",
    },
    "comparative": {
        "label": "对比分析",
        "triggers": [...],
        "required_contract": ["nameColumn", "metrics"],
        "layout": "comparison",
    },
    "ranking": {
        "label": "排名分析",
        "triggers": [...],
        "required_contract": ["nameColumn", "rateMetric"],
        "layout": "ranking",
    },
    "diagnostic": {
        "label": "诊断分析",
        "triggers": [...],
        "required_contract": ["nameColumn", "metrics", "signalRules"],
        "layout": "diagnostic",
    }
}
```

收益：

```text
以后新增“趋势分析”“同比环比分析”，只加一个 scene，不用到处改。
```

### 阶段三：报告契约健康度校验

新增一个后端校验函数：

```text
validate_report_contract(dataset_id)
```

检查：

```text
是否有 nameColumn
是否有 parentColumn
是否有 metrics
是否有 rate 指标
是否有 amount 指标
analysisDimensions 是否为空
signalRules 是否引用了不存在的 metric key
sqlOutputContract.requiredColumns 是否包含基础列
```

返回：

```text
健康 / 警告 / 严重缺失
```

前端展示：

```text
报告契约健康度 82 / 100
缺失：未配置 parentColumn，无法稳定下钻
建议：根据 SQL 测试结果自动生成
```

### 阶段四：智能补齐报告配置

在“报告模板配置”页新增：

```text
智能补齐报告配置
```

输入：

```text
当前数据集 DDL
数据字典
LLD
Agent2 Prompt
Agent4 Prompt
Golden SQL
最近一次 SQL 测试结果
```

输出：

```json
{
  "nameColumn": "节点名称",
  "parentColumn": "上级名称",
  "levelColumn": "层级",
  "trackColumn": "条线",
  "metrics": [],
  "analysisDimensions": [],
  "signalRules": [],
  "sqlOutputContract": {},
  "agentReportGuidance": ""
}
```

要求：

```text
只生成初稿
必须人工确认保存
不能覆盖用户已有配置，除非用户确认
```

### 阶段五：场景回归测试

每个数据集至少维护 5 个场景测试：

```text
单体分析：东部业绩怎么样
对比分析：东部和西部对比
排名分析：哪个分公司最好
下钻分析：东部下面代表处情况
诊断分析：西部为什么差
```

每个测试校验：

```text
命中数据集正确
scene 正确
layoutTemplate 正确
SQL 只读
SQL 输出标准列满足报告契约
report_spec 有 kpis/charts/accordions
前端不会白屏
```

## 9. 严格校验方案

为了避免升级后“看起来能跑，但内部重复/没用上”，需要加这些校验。

### 9.1 链路唯一性校验

同一问题只能有一个最终 scene：

```text
detail / comparative / ranking / diagnostic / trend
```

不能同时既是 detail 又是 comparative。

### 9.2 契约使用校验

如果 report_config 存在，必须记录：

```text
Agent2 是否收到 report_config
report_spec_builder 是否使用 report_config
前端是否收到 report_spec
```

### 9.3 标准列校验

SQL 结果必须检查：

```text
nameColumn 是否存在
metrics 中 column 是否存在
如果要下钻，parentColumn 是否存在
如果要分层，levelColumn 是否存在
```

如果缺失，不能静默降级，要在执行链路里提示。

### 9.4 场景渲染校验

每种 scene 必须有对应输出：

```text
comparative -> comparison table / compare kpis
ranking -> ranking chart / top bottom
detail -> focus node / drill children
diagnostic -> risk nodes / reasons / actions
```

### 9.5 重复内容校验

同一报告中避免：

```text
KPI 和正文重复堆同一段
左侧报告和全屏报告内容不一致
代表处和业务员层级混在一起
两个图表展示同一组指标却排序不同
```

## 10. 不建议马上做的事

暂时不建议：

```text
1. 让用户维护大量“问题模板”
2. 每种问法写一套硬编码报告
3. 直接废弃 report_config
4. 让 Agent4 自己决定前端结构
5. 把所有场景都塞进一个超级 prompt
```

原因：

```text
维护成本会越来越高
不同数据集难复用
场景之间容易互相污染
前端报告不可控
```

## 11. 推荐最终页面命名

当前：

```text
报告模板配置
```

建议改为：

```text
报告契约配置
```

页面分区：

```text
1. 标准输出列
2. 核心指标
3. 分析层级
4. 风险规则
5. 场景支持情况
6. JSON 高级配置
```

新增按钮：

```text
智能补齐报告契约
校验报告契约
生成场景测试题
```

## 12. 推荐开发顺序

优先级从低风险到高收益：

```text
P0 先加文档和链路说明，不改主逻辑
P1 增加 report_debug / scene_debug 返回字段
P2 前端显示“本次使用了哪个场景”
P3 抽出 scene registry，但保持原有行为不变
P4 加报告契约健康度校验
P5 加智能补齐报告契约
P6 加场景回归测试
P7 再考虑页面重命名和 UI 优化
```

## 13. 结论

报告模板不是没用，但它不应该继续叫“模板”。

它应该承担的是：

```text
数据集报告契约
```

你要维护的是稳定口径：

```text
指标
层级
标准列
阈值
写作口径
```

系统要自动处理的是动态场景：

```text
单体
对比
排名
下钻
诊断
趋势
```

下一步最稳的开发方式是：

```text
先把链路可观测化，再抽场景注册表，再做报告契约智能补齐。
```

这样不会推翻现有动态识别上下级的能力，也能让后续维护更简单。
