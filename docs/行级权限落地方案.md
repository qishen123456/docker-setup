# 行级权限落地方案

## 1. 当前问题

现在已经有了：

- 组织树类型
- 组织树节点
- 员工绑定组织节点
- 数据集绑定组织树和授权组织范围

但业务数据库里的数据本身没有组织编码，所以现在这套权限只能做到：

- 控制用户能不能看到某个数据集
- 不能真正控制用户只能看到自己组织范围内的行数据

原因很简单：

```text
员工授权的是组织树节点
数据库查询结果里却没有字段能和组织树节点对应
所以后端不知道该用哪一列去过滤
```

要让行级权限真正生效，必须补一层：

```text
数据集里的业务字段  <->  组织树节点
```

---

## 2. 最终目标

用户访问数据集时，后端自动完成：

```text
当前用户
  -> 查到员工授权组织节点
  -> 查到数据集绑定的组织树和组织范围
  -> 两者取交集
  -> 找到数据表里能匹配组织的字段或映射表
  -> 自动给 SQL 加行级过滤
```

普通用户只能看到自己有权限的组织数据。

超级管理员可以看到全部数据。

没有匹配到组织的数据，默认不可见。

---

## 3. 需要新增的核心能力

### 3.1 数据集权限映射配置

在“数据集权限控制”里增加一块配置，不叫 SQL 字段，叫：

```text
数据范围匹配方式
```

建议字段：

| 配置项 | 说明 |
| --- | --- |
| 权限模式 | 公开 / 按组织树控制 / 停用 |
| 组织树类型 | 数据集对应哪套组织树 |
| 授权组织 | 数据集允许哪些组织范围 |
| 匹配方式 | 直接字段 / 名称匹配 / 映射表 |
| 业务匹配字段 | 数据表里的分公司、部门、代表处等字段 |
| 组织树匹配字段 | 默认用组织树节点编码 |
| 未匹配策略 | 默认拒绝 |

页面上只给管理员看业务概念，不暴露 SQL 术语。

---

## 4. 三种落地方式

## 4.1 方式一：源表直接有组织编码

适用情况：

业务表里已经有类似字段：

- 组织编码
- 分公司编码
- 事业部编码
- 部门编码
- org_code
- dept_id
- branch_code

执行逻辑：

```sql
WHERE 业务表.组织编码 IN ('有权限的组织编码1', '有权限的组织编码2')
```

优点：

- 最简单
- 最稳定
- 性能最好

缺点：

- 要求源表本身有组织编码

---

## 4.2 方式二：源表只有组织名称

适用情况：

业务表里没有编码，但有名称：

- 分公司名称
- 事业部名称
- 部门名称
- 代表处名称

执行逻辑：

```sql
WHERE 业务表.分公司名称 IN ('东部分公司', '北部分公司')
```

优点：

- 可以较快跑起来

缺点：

- 名称可能变
- 名称可能不唯一
- 有错别字、简称时容易匹配失败

这个适合作为过渡方案。

---

## 4.3 方式三：新增业务组织映射表

这是最推荐的长期方案。

当业务数据没有组织编码，或者组织关系比较复杂时，新增一张映射表：

```text
business_org_mapping
```

建议字段：

| 字段 | 说明 |
| --- | --- |
| dataset_code | 数据集编码 |
| business_key | 业务对象编码，比如客户、代表处、人员、区域 |
| business_name | 业务对象名称 |
| org_tree_type_id | 组织树类型 |
| org_node_code | 组织节点编码 |
| org_node_name | 组织节点名称 |
| enabled | 是否启用 |

例子：

| business_key | business_name | org_node_code | org_node_name |
| --- | --- | --- | --- |
| rep_001 | 东部代表处 | gg9c5c9ce5c3faa9 | 东部分公司 |
| rep_002 | 北部代表处 | eb2685cfab3651df | 北部分公司 |

执行逻辑：

```sql
SELECT ...
FROM 业务表 t
JOIN business_org_mapping m
  ON t.代表处 = m.business_name
WHERE m.org_node_code IN ('有权限的组织编码1', '有权限的组织编码2')
```

优点：

- 不要求原业务表改结构
- 可以处理复杂映射
- 后续维护清晰

缺点：

- 需要多维护一张映射关系

## 5. 推荐实施路线

## 第一阶段：明确每个数据集的组织口径

给每个数据集确认一件事：

```text
这个数据集的数据，应该按哪个业务字段归属组织？
```

例如：

| 数据集 | 组织口径 |
| --- | --- |
| 消费者数据集 | 分公司 |
| 商用事业部数据集 | 业务部 / 分公司 |
| 线下门店数据集 | 门店归属分公司 |

产出：

```text
数据集 -> 组织树类型 -> 业务匹配字段
```

---

## 第二阶段：改数据集权限配置

数据集权限页面保持简洁：

```text
数据集
权限模式
组织树类型
授权组织
匹配方式
匹配字段
备注
编辑
```

不要再显示：

- SQL 过滤结果列
- 命中员工说明
- 兜底说明大段文字
- 技术型字段

命中员工和预检结果可以放到单独的“权限预检”里。

---

## 第三阶段：增加权限预检

保存前或保存后提供一个“预检”按钮。

预检展示：

```text
数据集：商用事业部销售分析
组织树：商用组织树
授权组织：东部分公司、北部分公司
匹配方式：名称匹配
匹配字段：分公司名称
命中员工：3 人
可见组织编码：2 个
未匹配业务对象：5 个
```

预检的作用：

- 管理员能知道配置有没有生效
- 能发现业务表里哪些组织名称匹配不上
- 避免权限配置看起来保存了，实际没有过滤

---

## 第四阶段：后端真正拼接行级过滤

后端执行 SQL 前做：

```text
1. 判断数据集是否启用组织树权限
2. 获取当前员工授权组织节点
3. 获取数据集授权组织节点
4. 两者取交集
5. 根据数据集匹配方式生成过滤条件
6. 拼接到最终 SQL
```

三种过滤方式：

```text
直接字段：WHERE t.org_code IN (...)
名称匹配：WHERE t.branch_name IN (...)
映射表：JOIN 映射表后 WHERE m.org_node_code IN (...)
```

---

## 第五阶段：未匹配数据默认拒绝

规则必须明确：

```text
普通用户：
  没有匹配到组织的数据，不可见

超级管理员：
  可以查看全部数据

停用数据集：
  所有人不可见，超级管理员除外可按管理需要决定
```

不要默认放行未匹配数据，否则行级权限会穿透。

---

## 6. 我建议的最终方案

短期：

```text
先支持名称匹配
让现有业务数据不用改表，也能跑起来
```

中期：

```text
增加业务组织映射表
把代表处、客户、人员、区域等业务对象映射到组织树节点
```

长期：

```text
重要业务宽表里尽量沉淀稳定组织编码
行级权限优先按编码过滤
```

最终优先级：

```text
直接组织编码 > 映射表 > 名称匹配
```

## 8. 当前最应该先做什么

建议先做这一版：

```text
数据集权限控制里增加：

匹配方式：直接字段 / 名称匹配
匹配字段：从数据集字段里选择

后端：
根据员工组织权限和数据集组织范围取交集
再用匹配字段拼 WHERE IN 过滤
```

这样最小改动就能先把行级权限跑起来。

映射表可以作为第二步增强。
