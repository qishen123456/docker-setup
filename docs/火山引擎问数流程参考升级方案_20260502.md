# SmartAsk 参考火山引擎 DataAgent 问数流程升级方案

> 版本：V1.0  
> 日期：2026-05-02  
> 目标：参考火山引擎 DataAgent 问数链路、数据集配置、Prompt 配置、ELT 规范、图表实践和提问建议，升级当前 SmartAsk 的数据集知识、Golden SQL 覆盖、歧义确认、SQL 可信生成和报告输出闭环。

## 1. 结论先行

当前 SmartAsk 已经具备 4-Agent 问数链路、数据集知识库、Golden SQL、低相似确认、ReportSpec v2、Docker 部署等基础能力，但当前商用事业部数据集仍然偏“单样本驱动”：Golden SQL 只有少量高质量样例，LLD 和字段字典能解释基础口径，但还没有形成覆盖老板常问场景、边界场景、歧义场景、图表场景和反例场景的 SQL 样本库。

下一步不建议一次性把系统改成完整企业级 DataAgent。更稳的路线是三阶段升级：

1. 第一阶段先把当前商用事业部做稳：保留秒出体验，但补上意图识别、空结果拦截、Top/Bottom/下钻等高频场景，避免“秒出空报告”。
2. 第二阶段再做可信问数闭环：补齐 Golden SQL Pack、回归用例、执行前后复核和 ReportSpec 图表规则，让常问问题稳定可验收。
3. 第三阶段才做企业级扩展：语义宽表、数据集资料自动生成、多候选 SQL 投票、反馈学习和数据集健康评分。

阶段原则是：先解决当前用户可感知的问题，再提升准确率和可维护性，最后再追求可复制、可迁移和企业级治理。

## 2. 已阅读资料

本方案参考了目录 `火山引擎/问数逻辑pdf/火山智能体pdf/` 下的资料，重点吸收以下工程原则：

## 3. 当前项目与数据集现状

### 3.1 当前链路

SmartAsk 当前链路为：

```text
用户提问
  -> Agent1 数据集路由与歧义确认
  -> Agent2 SQL 生成
  -> Agent3 SQL 审核
  -> SQL 执行
  -> Agent4 业务解读
  -> ReportSpec v2 确定性报告协议
  -> 前端动态 KPI / 图表 / 下钻 / 全屏展示
```

已有优势：

| 能力 | 当前状态 |
| --- | --- |
| 数据集路由 | 支持候选打分、LLM 仲裁、低相似确认。 |
| SQL 生成 | 支持 LLD、DDL、字段字典、Golden SQL 样例注入。 |
| SQL 审核 | Agent3 可检查只读、安全、年份、层级隔离等规则。 |
| 报告渲染 | 后端 ReportSpec v2 生成结构，前端按协议渲染。 |
| 部署 | Docker 一键部署已具备基础。 |

主要缺口：

| 缺口 | 风险 |
| --- | --- |
| Golden SQL 样例太少 | 相似问题容易变成 LLM 自由发挥，SQL 不稳定。 |
| 原始数据仍是 JSONB 字段 | 每次 SQL 都要重复字段提取和金额清洗，出错面大。 |
| 场景矩阵未系统化 | 老板问 Top、Bottom、缺口、下钻、对比、风险时，命中不一定稳定。 |
| 歧义确认还不够细 | “东部”“节点”“表现不好”“任务压力”等词需要更细的确认模板。 |
| 图表选择还偏规则兜底 | 应把问题意图、字段角色、图表类型配置成结构化协议。 |

### 3.2 当前商用事业部数据集

当前核心数据集：

| 项 | 内容 |
| --- | --- |
| dataset_code | `angel_business_2026` |
| dataset_name | 商用事业部 |
| 主表 | `angel_group_data` |
| 字段模式 | `fields JSONB` |
| 固定年份 | 2026 |
| 核心维度 | 事业部、分公司、代表处、业务代表、当前年 |
| 核心指标 | 总任务金额、年度开单金额、达成率、剩余任务金额 |
| 管理链条 | 区域：事业部 -> 分公司 -> 代表处 -> 业务代表；行业：事业部 -> 业务部 -> 业务代表 |
| 核心红线 | 上级统计必须排除下级明细，避免数据翻倍。 |

## 4. 目标架构

升级后目标不是让模型“猜得更聪明”，而是让模型在更清晰的轨道上行动：

```text
数据源
  -> 数据质量扫描
  -> 问数语义宽表/视图
  -> 数据集资料自动生成
     - DDL
     - LLD
     - Data Dictionary
     - Metric Dictionary
     - Entity Dictionary
     - Synonyms
     - ReportConfig
     - Golden SQL Pack
     - Regression Cases
  -> 数据集发布与评分
  -> 问数执行
     - 意图解析
     - 数据集路由
     - 歧义确认
     - Golden SQL 检索
     - 多候选 SQL 生成
     - SQL 执行前复核
     - SQL 执行后结果校验
     - ReportSpec 生成
     - 回归反馈入库
```

## 5. Golden SQL 全场景枚举计划

### 5.1 样例不是越多越好，而是要成体系

每条 Golden SQL 必须包含：

| 字段 | 说明 |
| --- | --- |
| `question` | 标准问题。 |
| `alternative_questions` | 同义问法，如“业绩怎么样”“开单表现”“完成率”。 |
| `intent_type` | summary/detail/ranking/comparison/risk/drilldown/chart/confirmation。 |
| `scope` | 事业部/分公司/代表处/业务部/业务代表/条线/全局。 |
| `metric_set` | 任务、开单、达成率、剩余任务。 |
| `dimension_set` | 条线、层级、节点、上级、人员。 |
| `sql_text` | 可直接执行的只读 SQL。 |
| `expected_columns` | 输出列，供 Agent3 和 ReportSpec 校验。 |
| `chart_hint` | 推荐图表：指标卡/柱状图/条形图/表格/组合图/热力图。 |
| `redline_rules` | 年份过滤、层级隔离、只读、LIMIT、金额清洗。 |
| `quality_score` | 初始建议 80-100，回归通过后提升。 |
| `regression_assertions` | 行数、字段、关键节点、数值范围、是否需要确认。 |

### 5.2 SQL 场景矩阵

这里的 72 条不是“已经准确的 SQL”，而是 72 个候选场景槽位，用来保证覆盖面。任何候选 SQL 必须通过执行校验、口径校验、结果抽样和回归断言后，才能从候选样例升级为 Golden SQL。

因此第一阶段不追求 72 条，只挑 15-20 个高频问题做准；第二阶段再按验证通过率逐步扩容。完整候选矩阵如下：

| 大类 | 场景 | SQL 数量 | 示例问题 |
| --- | --- | ---: | --- |
| 总览 | 事业部总任务、开单、达成率、缺口 | 4 | 商用事业部当前年整体完成怎么样？ |
| 区域条线 | 分公司对比 | 4 | 东南西北分公司谁达成率最高？ |
| 区域条线 | 单个分公司看板 | 4 | 东部分公司当前年达成率和剩余任务是多少？ |
| 区域条线 | 代表处 Top/Bottom | 8 | 东部分公司下哪些代表处最好和最差？ |
| 区域条线 | 代表处下钻业务代表 | 8 | 安徽代表处下面每个业务员开单情况如何？ |
| 行业条线 | 业务部对比 | 4 | 餐饮、工业医疗、公共办公哪个完成率最高？ |
| 行业条线 | 单个业务部看板 | 3 | 公共办公业务部任务缺口是多少？ |
| 行业条线 | 业务代表 Top/Bottom | 8 | 业务代表 Top10 是谁？低于 10% 的是谁？ |
| 风险 | 达成率低于阈值 | 5 | 哪些节点达成率低于 10%？ |
| 风险 | 剩余任务金额最大 | 5 | 哪些节点剩余任务压力最大？ |
| 资源配置 | 待分配任务 | 4 | 任务有没有滞留在上级，没有拆到代表处或业务员？ |
| 空白/覆盖 | 行业线区域空白 | 3 | 哪些区域没有行业线开单？ |
| 排名 | 按开单、任务、达成率排序 | 5 | 按年度开单金额排名前 5 的节点是谁？ |
| 对比 | 条线、上级、节点交叉对比 | 4 | 区域条线和行业条线贡献差异如何？ |
| 确认流 | 组织歧义、指标歧义、低相似 | 7 | 东部表现怎么样？哪些节点不好？ |

候选 SQL 升级为 Golden SQL 的准入标准：

| 校验项 | 准入要求 |
| --- | --- |
| SQL 执行 | 能在当前数据源稳定执行，无语法错误、权限错误、超时错误。 |
| 输出字段 | 满足该场景的 `expected_columns`，报告必需字段不缺失。 |
| 口径红线 | 年份、金额清洗、层级隔离、只读、LIMIT 全部符合。 |
| 结果合理性 | 行数、关键节点、达成率范围、金额汇总与人工抽样一致。 |
| 问题匹配 | 标准问法和 2-3 个同义问法都能命中同一 SQL 或同一口径。 |
| 空结果处理 | 只有业务上确实为空时才允许返回 0 行，否则必须触发自检或确认。 |
| 回归断言 | 至少包含行数范围、必需字段、关键节点、数值范围、是否需要确认。 |

未通过准入的样例只能标记为 `candidate_sql` 或 `needs_review`，不能进入 Golden SQL Pack，也不能作为 Agent2 的强参考样例。

### 5.3 第一批 SQL 模板分层

#### A. 基础字段提取模板

所有 SQL 复用一个标准 CTE：

```sql
WITH 字段提取 AS (...),
基础数据 AS (...),
维度汇总 AS (...)
SELECT ...
```

规则：

| 规则 | 要求 |
| --- | --- |
| JSONB 兼容 | `jsonb_typeof(fields->'字段')='array'` 时取 `->0->>'text'`，否则取 `->>`。 |
| 年份 | `COALESCE(NULLIF(当前年, ''), '2026') = '2026'`，兼容源数据年份为空的情况。 |
| 金额 | `regexp_replace(..., '[^0-9.-]', '', 'g')` 清洗后转 numeric。 |
| 层级隔离 | 上级组织统计必须排除下级明细。 |
| 安全 | 只允许 SELECT/WITH/SHOW，必须 LIMIT。 |

#### B. 总览 SQL

输出事业部总任务、开单、达成率、剩余任务，适合指标卡 + 文字解释。

#### C. 分层 SQL

输出 `条线、层级、节点名称、上级名称、总任务金额、年度开单金额、达成率、剩余任务金额`，作为 ReportSpec 的主输入。

#### D. 排名 SQL

针对 Top/Bottom、达成率排名、缺口排名、开单排名，必须明确排序指标和排序方向。

#### E. 下钻 SQL

针对“分公司 -> 代表处 -> 业务代表”或“业务部 -> 业务代表”，必须保留 `上级名称`，让前端可以动态展开。

#### F. 风险 SQL

包含阈值参数：达成率 `<10%`、缺口 TopN、任务为 0 但开单不为 0、任务金额很高但开单为 0。

#### G. 确认 SQL 与非执行样例

模糊问题不应该生成 SQL，而是生成确认项。也要作为回归样例入库，例如：

| 问题 | 应返回 |
| --- | --- |
| 东部表现怎么样？ | 确认：东部分公司整体、下属代表处、还是下属业务代表？ |
| 哪些节点不好？ | 确认：按达成率低、剩余任务高、开单低，还是综合风险？ |
| 业务怎么样？ | 确认：区域条线、行业条线、事业部总览？ |
| 今年如何？ | 自动改写为 2026，但展示年份口径。 |
| 问明显无关主题 | 低相似确认，不直接执行。 |

## 6. 数据集自动化生成方案

### 6.1 生成入口

新增数据集资料生成器建议命名为：

```text
backend/dataset_copilot/profile_generator.py
backend/dataset_copilot/golden_sql_pack_generator.py
backend/dataset_copilot/regression_pack_generator.py
```

输入：

| 输入 | 来源 |
| --- | --- |
| 业务说明 | 用户上传的提示词、数据说明 Markdown。 |
| 表结构 | PostgreSQL information_schema 或现有 DDL。 |
| 样例数据 | 表前 N 行、字段枚举、数值分布。 |
| 当前 ReportConfig | `bs_dataset_report_config`。 |
| 用户问题集 | 推荐问题、历史问答、老板常问问题。 |

输出：

| 输出 | 入库表 |
| --- | --- |
| DDL | `bs_schema_definitions` |
| LLD | `bs_lld_documents` |
| Data Dictionary | `bs_data_dictionary_items` |
| 业务术语/同义词 | `bs_dataset_synonyms` + external config |
| Golden SQL | `bs_golden_sql_samples` |
| Agent Prompt Fragments | `bs_agent_prompt_fragments` |
| 推荐问题 | `bs_common_questions` |
| 回归用例 | `bs_regression_cases` |
| 报告协议配置 | `bs_dataset_report_config` |

### 6.2 自动清理旧错误数据

删除旧数据不能直接物理删除，建议走“版本化 + 失效”策略：

| 对象 | 清理方式 |
| --- | --- |
| 旧 Golden SQL | `is_active=false`，保留审计。 |
| 明显错误 SQL | 标记 `quality_score=0`，记录错误原因。 |
| 旧 LLD/Prompt | 新版本生效，旧版本失效。 |
| 旧推荐问题 | 保留但降权，避免用户历史丢失。 |
| 错误业务数据 | 进入数据质量报告，用户确认后再清理或重导入。 |

## 7. 问数执行链路升级

### 7.1 Agent1：路由与确认

升级点：

| 能力 | 规则 |
| --- | --- |
| 数据集路由 | 数据集语义、字段同义词、业务术语、Golden SQL 命中共同打分。 |
| 上下文继承 | 支持上一轮已确认的数据集、组织范围、指标口径。 |
| 低相似确认 | 低于阈值时不执行 SQL。 |
| 多数据集歧义 | 展示候选数据集、命中原因、字段和样例问题。 |
| 单数据集口径歧义 | 对“节点、表现、东部、业务、风险”等词进入口径确认。 |

### 7.2 Agent2：SQL 生成

升级点：

| 能力 | 规则 |
| --- | --- |
| Golden SQL 优先 | 命中高质量样例时轻改写，不重新发明 SQL。 |
| 模板参数化 | 组织、层级、指标、排序、阈值替换为参数。 |
| 多候选生成 | 同一问题生成 2-3 条候选 SQL，后续投票。 |
| 结构强约束 | 输出字段必须匹配 ReportSpec 需要的列。 |
| 失败重试 | SQL 为空、解释文本、非只读、无 LIMIT 时自动重试。 |

### 7.3 Agent3：执行前后复核

执行前复核：

| 检查项 | 示例 |
| --- | --- |
| 只读 | 禁止 insert/update/delete/drop。 |
| 表范围 | 仅允许当前数据集授权表。 |
| 年份 | 2026 口径必须明确。 |
| 层级隔离 | 分公司/代表处统计不混入下级。 |
| 金额清洗 | 金额字段必须 numeric。 |
| LIMIT | 防止超大结果。 |

执行后复核：

| 检查项 | 示例 |
| --- | --- |
| 空结果 | 需要提示可能是筛选过窄或口径不匹配。 |
| 字段缺失 | ReportSpec 必需字段缺失则回退或修 SQL。 |
| 异常数值 | 达成率异常高、任务为 0、负金额需要标记。 |
| 组织链完整性 | `上级名称`、`节点名称`、`层级` 是否可组成树。 |

### 7.4 多候选投票

参考火山引擎“多路并行 + 首次 SQL 投票”的思想，SmartAsk 可做轻量版：

1. Golden SQL 直接候选。
2. 规则模板候选。
3. LLM 生成候选。
4. 每条候选先审核再执行小样本。
5. 对比输出列、行数、关键指标、SQL shape 和业务口径。
6. 选择兼容性最高、风险最低的候选。

## 8. ReportSpec 与图表升级

### 8.1 图表选择规则

| 问题意图 | 图表建议 |
| --- | --- |
| 单一指标 | 指标卡。 |
| 多节点比较 | 柱状图或条形图。 |
| Top/Bottom | 条形图 + 表格。 |
| 时间趋势 | 折线图。当前数据缺少月份时不要硬画趋势。 |
| 占比 | 饼图/环形图，分类不宜过多。 |
| 指标组合 | 开单/任务用柱，达成率用线或标签。 |
| 空白区域/行业 | 热力图。 |
| 明细核验 | 表格。 |

### 8.2 报告结构

报告不再写死“区域 + 行业”两块，而由 ReportConfig 决定：

| 配置项 | 说明 |
| --- | --- |
| `hierarchy` | 数据集有哪些层级，谁是父子关系。 |
| `metrics` | 哪些指标是金额、比例、数量。 |
| `default_sections` | 总览、分层对比、风险、建议。 |
| `drilldown_rules` | 哪些节点可展开、展开后显示什么图。 |
| `chart_rules` | 根据字段角色和问题意图选择图表。 |
| `narrative_rules` | 文字必须包含金额、达成率、缺口、风险原因。 |

## 9. 三阶段实施路线

这次升级不按“一次性企业级”推进，而是拆成三个可验收阶段。每一阶段都能单独上线、单独回滚、单独验收。

### 阶段一：当前问数先稳住

目标：保留现在“常见问题秒出”的体验，但把明显不可信的秒出挡住。

适合周期：1-2 天。

核心判断：当前最大问题不是能力不够炫，而是规则 SQL 和规则报告太容易在意图没识别准时仍然输出结果。例如“哪些代表处达成率最低”不应该返回 0 行空报告。

交付物：

| 任务 | 验收标准 |
| --- | --- |
| 补齐意图分类 | 能区分总览、单主体、Top/Bottom、对比、下钻、风险、图表、确认。 |
| 修正规则 SQL 误命中 | “哪些代表处达成率最低”不再被当成实体过滤。 |
| 增加空结果拦截 | SQL 返回 0 行时，不直接生成正式报告，进入 SQL 自检或口径提示。 |
| 固化 15-20 条高频 SQL | 覆盖事业部总览、东部分公司、代表处排名、业务代表 Top、风险节点。 |
| 保留规则快路径 | 明确命中高频模板时仍然 1 秒内返回。 |
| 基础回归脚本 | 每条高频问题校验行数、字段、关键节点、是否应确认。 |

阶段一完成后的效果：

| 用户体验 | 预期表现 |
| --- | --- |
| 常问问题 | 继续快速出结果。 |
| 排名/Top/Bottom | 有正确排序，不再空跑。 |
| 模糊问题 | 该确认就确认，不强行出报告。 |
| 空结果 | 展示可能原因，不包装成正式结论。 |

### 阶段二：可信问数闭环

目标：从“能跑”升级为“可解释、可验收、可回归”。

适合周期：3-5 天。

核心判断：这一阶段才系统补齐火山 DataAgent 文档里强调的数据集语义、字段口径、Golden SQL、复核和图表协议，但仍然只围绕当前商用事业部，不急着泛化到所有数据集。

交付物：

| 任务 | 验收标准 |
| --- | --- |
| Golden SQL Pack 逐步扩容 | 以 72 个候选场景为覆盖目标，但只把通过准入校验的 SQL 纳入 Golden SQL Pack。 |
| 完善 LLD 和字段字典 | 业务术语、指标口径、组织层级、红线规则能被 Agent2/Agent3 使用。 |
| Agent3 执行前后复核 | 校验只读、表范围、年份、层级隔离、字段缺失、异常数值、空结果。 |
| ReportSpec 图表规则补齐 | KPI、分公司、代表处、业务代表、Top/Bottom、风险节点均可动态展示。 |
| 可信说明 | 报告展示命中口径、数据集、SQL 复核结论、结果可信度。 |
| 回归用例常态化 | 每次改 SQL、Prompt、ReportSpec 都能跑一遍核心用例。 |

阶段二完成后的效果：

| 用户体验 | 预期表现 |
| --- | --- |
| 老板常问问题 | 基本稳定，结果可复核。 |
| 报告质量 | 不只是有图有字，而是有口径、有结论、有风险、有建议。 |
| 问题变体 | “业绩怎么样”“完成如何”“压力最大”等同义问法能稳定命中。 |
| 迭代安全 | 改一处规则不会轻易把其他问题搞坏。 |

### 阶段三：企业级扩展

目标：把当前商用事业部沉淀出的能力，推广成可复制的数据集接入和问数治理体系。

适合周期：1-2 周以上，按业务优先级逐步做。

核心判断：只有阶段一和阶段二稳定后，才值得做自动生成、多候选投票、持续学习和数据集健康评分。否则会把不稳定能力自动化放大。

交付物：

| 任务 | 验收标准 |
| --- | --- |
| 语义宽表/视图 | 复杂 JSONB 提取和金额清洗前置，减少每条 SQL 的复杂度。 |
| 数据集资料自动生成器 | 从表结构、样例数据、业务说明生成 LLD、字典、SQL Pack、ReportConfig。 |
| 一键导入数据集知识 | 写入 bs_* 表，支持版本化、失效旧样例、回滚。 |
| 多候选 SQL 投票 | Golden SQL、规则模板、LLM 生成 SQL 可比较、可择优。 |
| 问答反馈闭环 | 用户确认好的 SQL 可沉淀为 Golden SQL，失败问题可归因分类。 |
| 数据集健康评分 | 展示字典覆盖率、SQL 覆盖率、回归通过率、失败类型分布。 |

阶段三完成后的效果：

| 用户体验 | 预期表现 |
| --- | --- |
| 新数据集接入 | 不再大量改代码，主要补数据集资料和验收用例。 |
| SQL 稳定性 | 多候选和投票降低单模型自由发挥风险。 |
| 运营治理 | 能看到哪些问题常失败、哪些字段口径不清、哪些 SQL 样例需要补。 |
| 企业级感知 | 具备可发布、可评分、可回归、可持续优化的数据产品形态。 |

## 11. 验收标准

| 验收项 | 标准 |
| --- | --- |
| SQL 可执行率 | 已入库 Golden SQL 执行成功率 >= 95%；候选 SQL 单独统计，不混入正式成功率。 |
| 口径正确率 | 分公司、代表处、业务代表层级不混算。 |
| 确认准确率 | 模糊问题不直接生成报告，进入确认。 |
| 报告可信度 | 报告必须展示路由把握、SQL 口径、结果可信说明。 |
| 图表专业度 | 不出现字段标签错、图例拥挤、无意义趋势图。 |
| 回归覆盖 | Golden SQL、确认流、低相似、ReportSpec 都有自动化用例。 |
| 数据集可迁移 | 换一个新数据集时，不需要改前端硬编码即可展示基础报告。 |

## 12. 下一步执行建议

建议先只启动阶段一，不要同时做阶段二和阶段三。阶段一开工顺序如下：

1. 先修当前已暴露问题：`哪些代表处达成率最低` 不能返回空报告，排名类问题必须走排名 SQL。
2. 梳理 15-20 个最高频问题，先覆盖总览、东部分公司、代表处排名、业务代表 Top、风险节点、模糊确认。
3. 给每个问题写最小回归断言：是否执行、行数范围、必需字段、关键节点、是否需要确认。
4. 把空结果处理改成自检流程：如果 SQL 返回 0 行，检查实体过滤、层级条件、年份条件和字段投影，再决定是否重试或提示用户。
5. 给报告增加可信说明：命中数据集、执行 SQL 来源、是否规则模板、是否 Golden SQL、复核结论。
6. 阶段一验收通过后，再进入阶段二：围绕 72 个候选场景逐条验证，通过一条沉淀一条，不把未验证 SQL 当 Golden SQL。

这条路线的核心判断是：先让当前系统“快但不乱说”，再让它“准且可复核”，最后再做“可复制、可治理、可扩展”。企业级不是一次改出来的，是每个阶段都有稳定交付后长出来的。
