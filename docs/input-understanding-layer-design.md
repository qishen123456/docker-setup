## 一、背景与痛点

### 1.1 问题定义

SmartAsk 的输入端假设"用户的问题大体正确"。真实用户（尤其语音输入、快速打字场景）的问题充满失误，现有体系对失误的处理是**补丁式的**：每发现一类失误加一条规则，永远追不上失误的多样性。

真实案例（全部来自本阶段实测）：

| 用户输入 | 失误类型 | 现状 |
|---|---|---|
| 「商泳事业部业绩」 | 同音错字（泳/用） | 错字快检可拦 ✅（已上线） |
| 「看下最好不的业务员」 | 方向词叠用手误 | 0.5 层弹卡 ✅（已上线） |
| 「看下最好最坏的业务员」 | 相邻双方向词口误 | 0.5 层弹卡 ✅（已上线） |
| 「靳峰的业绩」 | **2 字人名同音错**（峰/锋） | ❌ 查 0 行，输出垃圾分析报告 |
| 「丁洁的业绩」 | **2 字人名同音错**（洁/杰） | ❌ 同上 |
| 「商泳事业部业绩」（路由到「消费者事业部开单金额」数据集后 0 行） | 错字 + 路由错 | ❌ 0 行后照样生成"经营分析报告"，风险节点 0 个、痛点建议全是废话 |
| 「我打错了，是要看最不好的」（确认卡自由文本） | 对话内纠正 | ✅ 已上线（方案 C） |

### 1.2 根本结论（用户拍板）

- **规则做不到全面**。失误谱系 = 同音/谐音错 + 漏字 + 多字 + 不完整 + 方向口误 + 语音转文字偏差，每类的变体都是开放集合，正则/词表永远滞后。
- **大模型能力必须用**。「不差这些时间」——接受每问 +2~5s、多一次快模型调用的代价。
- 规则不退场，但**降级为证据官**：规则负责"从书架捞出最像的候选给 LLM 当小抄"，**决策权全部上交 LLM**。

### 1.3 设计目标

1. **容错全面**：同音、漏字、不完整、口误、语音转写偏差，统一由一层处理，不再按失误类型打补丁。
2. **不错杀**：清晰问题零打扰；高置信纠正只出不打断；真歧义才弹卡。
3. **可度量**：影子模式先行，误拦率 <2% 才允许开真实拦截。
4. **可回滚**：一键开关，关掉即回到现有老流程。

## 二、架构总览

```
用户输入
  │
  ▼
【输入理解层 · 每问必过】
  │
  ├─ ① 纯代码预处理（只备证据，不决策）
  │     · 规范化（去标点/空白/全半角）
  │     · 拼音索引锚定：从书架捞出字形/读音最接近的 ≤5 个
  │       节点/指标/别名 → 作为"锚定证据"
  │
  ├─ ② LLM 主判（唯一决策者）
  │     输入：原问题 + 书架摘要(按权限裁剪) + 锚定证据 + 对话上下文
  │     输出：{ action, canonical_question, candidates,
  │             confidence, reason }
  │
  └─ ③ 出口路由
        pass            → 按原问题进流水线
        rewrite(高置信)  → 书架校验 → 按改写问题进流水线 + 顶部细条「已按 XX 理解」
        soft_hint(中置信) → 原问题照常执行 + 非阻断细条「你是不是想问 XX？」
        clarify(真歧义)  → 弹确认卡（复用现有 early_clarify 通道）
  │
  ▼
问数流水线（现有，不动）
  │
  ▼
【0 行诊断 · LLM 增强】（结果为 0 行时触发）
  三分支：真没数据 / 路由错数据集 / 对象不存在
  → 给候选「你可能想问」，而非输出垃圾分析报告
```

**与现有组件的收编关系**（详见第六节）：错字快检、方向口误检测、事后守门员全部降级为"输入理解层的历史形态"，拼音索引建好后被 ① 吸收，LLM 主判上线后被 ② 吸收，按分期逐步退役。

## 三、拼音索引设计（P0，一切的地基）

### 3.1 为什么必须先建它

2 字人名同音错（靳峰→靳锋、丁洁→丁杰）是实测漏网的最大软肋。字形编辑距离对同音错几乎无效（峰/锋字形差很远），必须引入**读音维度**。拼音索引同时服务两个场景：输入理解层的证据锚定（①）和 0 行诊断的候选召回（五）。

### 3.2 索引内容

数据源 = 书架（`config/dataset_node_index.json` + 数据集别名表 + 指标名及近义词表），**构建时先按 `allowed_dataset_ids` 过滤**（权限红线，见 4.1）。

每个条目建三条键：

| 键 | 示例（靳锋） | 用途 |
|---|---|---|
| 原文 | 靳锋 | 精确匹配 |
| 全拼（含声调） | jin1feng1 | 2 字硬门判定 |
| 全拼（不含声调） | jinfeng | ≥3 字同音/近音召回 |
| 首字母 | jf | 缩写、漏字召回 |

### 3.3 召回算法（仅适用于 ≥3 字条目）

对问题中的每个候选片段（滑窗 2~6 字，复用 typo_fastpath 的滑窗逻辑）：

1. 算片段全拼（**不含声调**——语音转文字通常丢声调），与索引无调全拼键做拼音编辑距离（声母/韵母分开打分）
2. 同时算字形编辑距离
3. 综合分 = min(拼音距离权重, 字形距离权重)，取 Top-5 作为锚定证据

### 3.4 边界规则：2 字条目走硬门，不走打分

**打分层（3.3）只对 ≥3 字条目生效。2 字条目单独走硬门**：

- 仅当片段的**无调全拼与条目完全相等**时才进候选——即 2 字只做**同音召回**，**不做字形近似召回**
- 声调不参与的原因（实测修订）：pypinyin 返回声调符号（liú 非 liu2），且语音转文字常丢声调——「订杰 dìngjié→丁杰 dīngjié」是真实失误形态；候选集是封闭书架（346 别名），最终决策权在 LLM 主判层，放宽声调不误拦（京东 jingdong ≠ 京津 jingjin）
- 与 typo_fastpath 的"2 字别名主动放弃"（`typo_fastpath.py:151-154`）**互补不冲突**：快检放弃的是 2 字的**字形维度**纠错，拼音索引补上的是 2 字的**读音维度**。两个机制处理的维度不重叠
- 已知设计性放弃：非谐音的 2 字字形错（如「迟吴」→「迟昊」，读音完全不同）两层都不拦，由 0 行诊断兜底

其余规则继承错字快检教训：

- 人名片段必须命中别名表才参与，不与普通词混排
- 索引启动时一次性加载、内存常驻、查询零 IO
- **热更新**：每次构建证据前检查 `dataset_node_index.json` 的 mtime/版本号，变化才重建，避免书架更新后索引陈旧

### 3.5 依赖

需要 `pypinyin`。**注意**：容器内 `pip install` 不持久，正式落地必须改 `backend/requirements.txt` 并重建镜像（已核实：当前 requirements.txt 无 pypinyin）。多音字（如「贾」jiǎ/gǔ）索引存全部读音，召回取最小距离。

## 四、LLM 主判协议（P1 核心）

### 4.1 输入 schema

```json
{
  "question": "用户原问题",
  "conversation_context": ["上一轮问题", "上一轮答案摘要"],
  "bookshelf_digest": {
    "datasets": ["数据集名1", "数据集名2"],
    "node_aliases": ["靳锋", "商用事业部", "..."],
    "metric_synonyms": {"业绩": ["开单金额", "回款"]}
  },
  "anchor_evidence": [
    {"fragment": "靳峰", "candidates": [{"text": "靳锋", "pinyin_dist": 0, "char_dist": 1}]}
  ]
}
```

**权限裁剪（安全红线）**：`bookshelf_digest` 和拼音索引召回都必须先按当前用户的 `allowed_dataset_ids` 过滤（沿用 `typo_fastpath.py:137-141` 的既有红线）——**无权限数据集的组织名/指标名不得进入 prompt**，否则 LLM 的 reason 会把无权限实体名泄漏到前端细条/卡片上。

### 4.2 输出 schema

```json
{
  "action": "pass | rewrite | soft_hint | clarify",
  "canonical_question": "规范化后的问题（rewrite 时为改写结果）",
  "candidates": ["歧义候选1", "歧义候选2"],
  "confidence": 0.0,
  "reason": "给人看的一句话解释"
}
```

### 4.3 决策规则（四态）

| action | 条件 | 出口 |
|---|---|---|
| pass | 问题清晰、无失误证据（conf < 0.7） | 原问题直接进流水线，**零打扰** |
| soft_hint | 有失误证据但置信中等（**0.7 ≤ conf < 0.85**） | 原问题照常执行 + 顶部**非阻断**细条「你是不是想问『XX』？」可点击重查 |
| rewrite | 有明确失误证据且高置信（conf ≥ 0.85） | **先过书架校验**（见 4.5）→ 按改写问题进流水线 + 顶部细条「已按『XX』理解，点此处按原问题重查」 |
| clarify | 真歧义（两个候选都讲得通，如「最好最坏」） | 弹卡（复用 early_clarify 通道），候选由 LLM 生成自然措辞 |

**soft_hint 态的存在理由**：靳峰类 2 字同音错恰恰最可能落在 0.7~0.85 区间——没有这一态它们会静默 pass、继续 0 行漏网，与 P0 目标直接冲突。

### 4.4 模型选型与红线（照搬守门员 B1 模式）

- 独立 `UnderstandingLLMClient`：**照搬 `shadow_gatekeeper.py:296-302` 的独立 OpenAI 实例模式**（timeout 配置驱动、默认 4s、`max_retries=0`）
- **禁止复用** `llm_client._chat`（180s 硬编码超时 + 多候选重试），**禁止**共享 `_preferred_model_id` 模块级单例（审计 A-03 已知坑）
- 挂载点：与 typo_fastpath 同位（`controllers/smart_chat.py` 同步/SSE 两处），在 0.5 层之后、Agent1 之前
- **挂载顺序与影子对照**：typo_fastpath 短路在前保持不变；影子期内**无论快检是否短路，LLM 主判都记录判定日志**（短路场景异步补记），保证影子数据覆盖全量问题、可与规则层逐条对照
- 书架摘要做**缓存**：书架不变则 digest 不变，prompt 前缀稳定可命中模型侧缓存

### 4.5 rewrite 的书架否决权

rewrite 的 `canonical_question` 进流水线前**必须过书架校验**：改写引入的实体不在（按权限裁剪后的）书架内 → 降级为 soft_hint，不直接放行。此校验层来自澄清 v4 的书架接地/代码校验层，**不随规则层退役**，随 rewrite 路径迁移保留。

## 五、0 行诊断器（P0.5，LLM 增强）

### 5.1 触发

流水线执行结果 0 行时触发（现有"0 行照样生成垃圾报告"路径的替代）。

### 5.2 决策树

```
0 行
 ├─ 分支 A：对象不存在（问题中的节点/指标在书架里找不到，拼音索引也找不到近邻）
 │    → 「未找到『XX』相关数据」+ 拼音索引召回最近 1~3 个节点给「你可能想问」候选
 ├─ 分支 B：路由错数据集（对象存在于书架但不属于当前数据集）
 │    → 「『XX』在数据集『YY』中」+ 一键切换重查候选
 └─ 分支 C：真没数据（对象存在、数据集正确、口径内确实无数据）
      → 如实回答「XX 在当前口径下无数据」，不编痛点、不编建议
```

### 5.3 判定方式

- A/B 的判定用拼音索引 + 书架归属关系，纯代码，不调 LLM（快）
- 拿不准时（A/C 边界）才升级 LLM 判一次
- 三分支输出统一走 early_clarify 卡片样式，候选点击 = 重走 ask
- **测试夹具**：三分支各配 mock 夹具（固定 SQL 结果集），否则数据变动后 0 行场景不再复现、无法自动回归

## 六、收编与退役计划

| 现有组件 | 位置 | 归宿 |
|---|---|---|
| typo_fastpath（错字快检） | `backend/disambiguation/typo_fastpath.py` | P0 后：滑窗/边界规则被拼音索引吸收；P1 影子期并行运行做对照；LLM 主判达标后退役 |
| direction_ambiguity（方向口误） | `backend/disambiguation/direction_ambiguity.py` | P1 后：clarify 类判断全部上交 LLM；正则保留为影子对照 |
| classify_confirmation_draft（确认框消化） | `shadow_gatekeeper.py` | **保留且唯一化**。它处理"确认卡弹出后的自由文本"；输入理解层 clarify 弹卡后的自由文本也统一走它，**不新增第二个消化器** |
| build_correction（事后守门员） | `shadow_gatekeeper.py` | P1 后退役。**退役前置：P0.5 0 行诊断器已上线**——否则 0 行垃圾报告场景失去最后一道兜底，直接回潮 |
| 书架接地/代码校验层（书架否决权） | 澄清 v4 各校验点 | **不在退役范围**。随 rewrite 路径迁移保留（见 4.5），rewrite 高置信直进恰恰需要它否决非法实体 |

**fail-open 兜底语义钉死**：规则层全部退役后，fail-open 的"老流程"= **问数流水线本体**（LLM 挂了错字问题零拦截直进流水线，行为与"输入理解层不存在"完全一致）。退役顺序保证任何时刻 fail-open 语义都不是空的。

退役铁律：**并行影子 ≥1 周、指标达标、用户确认**三者齐了才删旧代码，删除前 git 提交留档。

## 七、横切铁律

1. **fail-open**：LLM 挂/超时/输出解析失败/置信度不足 → 一律按原问题进问数流水线本体，任何异常静默放行，绝不拦路。
2. **置信度分级**：高置信 rewrite 只出细条不打断；中置信 soft_hint 非阻断；真歧义才弹卡；低置信一律 pass。
3. **影子模式先行**：LLM 主判先只记日志不拦截，与现有规则层并行对照（含快检短路场景，见 4.4）。
4. **一键开关**：`config/gatekeeper_settings.json` 加 `input_understanding_enabled`，关闭即回到现有行为，秒级回滚。
5. **影子日志**：每次主判记录 `{question, evidence, llm_output, final_action, latency_ms, 与规则层判定是否一致}`，供离线校准（复用 B3 影子日志挂载点 `backend/disambiguation/`）。

## 十、已知风险与对策

| 风险 | 对策 |
