## 一、现状分析

### 1.1 整体架构

智能问数系统当前为**单数据集（syyb 商用事业部）深度定制**，后端四 Agent 管道 + 前端报告渲染均含大量硬编码业务逻辑，换数据集时需要重写大量代码。

```
用户提问 → Agent1路由 → Agent2生成SQL → Agent3审核SQL → Agent4业务分析 → 前端渲染报告
```

| Agent | 职责 | 定制化程度 |
|-------|------|-----------|
| Agent1 | 路由决策 + 歧义确认 | 通用（LLM判断） |
| Agent2 | SQL生成 | 数据集专属（prompt填充） |
| Agent3 | SQL审核 | 通用（硬编码为主） |
| Agent4 | 业务分析 + JSON输出 | **完全硬编码（syyb专用）** |
| 前端渲染 | buildReportModel | **完全硬编码（syyb专用）** |

### 1.3 Agent4 数据集专属提示词（syyb）

`fill_syyb_dataset.py` 存储的 `AGENT4_PROMPT`（第 296-341 行）是纯文本 prose 格式，描述的是**报告应该怎么写**（条线分离规则、图表规范），而非**JSON 结构**：

```python
AGENT4_PROMPT = """
你是 Agent4（业务解读官），面向商用事业部管理层输出结论。

铁律：输出内容必须严格按条线分层，绝不允许跨条线混排。

一、条线定义（硬性边界）
- 区域条线 = 代表处层级（安徽/河南/湖北/江苏/山东/上海/浙江代表处）
  → 图表仅展示代表处名称，绝不出现业务员姓名
- 行业条线 = 业务代表层级（个人业绩）
  → 图表仅展示业务员姓名，绝不出现代表处名称
...
"""
```

这段 prompt 描述的是**写作规则**，而 JSON 格式（`dimensions`、`insight`、`suggestions`）是通过注入点 A/B 强加给 LLM 的。**两个来源的格式定义不一致**，是 Agent4 经常输出格式错误或幻觉的根本原因。

### 1.4 前端 `buildReportModel` 现状：完全硬编码

`SmartAsk.vue` 第 490-985 行的 `buildReportModel` 函数是 syyb 的专用报告构建器，包含以下硬编码部分：

#### 硬编码常量（第 490-497 行）

```javascript
const TRACK_COL = '条线'
const LEVEL_COL = '层级'
const NAME_COL = '节点名称'
const PARENT_COL = '上级名称'
const RATE_COL = '达成率'
const TASK_COL = '总任务金额'
const ACTUAL_COL = '年度开单金额'
const REMAIN_COL = '剩余任务金额'
```

这些列名是 syyb 数据集执行 SQL 后返回的列名，**换数据集后如果列名不同，报告直接崩溃**。

#### 硬编码层级判断函数（第 530-535 行）

```javascript
const isRegionOfficeLevel = (value) => normalizeText(value).includes('代表处')
const isDepartmentLevel = (value) => normalizeText(value).includes('业务部')
const isPersonalLevel = (value) => {
  const text = normalizeText(value)
  return text.includes('业务代表') || text.includes('业务员') || text === '业务'
}
```

**这是字符串匹配，不是结构化数据**。如果另一个数据集用"部门/员工"或"校区/班级"作为层级名称，这些函数会全部失效。

#### 硬编码的分组逻辑（第 708-714 行）

```javascript
const companyRows = uniqueRowsByName(rows.filter((row) =>
  row?.[TRACK_COL] === '区域条线' && normalizeText(row?.[LEVEL_COL]).includes('分公司')))
const regionRows = uniqueRowsByName(rows.filter((row) =>
  row?.[TRACK_COL] === '区域条线' && isRegionOfficeLevel(row?.[LEVEL_COL])))
const trackIndustryRows = uniqueRowsByName(rows.filter((row) =>
  row?.[TRACK_COL] === '行业条线' && isPersonalLevel(row?.[LEVEL_COL])))
```

直接写死了 `区域条线`、`行业条线`、`代表处`、`业务代表` 这些值，**任何其他数据集都无法复用**。

#### 硬编码的报告节数与标题

```javascript
// sections 固定 5 节：一、核心看板 → 二、区域条线 → 三、行业条线 → 四、风险预警 → 五、策略建议
sections: [
  { key: 'core',    title: '一、核心业绩看板', ... },
  { key: 'region',  title: orgSectionTitle, /* 二、分公司业绩概览 / 二、区域条线分析 */ ... },
  { key: 'industry',title: '三、行业条线分析', ... },
  { key: 'risk',   title: '四、风险预警', ... },
  { key: 'strategy',title: '五、策略建议', ... },

```

报告结构是写死的，**不管数据有几层，都硬套这 5 节**。如果数据集只有 2 层（公司→员工），第"三、行业条线分析"节就会是空的；如果有 4 层（事业部→分公司→代表处→业务员），中间层完全丢失。

#### 硬编码的多图表配置（第 1010-1066 行）

`multiCharts` computed 中：

```javascript

const regionRows = rows.filter(r => r['条线'] === '区域条线' && r['层级'] === '代表处')
const industryRows = rows.filter(r => r['条线'] === '行业条线' && r['层级'] === '业务代表')
```

### 1.5 syyb 数据集的真实数据结构

理解 syyb 的 SQL 输出结构，是设计改造方案的基础。当前 `fill_syyb_dataset.py` 中的 SQL（第 100-120 行）输出的数据结构：

| 列名 | 示例值 | 说明 |
|------|--------|------|
| `条线` | 区域条线 / 行业条线 | 分类维度（两选一） |
| `层级` | 代表处 / 业务代表 / 业务部 / 分公司 | 层级名称（字符串） |
| `节点名称` | 安徽代表处 / 张三 | 实际单元名称 |
| `上级名称` | 商用事业部 / 东部分公司 | 父节点名称（树结构的关键） |
| `总任务金额` | 1234567.00 | 数值 |
| `年度开单金额` | 987654.00 | 数值 |
| `达成率` | 80.00 | 百分比数值 |
| `剩余任务金额` | 246813.00 | 数值 |

**关键发现**：`上级名称` 列的存在意味着数据天然就是一棵扁平化的树。系统可以**不依赖任何外部配置**，直接从 SQL 返回的 rows 中推断出完整的父子关系。

### 1.6 现状问题汇总

| 问题 | 位置 | 影响 |
|------|------|------|
| Agent4 输出格式两处硬编码（system prompt + user prompt） | `four_agent_ask.py:188-224, 528-552` | 换数据集必须改两处代码 |
| `dimensions` 固定为 2 个（区域/行业条线） | `four_agent_ask.py:188-224` | 不支持其他维度结构 |
| 列名硬编码（8个常量） | `SmartAsk.vue:490-497` | 列名不同则报告崩溃 |
| 层级判断用字符串 includes（5处） | `SmartAsk.vue:530-535, 708-714` | 新数据集层级名称不同则全部失效 |
| 报告节数固定 5 节 | `SmartAsk.vue:916-983` | 层数不匹配时产生空节 |
| 图表配置固定 2 张（区域+行业） | `SmartAsk.vue:1010-1066` | 无法按实际层数动态渲染 |
| `levels.values` 用模糊字符串（`includes('代表处')`） | `SmartAsk.vue` 多处 | LLM 识别偏差会导致渲染错误 |
| 配置由 Agent4 自己理解，而非声明式配置 | 整体设计 | 每次问数都依赖 LLM 猜测，稳定性差 |

## 二、改造目标

### 2.1 核心目标

让**任何一个数据集**接入后，只需在管理界面填写一份结构化配置（列名映射 + 指标定义 + 层级枚举），前端报告渲染和 Agent4 输出格式全部自动适配，无需修改任何业务代码。

### 2.2 具体指标

- 新数据集接入时间：从"重写 ~800 行代码"降至"填写 1 份配置（约 10-15 分钟）"
- 硬编码业务常量数量：从 ~50 个减少到 ~5 个（全局通用工具函数）
- Agent4 prompt 中的业务字符串：从 ~30 处减少到 0 处（全部迁移到配置）
- 前端报告节数：从固定 5 节变为**由数据实际层数动态决定**

### 2.3 非目标

- 不改变 SQL 生成逻辑（Agent2/Agent3）
- 不改变现有的 LLM 调用方式（模型选择、fallback、重试机制）
- 不改变前端 UI 组件和交互逻辑（只改变 `buildReportModel` 的数据来源）

## 三、改造方案

### 3.1 核心设计思想：三层职责分离

```
┌─────────────────────────────────────────────────────────────┐
│ 第一层：配置（静态，人工维护，LLM 不可改）                       │
│   - 列名映射（哪个列是名称、上级、层级、条线）                   │
│   - 指标定义（哪个列是任务、开单、达成率）                       │
│   - 渲染开关（开哪些节、风险阈值、信号灯规则）                   │
│   - levels.values（枚举值，从真实数据中取，不模糊匹配）            │
├─────────────────────────────────────────────────────────────┤
│ 第二层：树（动态推断，数据驱动，不需人工建树）                     │
│   - 从 rows + parentColumn 实时构建父子关系                     │
│   - 自动识别树深度（从根节点向下追踪）                          │
│   - 自动按深度映射到 levels 配置（机构层/个人层）                │
│   - 按实际层数生成对应的 levelSections                          │
├─────────────────────────────────────────────────────────────┤
│ 第三层：内容（LLM 填空，只填 KPI 数值 / 建议文本）               │
│   - Agent4 不再需要理解组织结构                                 │
│   - Agent4 只知道有哪些指标（metrics），按模板填 insight         │
│   - 不再需要"铁律"约束（因为结构由系统决定）                     │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 新增数据库表：`bs_dataset_report_config`

```sql
-- backend/migrations/YYYYMMDD_report_config.sql
CREATE TABLE bs_dataset_report_config (
    id          BIGSERIAL PRIMARY KEY,
    dataset_id  BIGINT NOT NULL REFERENCES bs_datasets(id),
    config_json JSONB NOT NULL DEFAULT '{}',
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    updated_at  TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(dataset_id)
);
```

`config_json` 结构（由管理员在数据集管理界面填写）：

```json
{
  "nameColumn": "节点名称",
  "parentColumn": "上级名称",
  "trackColumn": "条线",
  "levelColumn": "层级",
  "metrics": [
    { "key": "task",   "label": "总任务金额",   "column": "总任务金额",  "format": "amount"   },
    { "key": "actual", "label": "年度开单金额", "column": "年度开单金额", "format": "amount"   },
    { "key": "rate",   "label": "达成率",       "column": "达成率",       "format": "percent"  },
    { "key": "remain", "label": "剩余任务金额", "column": "剩余任务金额", "format": "amount"   }
  ],
  "levels": [
    { "name": "机构层", "values": ["代表处", "分公司", "业务部"] },
    { "name": "个人层", "values": ["业务代表", "业务员", "业务"] }
  ],
  "trackValues": { "org": "区域条线", "personal": "行业条线" },
  "riskThreshold": 80,
  "signalRules": [
    { "key": "rate", "op": ">=", "value": 100, "tone": "good",  "label": "绿灯"  },
    { "key": "rate", "op": ">=", "value": 80,  "tone": "warn",  "label": "黄灯"  },
    { "key": "rate", "op": "<",  "value": 80,  "tone": "danger","label": "红灯"  }
  ],
  "sections": ["core", "group", "risk", "strategy"],
  "reportTitle": "经营分析报告"

```

**设计原则**：配置里只有列名和枚举值，**没有模糊表达**。
- 原来：`filter: "包含代表处"`（模糊，可能匹配失败）
- 现在：`values: ["代表处", "分公司", "业务部"]`（精确枚举，LLM 零歧义）

### 3.3 组织树自动推断算法

#### 3.3.1 为什么不用显式建树

syyb 的 SQL 输出中已经有 `上级名称` 列，可以直接推断父子关系。如果用显式建树（另建一张 `bs_org_tree` 表），每个数据集都需要人工维护节点关系，工作量大且容易出错。

自动推断的优势：
- **零人工维护**：树从 SQL 返回的 rows 中实时构建
- **自适应**：不管数据集有几层（2层/3层/4层），都能正确推断
- **自动更新**：当 SQL 结果变化时，树自动跟着变

#### 3.3.2 树节点结构

```javascript
class OrgNode {
  name          // 节点名称（来自 nameColumn 列）
  parentName    // 父节点名称（来自 parentColumn 列）
  levelName     // 层级名称（如"代表处"），由 levels 配置映射
  trackName     // 条线名称（来自 trackColumn 列）
  depth         // 深度（根=0，逐层+1）
  children      // 子节点数组
  metrics       // 聚合后的指标 { task, actual, rate, remain }
  rows          // 该节点对应的原始数据行
  rate          // 达成率
  isRisk        // 是否风险节点（rate < riskThreshold）
  isTop         // 是否优秀节点（rate 排名前 N）
}
```

#### 3.3.3 树构建流程

```
输入：rows（SQL结果集）+ config（报告配置）

Step 1：节点去重
  → uniqueRowsByName(rows)  去除同名重复行

Step 2：构建父子关系 Map
  Map<name, parentName>  从所有行的 parentColumn 列提取
  根节点：parentName 为空或 null 的行

Step 3：识别树深度（递归遍历）
  从根节点出发，按 parentName 向下追踪
  每个分支取最大深度 → 树总深度 = max(depth)

Step 4：将行数据挂载到对应节点
  每行按 nameColumn 匹配到对应节点
  聚合计算：task=sum(taskCol), actual=sum(actualCol), rate=calc(task,actual)

Step 5：从 depth 1 开始，每层生成一个 levelSection
  levelSection = {
    depth: N,
    name: `第 N 层`,
    levelName: "机构层" 或 "个人层"（由 levels 配置映射）,
    nodes: 该层所有节点（按达成率排序）,
    groupBlocks: 按 parentName 分组后的节点集合,
    hasChildren: 是否有子节点,
    riskNodes: 风险节点列表,
    topNodes: 优秀节点列表,
  }

Step 6：确定报告节数
  levelSections[0] → 渲染"核心业绩看板"
  levelSections[1..N-1] → 渲染"N-1 个分组分析"节
  最后一个 levelSection → 渲染"风险预警"节
  全局 → 渲染"策略建议"节
```

#### 3.3.4 levels 配置的映射逻辑

```javascript
function inferLevelName(row, config) {
  // 从行数据的 levelColumn 值匹配 levels.values
  const levelValue = row[config.levelColumn]
  const matched = config.levels.find(l => l.values.includes(levelValue))
  return matched?.name || `第 ${depth} 层`
}
```

这样，即使不同数据集的层级名字完全不同（"部门/小组" 或 "校区/班级"），只要在 `levels.values` 里枚举正确的前端展示名，系统自动映射，无需硬编码。

### 3.4 后端改造

#### 3.4.1 新建 `backend/dataset_report_config.py`

```python

    @staticmethod

        row = db.fetchone(
            "SELECT config_json FROM bs_dataset_report_config WHERE dataset_id = %s",
```

### 3.6 数据集报告配置管理界面

#### 3.6.1 入口

在现有"数据集管理"页面（`Databases.vue` 或 `Bookshelves.vue`）的表格中，为每行数据集添加操作按钮：**「配置报告」** → 跳转到 `DatasetReportConfig.vue`。

#### 3.6.2 Tab 1：「自动导入」（推荐方式）

```
Step 1：用户选择数据集 → 发起一次问数（或使用最近一次结果）
Step 2：系统展示该数据集的 columns 列表 + 前 3 行样本数据
Step 3：用户在界面上点选（从真实 columns 中选择，无手填）：
  - [下拉] 名称列：选择 "节点名称"（候选来自 columns）
  - [下拉] 上级列：选择 "上级名称"
  - [下拉] 条线列（可选）：选择 "条线"
  - [下拉] 层级列（可选）：选择 "层级"
  - [多选] 指标列：勾选 "总任务金额, 年度开单金额, 达成率"
  - [多选] levels.values：根据 rows 唯一值枚举 → 用户勾选归入"机构层"/"个人层"
Step 4：系统自动生成 config_json 预览（树结构预览 + 模拟渲染预览）
Step 5：用户确认 → 保存
```

**核心 UX 保证**：用户**永远不需要手打列名**，都是从真实数据里选的。LLM 识别错误的概率降到接近零。

#### 3.6.3 Tab 2：「手动编辑」（高级模式）

- 直接编辑 JSON（带语法高亮和字段提示）
- 手动维护 metrics / levels / signalRules
- 用于对渲染细节有特殊要求的场景

#### 3.6.4 配置预览

保存前，系统自动用最近一次问数结果做一次"配置预览"——右侧实时渲染报告。如果分组是空的、图表出不来，说明配置填错了，立刻提示用户修正。
