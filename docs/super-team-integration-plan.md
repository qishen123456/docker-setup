# 超级专家团队整合方案

> 基于 WorkBuddy 平台 6 个优秀软件开发专家/团队的深度分析，将各自核心长处系统性整合到 fullstack-dev-team，构建一支技术全面、协作高效、能应对复杂软件开发挑战的精英团队。

---

## 一、各专家核心优势深度分析

### 1. gstack · 软件工坊（6人团队）

**核心优势：**

| 角色 | 独特能力 | 我们当前缺失 |
|---|---|---|
| **gstack-security-officer** | **14 阶段安全审计框架**：架构心智模型 -> 攻击面普查 -> 密钥考古 -> 依赖供应链 -> CI/CD 安全 -> 基础设施影子面 -> Webhook 审计 -> LLM/AI 安全 -> OWASP A01-A10 逐项 -> STRIDE 威胁建模 -> 数据分级 -> 误报过滤+主动验证 -> 趋势追踪。双模式（Daily 零噪音 / Comprehensive 深扫），置信度门禁（Daily≥8 / Comprehensive≥2），**每个发现必须主动复现确认** | 我们的 reviewer 只有简单 OWASP 清单，无 STRIDE、无供应链审计、无主动验证、无置信度分级 |
| **gstack-investigator** | **四阶段根因调查法**（Investigate->Analyze->Hypothesize->Implement）+ **3-strike 规则**（假设失败 3 次就重新调查，不继续打补丁）+ **Scope Lock**（只改根因直接涉及的文件）+ **会话检查点**（跨会话续接工作状态）+ **知识管理**（非显然 bug / 设计决策 / 重复模式 / 踩坑记录） | 我们没有根因调查方法论，BugFix 路径只有"QA复现->工程师修"，没有假设驱动调查；没有知识沉淀机制 |
| **gstack-product-reviewer** | **YC 风格 6 个强迫性问题**（需求现实/现状替代/绝望的具体性/最窄楔子/观察验证/...）+ **四维评审**（CEO 范围审计 / Design 0-10 维度打分 / Eng 架构锁定 / DX 开发者体验）+ **Autoplan 流水线**（CEO->Design->Eng->DX 串联自动决策） | 我们的 PM 只有需求拆解和优先级，没有产品诊断的强迫性提问框架，没有设计维度打分 |

**值得萃取的能力：**
- 14 阶段安全审计框架（替代我们的简单 OWASP 清单）
- 四阶段根因调查法 + 3-strike 规则 + Scope Lock（强化 BugFix 路径）
- 会话检查点机制（跨会话续接）
- YC 6 问产品诊断（强化 PM 的需求澄清能力）

### 2. mvp-dev-expert-team · MVP 开发专家团（8人团队）

**核心优势：**

- **五层工程化体系**：标准化需求工程 -> 项目级上下文系统 -> 角色级 Agent 编排 -> 企业级规范约束 -> 实时可观测性。这套体系把"为什么需要流程"用数据说清楚了：**同模型+同需求，无 Harness 60% 完成率，有 Harness 98%**。
- **DDAD（文档驱动 AI 开发）**：PRD->架构->UIUX->Spec->代码->文档持续演化。区分 Vibe Coding（探索期）和 Spec-Driven（生产期）。
- **五源对齐法（UI 像素级还原）**：设计变量 + 设计元数据 + 设计截图 + AI 代码 + 渲染截图，五源交叉对比。
- **P0 绝对规则**：禁 emoji 作功能图标、禁紫粉渐变模板味、禁 AI 模板文案。这是实战中踩过的坑固化成的硬规则。
- **Harness Engineering 洞察**：流程即质量，不是控制狂，是数据驱动的。

**与我们 fullstack-dev-team 的差异：**
- 我们有 SOP 但没有"五层体系"的抽象框架
- 我们有前端规范但没有"五源对齐"的像素级校验方法
- 我们没有 P0 绝对规则（防止 AI 生成代码的典型坏味道）
- 我们的 DDAD 概念较弱（文档驱动 vs 代码驱动）

**值得萃取的能力：**
- 五源对齐法（前端实现质量门禁）
- P0 绝对规则体系（防 AI 模板味）
- Harness Engineering 数据驱动质量观

### 3. gpt-researcher-team · 深度研究团队（7人团队）

**核心优势：**

- **审稿-修订循环**（核心机制）：每章草稿 -> 审稿人 6 维标准审查（来源充分性/事实准确性/观点均衡性/内容深度/结构清晰度/格式规范性）-> PASS 或具体 REVISE 意见 -> 修订员逐条回应修改 -> 再审 -> 最多 3 轮，第 3 轮强制通过。这是一个**独立于 QA 的质量循环**。
- **研究参数卡**：主理人通过结构化参数卡在阶段间传递上下文（课题/模式/时效窗口/输出格式/引用格式），比我们的"上下文三级传递"更结构化。
- **失败隔离**：某位成员失败/超时时明确标注"XX 视角未能完成"，用其他视角做最大化补救，不放弃整份报告。

**值得萃取的能力：**
- **审稿-修订循环**--这是最值得引入的机制。我们的代码审查只有 1 轮 REJECT 回流，没有"审稿->修订->再审"的结构化循环
- 研究参数卡的上下文传递方式
- 失败隔离原则

### 4. huashu-data-pro · 花叔数据分析专家团（4人团队）

**核心优势：**

- **三视角并行分析**：趋势 / 结构 / 异常三个分析师同时看同一份数据，互不干扰，最后交叉印证。这比"一个人从头分析到尾"能发现更多盲区。
- **三格式交付**：HTML（看细节）/ XLSX（带数据透视表，给财务）/ PPTX（直接拉去开会），按受众自动适配。
- **数据诚实原则**：不编造任何数字，无法判断的标"待确认"。

**值得萃取的能力：**
- 多视角并行分析模式（可借鉴到代码审查：安全视角 / 可维护性视角 / 性能视角并行）
- 按受众适配的多格式交付

---

### 5. senior-developer · 吴八哥（单人专家）

**核心优势：**

- **Premium Craftsmanship 理念**：每个像素都应有意图，性能与美观必须共存，创新优于惯例（当能提升 UX 时）。
- **持久记忆**：记住之前的实现模式、什么有效、常见陷阱。
- **质量标准量化**：60fps 动画、1.5s 加载、跨设备响应式验证。

**值得萃取的能力：**
- Premium 级前端质量标准（60fps / 1.5s / 跨设备）
- 持久记忆模式（与 gstack-investigator 的知识管理互补）

---

### 6. prompt-engineering-expert · 提示词工程专家

**核心优势：**

- **提示词反模式诊断**：模糊、矛盾、过度约束、幻觉风险、上下文泄漏、越狱漏洞--6 类反模式的识别与修复。
- **评估与测试体系**：为提示词建立成功标准、测试用例、边界条件与回归测试，形成可量化的评估框架。
- **提示链设计**：Prompt Chaining 应对复杂任务。

**值得萃取的能力：**
- 提示词质量保证方法论（可应用于团队自身角色 prompt 的持续优化）
- 反模式诊断清单（审查 AI 生成代码时的"AI 味"检测）

## 三、超级团队协作模型

### 3.1 整合策略：增强而非扩编

**不新增角色**，而是将各专家的优势能力萃取为**方法论模块**，注入到 fullstack-dev-team 现有 9 角色中。理由：
- 角色越多，消息中转成本越高（团队自身设计原则）
- 这些能力是"方法论的提升"而非"独立的能力域"
- 用户不会直接问"帮我做 STRIDE 威胁建模"（那是审查员的事），但会期望审查员懂 STRIDE

### 3.2 能力注入映射

| 注入目标 | 注入内容 | 来源 | 注入方式 |
|---|---|---|---|
| **reviewer（代码审查工程师）** | 14 阶段安全审计框架精简版（OWASP+STRIDE+供应链+密钥考古+主动验证+置信度分级） | gstack-security-officer | 扩充审查框架章节 |
| **reviewer** | 多视角并行审查模式（安全视角/可维护性视角/性能视角） | huashu-data-pro | 审查流程增加三视角 |
| **reviewer** | AI 模板味检测规则（禁 emoji 图标/禁紫粉渐变/禁 Lorem Ipsum/禁硬编码色值） | mvp-dev-expert-team P0规则 | 审查清单增加 AI 味检测项 |
| **qa（测试工程师）** | 审稿-修订循环（审->修订->再审，最多 3 轮，第 3 轮强制通过） | gpt-researcher-team | 测试门禁从 2 轮扩为结构化循环 |
| **qa** | 前端像素级校验（五源对齐法） | mvp-dev-expert-team | 前端测试增加五源对齐 |
| **qa** | Premium 质量标准（60fps/1.5s/跨设备） | senior-developer | 前端测试增加性能基准 |
| **pm（产品经理）** | YC 6 问产品诊断（需求现实/现状替代/绝望的具体性/最窄楔子/观察验证/...） | gstack-product-reviewer | 需求澄清框架增加诊断模式 |
| **architect（系统架构师）** | 五层工程化体系 + DDAD 文档驱动开发 | mvp-dev-expert-team | 架构设计增加五层对齐检查 |
| **team-lead（主理人）** | 会话检查点机制（跨会话续接） | gstack-investigator | SOP 增加检查点保存/恢复 |
| **team-lead（主理人）** | 失败隔离原则（成员失败时标注并用其他成员补救） | huashu-data-pro | 协作规则增加失败隔离 |
| **team-lead（主理人）** | 知识沉淀机制（非显然bug/设计决策/重复模式/踩坑记录） | gstack-investigator | 交付后增加知识沉淀步骤 |
| **team-lead（主理人）** | Harness Engineering 数据驱动质量观 | mvp-dev-expert-team | 质量门禁增加完成率追踪 |

### 3.3 增强后的 SOP

```
Phase 0  架构师 -> 项目公约摘要 + 五层工程化对齐检查（新增）
Phase 1  PM -> PRD（需求澄清增加 YC 6 问诊断模式）
Phase 2  设计师 ∥ 架构师 -> 设计规范 ∥ 架构+契约(v1)+任务列表
Phase 3  前端 ∥ 后端 -> 实现
Phase 4  审查员 -> 三视角并行审查（安全/可维护性/性能）+ AI 味检测
         ├─ 审稿-修订循环（审->修订->再审，最多 3 轮）
         └─ 置信度分级（≥8 放行 / 2-7 附条件 / <2 不报告）
Phase 5  QA -> 测试（前端增加五源对齐+性能基准）
Phase 6  DevOps -> 部署+回滚
交付后   主理人 -> 知识沉淀（踩坑记录/设计决策/重复模式入库）
```

### 3.4 知识共享与最佳实践沉淀机制

```
.ai-team/
├── team-config.yaml          # 团队配置（已有）
├── agents/                   # 角色 prompt（已有，将注入新能力）
├── knowledge-base/           # [新增] 知识沉淀库
│   ├── pitfalls.md           # 踩坑记录（非显然 bug + 根因 + 解法）
│   ├── decisions.md          # 设计决策记录（决策 + 理由 + 被否方案）
│   ├── patterns.md           # 重复模式（项目特定的最佳实践）
│   └── ai-smells.md          # AI 生成代码的典型坏味道清单
├── checklists/               # [新增] 审查/测试清单
│   ├── security-audit.md     # 14 阶段安全审计清单（精简版）
│   ├── ai-template-smells.md # AI 模板味检测清单
│   └── frontend-pixel-check.md # 五源对齐前端校验清单
└── checkpoints/              # [新增] 会话检查点（gitignore）
    └── *.md                  # 跨会话工作状态续接
```

**知识沉淀触发条件：**
- 修复了一个非显然 bug -> 记入 pitfalls.md
- 做了一个有取舍的技术决策 -> 记入 decisions.md
- 发现了一个反复出现的模式 -> 记入 patterns.md
- 检测到 AI 生成的典型坏味道 -> 记入 ai-smells.md

**知识消费时机：**
- Phase 0 项目公约勘察时，读 knowledge-base/ 补充到公约摘要
- Phase 4 审查时，读 checklists/ 作为审查清单
- 新会话开始时，读最新的 checkpoint 恢复工作状态
