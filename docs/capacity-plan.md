# SmartAsk 企业级并发容量规划

> 版本：v1.0 · 2026-08-29
> 状态：规划（未实施）
> 目标：支撑 **20 → 100 并发用户**的企业级问数能力
> 关联：`docs/audit/2026-08-06_final-audit-report.md`（A-03 LLM 状态共享 / L-01 部署不完整）、AGENTS.md 架构事实

---

## 一、背景与容量账

SmartAsk 当前为单实例开发态部署。按企业级目标，需支撑 20（近期）→ 100（中期）并发用户同时问数。

### 1.1 单请求 LLM 开销（实测）

每个问数请求 = **2~4 次 LLM 调用**（Agent1 路由 + Agent3 复核 + Agent4 分析；Agent2 走规则 SQL 不调 LLM），单次响应 20~64s（默认 MiniMax-M3 为 reasoning 模型，实测 ~64s；M2.5 ~18s）。

### 1.2 峰值 LLM 并发需求

| 并发用户 | 峰值 LLM 并发请求 | 推算 |
|---------|------------------|------|
| 20 | ~60 次 | 20 × 3 次/问 |
| 100 | ~300 次 | 100 × 3 次/问 |

**核心结论**：瓶颈是 **LLM 配额 + 单进程内存状态**，不是 Flask 线程数。100 用户时商业 API 的 RPM/并发配额会被打爆，且单进程（确认会话 / SSE / LLM 状态全在内存）无法水平扩展副本。

## 二、现状瓶颈盘点（全部有代码实锤）

| 层 | 现状 | 证据 | 影响 |
|---|---|---|---|
| HTTP 服务 | Flask 开发服务器（Werkzeug），单进程多线程 | `Dockerfile:50` `python app.py`；`app.py:344` `app.run(threaded=True)` | 非生产服务器，无线程上限/防护 |
| SSE 问数 | 每问数请求占 2 线程（请求线程 + worker 线程） | `smart_chat.py:768/881/1093/1154` | 100 并发 = 200 线程 |
| 确认会话 | `_pending_confirmations` 内存 dict，模块级单例，30min TTL | `four_agent_ask.py:56`；`ask_flow/controller.py:9` | **多 worker 即丢状态，无法加进程** |
| LLM 状态 | 共享 `_preferred_model_id`，并发互相覆盖模型选择 | `llm_client.py:37/119`（审计 A-03） | 并发污染 |
| LLM 候选链 | 失败按白名单轮询全部激活模型 | `llm_client.py:59-91,103-176` | 最坏 N 模型 ×180s 超时 |
| 数据库 | `_connect()` 裸连接，无连接池，44 处/3 套独立定义 | AGENTS.md 架构事实 | 连接风暴 |
| 飞书同步 | 同进程守护线程跑调度 | `app.py:338-339` | 抢 GIL 拖慢问数 |

**瓶颈排序**（谁先撑不住）：① LLM 配额 ② DB 连接 ③ Werkzeug 开发服务器 ④ GIL+单进程 ⑤ 单进程内存状态（架构天花板）。

## 三、模型维护策略（企业级：分层绑定，非备胎轮询）

**"维护几个大模型"的正确答案 = 按任务绑定 1 主 1 备，而非全部激活当备胎轮询。**

| 角色 | 承担任务 | 模型选择 | 网关冗余 | 说明 |
|------|---------|---------|---------|------|
| **快模型** | Agent1/2/3（路由+SQL+复核） | MiniMax-M2.5（实测 18s，非 reasoning） | edgefn 主 + minimaxi 备 | 响应优先 |
| **强模型** | Agent4（经营分析） | MiniMax-M3 官方 或 GLM-5.1 | minimaxi 主 + edgefn 备 | 质量优先 |
| **守门员** | P1 每问必过（3~5s 超时，max_tokens≤256） | 超快小模型 | 独立配置，**不进候选链** | 沿用守门员 B1 红线 |
| **本地兜底** | 100 用户级商业配额不足时 | 本地部署（Qwen/Llama 等） | 独立容器 | 不被商业配额卡死 |

**关键动作**：把当前"6 个激活全当备胎"改为"**3 类任务各绑定 1 主 1 备**"，失败只在同类内切换（1~2 个备选），杜绝 6 模型 ×180s 轮询风险。当前 id=4 与 id=10 为同模型同网关重复，应精简。

## 四、架构升级路径

### 阶段 A：撑 20 用户（近期 1~2 周，低风险）

保持**单进程**（确认会话仍在内存，不能加 worker），只做横向减压：

| # | 动作 | 解决什么 | 投入 | 类型 |
|---|------|---------|------|------|
| A1 | 模型任务分层（3 类各绑定 1 主 1 备，砍冗余备胎） | LLM 配额 + 失败轮询风险 | 半天 | 配置 |
| A2 | `_preferred_model_id` 改请求参数透传 | 并发模型选择互相覆盖（A-03） | 1 天 | 代码 |
| A3 | DB 连接池（44 处 `_connect()` 收敛成池化模块） | 连接风暴（20×10 查询=200 建连） | 2 天 | 代码 |
| A4 | 飞书同步拆独立容器 | 同进程抢 GIL 拖慢问数 | 半天 | 配置 |
| A5 | gunicorn 单进程多线程（`--threads 32 -w 1`，**workers=1**） | Werkzeug 开发服务器脆弱 | 半天 | 配置 |

**20 用户判定**：LLM 并发 ~60 用任务分层+双网关扛住；单进程 40 线程 gunicorn 能扛；最终瓶颈在商业 API 的 RPM 上限（需向服务商确认配额）。

### 阶段 B：撑 100 用户（中期 2~4 周，架构级）

100 用户 = LLM 并发 ~300 + 单进程 200 线程 + GIL。**单进程必死，必须外置状态 + 多副本 + 队列化**：

| # | 动作 | 为什么必须 | 解锁什么 | 投入 |
|---|------|-----------|---------|------|
| B1 | **确认会话外置**（`_pending_confirmations` → Redis/PG 表） | 单进程内存 dict，多 worker 即丢 | **多进程/多副本的前置条件** | 3~4 天 |
| B2 | SSE 队列外置（内存 queue → Redis pub/sub） | 同上 | 多副本 SSE | 随 B1 |
| B3 | gunicorn 多 worker（4~8）或 多容器 + nginx 轮询 | 单进程扛不住 100 并发 | 水平扩展 | 1 天 |
| B4 | **问数队列化**（Celery/RQ：请求进队列立即返回 task id，worker 池消费，前端 SSE 订阅结果） | 100 并发 = 300 LLM 请求同时抢配额 | **削峰填谷** | 3~5 天 |
| B5 | 本地模型兜底容器 | 商业 API 300 并发配额不足/成本高 | 不被配额卡死 | 2 天 |

**100 用户的分水岭是队列化（B4）**：100 个并发提问不该是 100 个线程抢 300 个 LLM 配额，而是**进队列排队、worker 池按配额能力消费**——这是企业级与玩具部署的根本区别。

## 五、分阶段实施清单

**近期（20 用户目标，先不动多进程）**：
1. A1 模型任务分层（3 类绑定 1 主 1 备，砍冗余）——半天
2. A2 `_preferred_model_id` 参数透传（修并发污染）——1 天
3. A3 DB 连接池——2 天
4. A4 飞书拆容器——半天
5. A5 gunicorn 单进程多线程——半天

**中期（100 用户目标）**：
6. B1 确认会话外置 Redis（解锁多副本的钥匙）——3~4 天
7. B3 gunicorn 多 worker / 多容器 + nginx——1 天
8. B4 问数队列化（Celery）——3~5 天
9. B5 本地模型兜底容器——2 天

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| 商业 LLM 的 RPM/并发配额不透明 | 向服务商确认 20/100 用户对应配额；阶段 B 用本地模型兜底 |
| 会话外置改动面大 | B1 先做 `_pending_confirmations` 单点外置，验证后再推 SSE；用 feature_flag 灰度 |
| 队列化改变交互模型（同步→异步） | 前端 SSE 已支持流式订阅，改为订阅 task 结果即可；先做 20% 流量灰度 |
| 多 AI 助手压测占用配额 | 压测约定不同时跑 / 用独立快模型，不占默认强模型配额 |
| 多副本后 SSE sticky session | nginx `ip_hash` 或改结果轮询；队列化后天然规避 |

---

## 七、一句话结论

- **20 用户**：靠"任务分层 + 连接池 + 单进程优化（A1~A5）"即可，瓶颈在商业 API 配额。
- **100 用户**：必须走"**会话外置（B1）→ 多副本（B3）→ 队列化（B4）**"架构线，LLM 加本地兜底（B5）——否则商业配额与单进程会在 100 并发同时崩。
- **模型不是越多越好**：3 类任务各绑定 1 主 1 备（共 4~6 个），胜过 6 个全激活当备胎。
