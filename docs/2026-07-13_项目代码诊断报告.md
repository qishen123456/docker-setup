# SmartAsk 项目代码诊断报告

## 1. 审阅范围

本次审阅覆盖 Docker 启动与部署脚本、Flask 后端、基础/进阶问数链路、组织解析与节点索引、数据集与转换、飞书同步、认证与 RBAC、运行态迁移、Vue 前端、历史会话及测试基线。

代码规模约为：后端 Python 43,023 行，前端源码 39,413 行；核心单文件 `backend/four_agent_ask.py` 10,748 行，`frontend/src/views/SmartAsk.vue` 8,682 行。后端约 122 个路由，后端测试代码 2,858 行，前端没有成体系的单元或端到端测试。

本轮未修改业务代码、运行数据和配置，只新增诊断报告；问数报告现已累计覆盖 50 问。

## 2. 严重问题

### P0：AI Markdown 存在存储型 XSS 风险

`frontend/src/views/SmartAsk.vue:352` 等多处通过 `v-html` 展示模型内容，`frontend/src/views/SmartAsk.vue:3745` 和 `:3746` 直接调用 `marked.parse()`，项目未见 HTML sanitizer。认证令牌又由 `frontend/src/api/index.js:19` 保存在 `localStorage`。如果模型输出、历史报告或数据内容包含恶意 HTML，可能在用户浏览器执行脚本并读取令牌。

建议：在唯一渲染边界使用 DOMPurify 严格白名单净化；默认禁用 Markdown 原生 HTML；令牌迁移为 `HttpOnly + Secure + SameSite` Cookie，并配置 CSP。

### P0：密码散列强度不足且默认密码公开

`backend/controllers/auth.py:105` 和 `backend/controllers/rbac.py:71` 使用单次 SHA-256 计算 `salt:password`，无法抵抗现代离线破解；默认密码 `12345678` 在接口和 UI 中公开（如 `frontend/src/auth/AuthLogin.vue:61`）。

建议：改用 Argon2id 或 bcrypt，登录成功时渐进迁移旧散列；新账号采用一次性随机初始凭证并强制首次修改，重置接口不返回明文默认密码。

### P0：核心问数正确性没有稳定契约

累计 50 问中 21 题失败、10 题部分通过。组织范围、目标层级、指标、年份和 TopN 在 LLM、规则 SQL、数据集画像及报告生成之间会被覆盖。`backend/four_agent_ask.py:7441` 对可能为空的 `profile` 调用 `.get()`，直接造成同数据集和跨数据集电商对比崩溃。

建议：拆出不可变 Query Contract 和统一执行器；维度画像是可选能力而非隐式前置条件；所有结果在交给报告模型前执行范围、层级、指标、数量和多数据集完整性校验。具体复现见《SmartAsk 20 问诊断报告》。

## 3. 高优先级问题

### P1：飞书定时同步调度器没有实际运行

调度循环定义在 `backend/feishu_sync_service.py:881`，但后端入口只启动 `backend/app.py`。`docker compose top` 显示后端仅有 Flask 进程，没有调度器进程；界面配置的同步频率因此不会自动执行。

建议：增加独立 scheduler 容器或使用可靠任务队列，配套单实例锁、心跳、最后调度时间和失败告警；不要在 Web 多 worker 内直接启动循环。

### P1：生产容器运行 Flask 开发服务器

`backend/app.py:250` 使用 `app.run()`，当前容器进程也确认为 `/usr/local/bin/python /app/backend/app.py`。这不具备生产级 worker 管理、超时、优雅重启和并发隔离。

建议：改为 Gunicorn/Waitress，并明确 worker、thread、timeout、graceful shutdown 和反向代理超时配置。

### P1：JSON 运行态写入缺少原子性和并发控制

`backend/config_manager.py` 的通用 JSON 读写直接操作目标文件，没有临时文件加 `fsync + os.replace` 的原子提交，也没有跨进程锁。多请求或多 worker 下可能丢更新、读到半文件或损坏配置。报告历史的进程内锁也不能覆盖多 worker。

建议：重要运行态迁移到 PostgreSQL；保留文件的部分采用原子写、文件锁、版本号和 compare-and-swap。

### P1：运行态迁移不包含节点索引

`backend/runtime_migration.py:31-46` 的 `RUNTIME_CONFIG_FILES` 未包含 `dataset_node_index.json`。迁移到其他服务器后，即使数据集和权限导入成功，组织解析仍可能使用缺失或重新生成前不一致的索引。

建议：明确节点索引是派生物还是迁移物。更稳妥的方案是 bundle 记录索引 schema/version 和源数据版本，导入完成后强制按受影响数据集重建并校验，而不是携带陈旧索引。

### P1：节点索引没有被当前目录和权限边界约束

完整测试中 `test_matching_suffix_still_routes_hunan_consumer_branch` 失败：隔离测试只声明数据集 3/11，但解析器读取真实索引并引入数据集 2，最终缺少预期的 `resolved_members`。这说明索引候选可能越过当前 catalog/授权集合。

建议：解析入口必须先以可见 `dataset_ids` 裁剪索引；测试显式注入索引仓库，禁止读取宿主真实配置。

### P1：转换 SQL 的只读校验可绕过

`backend/dataset_transform_service.py:65` 只要求 SQL 以 `SELECT` 或 `WITH` 开头。PostgreSQL 的 data-modifying CTE 可以 `WITH ... DELETE/UPDATE/INSERT ...`，因此前缀检查不等于只读。

建议：以只读数据库角色执行转换预览；使用 SQL AST 限制语句类型；事务设为 `READ ONLY`，三层同时生效。

## 4. 中优先级问题

### P2：核心文件过度集中

`four_agent_ask.py` 同时承担意图识别、组织解析、数据集特例、SQL 拼装、执行、回退和报告生成；`SmartAsk.vue` 同时承担会话、流式状态、历史恢复、报告和复杂布局。局部修复容易改变其他问法，这与近期“时而有、时而没有”的表现一致。

建议：先按可测试边界提取 Query Contract、Scope Resolver、Metric Registry、SQL Planner、Result Validator 和 Comparison Aggregator；前端拆出会话控制器、当前结果与历史结果的统一 view model。避免一次性重写。

### P2：基础/进阶能力配置与产品能力不一致

当前默认基础流程且进阶关闭，但基础流程不能可靠完成跨数据集对比；进阶流程对电商根汇总也可能取错粒度。界面允许提出问题，却没有稳定执行能力。

建议：能力路由应根据请求契约和数据集能力自动选择执行器；不支持时明确确认或拒绝，不能静默降级为单边结果。

### P2：部署和初始化口径矛盾

`docker-compose.yml:44-45` 默认跳过内置数据集和首次 bundle 导入，符合“由用户迁移”的现状；但 `update.sh:569` 仍无条件执行消费者标准数据集创建脚本。更新过程可能重新引入用户已经删除的初始化内容。

建议：所有初始化和示例数据改为显式、幂等、默认关闭的命令；`update.sh` 只升级 schema 和应用，不创建业务数据。文档同步说明首次部署与迁移的唯一流程。

### P2：数据库迁移无版本账本

启动脚本会重复扫描和执行迁移文件，但没有标准 migration ledger。依赖每个 SQL 自身幂等，难以判断服务器真实 schema 版本，也不利于失败恢复。

建议：引入 Alembic/Flyway，记录版本、校验和、执行时间和状态。

### P2：OAuth 会话令牌进入 URL

`backend/controllers/auth.py:669` 将 session token 放入重定向查询参数，`frontend/src/views/AuthCallback.vue:21` 再读取。令牌可能进入浏览器历史、代理日志和 referrer。

建议：回调直接设置短生命周期 HttpOnly Cookie，或使用一次性 code 由前端后端交换；立即清理 URL 只能降低、不能消除中间链路泄漏。

### P2：错误可能被部分成功掩盖

跨数据集聚合在任一数据集有结果时可能移除顶层错误，用户看到的是不完整比较；第 16 问已真实复现单边数据。错误模型应区分 `complete/partial/failed`，默认禁止用 partial 生成比较结论。

### P2：报告文本缺少事实约束

第 4 问结果是全局城市公司，文案却称山东范围；第 20 问没有确认，文案却称“待确认”。当前报告模型能自由描述执行状态。

建议：核心结论由结构化数据模板生成一句话；模型只补充解释。数据集、范围、指标、行数、确认状态必须来自执行结果，不允许模型推断。

## 5. 测试与文档

本次执行后端全量测试结果为：`122 passed, 16 subtests passed, 1 failed`。失败位于 `backend/tests/test_route_and_permission_guards.py:83`，暴露索引依赖未隔离。部署自检可以通过，但未覆盖真实问数语义，因此不能作为问数正确性的发布门槛。

主要测试缺口：

- 没有前端单元测试和真正的浏览器 E2E，历史恢复、流式更新、Markdown 安全和结果卡片缺乏自动保护。
- 集成问数测试对部分错误按 SKIP 处理，容易让真实失败通过流水线。
- 缺少跨数据集、组织多层级、同名实体、指标别名、空结果和部分失败的契约测试。
- 部署文档对首次导入、内置数据和运行态迁移的描述存在漂移。

建议将累计 50 问作为首批语义基线，每题断言结构化字段而非完整自然语言；发布门槛同时包含后端单元测试、真实 PostgreSQL 集成测试、50 问语义回归和 Playwright 历史恢复测试。

## 6. 已有优势

- Docker 健康检查和持久化挂载清晰，当前三个服务健康运行。
- 数据查询多数使用参数化执行，数据集转换对标识符有引用处理。
- OAuth state 校验、RBAC、数据权限和行级权限已经形成较完整基础。
- 敏感配置支持认证加密，并兼容旧格式迁移。
- 运行态迁移支持预览、引用校验和备份；飞书全量同步与增量 upsert 语义清楚。
- 同步成功后会触发转换及受影响数据集节点索引重建，方向符合派生索引设计。
- 前端历史会话对异步竞争已有专门处理，部署诊断脚本也具备继续扩展的基础。

## 7. 建议实施顺序

1. 立即修复 Markdown XSS、密码散列和令牌传递，补安全回归。
2. 建立统一 Query Contract、组织树范围解析和 Result Validator，修复 50 问中的共享正确性问题。
3. 重做跨数据集聚合及维度画像可选能力，关闭单边结果伪装成功。
4. 将飞书 scheduler 独立部署，并把 Web 服务切换到生产 WSGI。
5. 收敛运行态：数据库化或原子写，明确节点索引导入后重建协议，移除更新脚本中的业务初始化。
6. 渐进拆分超大文件，以 50 问和前端 E2E 作为重构保护网。
