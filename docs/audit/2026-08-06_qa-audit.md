## 1. 核心结论

这个系统最要命的不是「测试不够多」，是**它把几乎所有失败都翻译成了「看起来正常的输出」**。

Agent2 没生成出 SQL、Agent3 复核否决、SQL 执行报错且修复失败、LLM 调用整个挂掉、权限过滤把结果全部滤空——这些**性质完全不同的硬失败**，最终都汇流成同一句用户可见文案：

> 「本次围绕『XX』未查询到匹配数据，暂不能判断业绩好坏。」

用户读到的是「这块业务没数据」，真相是「这个查询坏了」。对一个内部 BI 问数系统，这意味着**错误结论会被当作业务事实带进决策会议**，且没有任何环节会喊停。

这一模式在本报告中被命名为**「静默降级族」**（§3），它不是四条散装 bug，是一个需要架构级修复的缺陷族。

次高危的是 **SD-1（LLM 共享状态串用）**，它是本清单唯一一条达到**数据出境**级别的缺陷：用户 A 的业务问题与组织架构数据，可能用用户 B 的 api_key 发往 B 的服务商端点。

## 3. 缺陷族：静默降级族（本报告核心论点）

> **一个族比四条散装 bug 更能说服人去改架构。**

**族定义**：异常/降级状态在系统内部被记录或被吞掉，但**没有任何机制让它浮到用户面前**；调用方拿到降级产物当正常结果继续往下走，最终渲染为与「正常但无数据」不可区分的界面。

**族成员**：

| 成员 | 位置 | 埋点状态 | 是否阻断 | 用户可见性 |
|---|---|---|---|---|
| **SD-2（原 B1）** 三条硬失败汇流为「未查询到匹配数据」 | `four_agent_ask.py:8139-8154` / `8228-8237` / `8358-8367` → `_build_graceful_dataset_result:1196-1232` → `_build_fallback_analysis:506,535-546` | 有 trace | 否 | 与真实空结果**完全同形** |
| **SD-1 出口3** 撕裂配对导致 400/404 | `llm_client.py:136-137` 报错 → `:157` catch | 有 trace | 否 | 无感 |
| **SD-3** `_chat_json` 吞掉全部异常返回 fallback | `llm_client.py:251-261` | **有完整埋点**，含 `error` + `traceback` + `fallback` | 否 | 无感 |
| **SD-4** 流式解析吞异常 | `llm_client.py:189-191` `except Exception: delta=""` | **无任何埋点**（族内唯一真正无声者） | 否 | 无感，表现为回答被静默截断 |
| **SD-5** 权限过滤把结果全部滤空 | `data_permission_store.py:352,514`（详见 B4） | 无 | 否 | 落入 SD-2，显示「未查询到匹配数据」 |
| **SD-6** 否决态被伪造为成功态 | 后端 `four_agent_ask.py:8217-8223`（早于 `:8225` 的 approved 判断）；前端 `SmartAsk.vue:4026` / `4052-4088` | 有 trace（`:8205-8216` 记了 `approved`） | 否 | **比无感更坏——界面主动宣称成功** |

**SD-6 是族内唯一「主动说谎」的成员，其余五条只是「不说话」。** 族定义原本是「降级状态没浮到用户面前」，SD-6 突破了这个边界：它把降级状态**反向渲染为成功态**。用户不是没收到警告，是收到了一个错误的安心信号。因此它在族内单列，且是族里唯一同时污染后端数据契约与前端呈现层的一条。

**关于 SD-3 的表述修正（重要）**：
前序描述称 `_chat_json`「无日志无重抛」，**该表述不准确**。实测 `llm_client.py:252-259` 的 `_append_trace(..., "fallback", error=str(exc), traceback=traceback.format_exc(), fallback=fallback)` **埋点是全的，连 traceback 都落了**。

准确表述是：**有埋点，但不阻断、不告警、不上抛**。

这个区别决定修复方向截然不同：
- 若按「无日志」修 → 加日志 → **做了等于没做**，埋点本来就有；
- 若按「有埋点但不阻断」修 → 把 fallback 提升为**一等状态**，让调用方能判断「这是降级结果」并向用户显式标注 → **这才是真修**。

**族级修复方向**（优先于逐条修）：
在结果契约中引入统一的 `degradation` 字段（`kind` / `stage` / `reason` / `user_visible_message`），规则如下：
1. 任何降级路径**必须**填充该字段，不得静默 return；
2. `_build_graceful_dataset_result` 的四种入因（`no_sql` / `review_rejected` / `exec_failed` / `genuinely_empty`）必须可区分；
3. 前端对非 `genuinely_empty` 的降级，渲染**醒目错误态**，而非分析报告；
4. `_chat_json` 与 `_consume_stream` 的 fallback 必须冒泡到 `degradation`，不得就地咽下。

## 4. 缺陷清单

### P0

#### SD-1 | P0 | 模块级单例 + 共享可变 LLM 状态（合并原 B-1 与 B16，同一根因三出口）

**根因**：`four_agent_ask.py:9063` `four_agent_ask_service = FourAgentAskService()` 为模块级单例，全部请求共用。`ask()` 在 `:8487` 写 `self._preferred_model_id = model_id`，该 setter（`:147-149`）实际写入**共享 LLM 组件**属性。而 `llm_client.py:113` 在**每次 `_chat`** 都重读该共享态，`:119` 每次循环重新 `_activate_llm`。

**关键性质更正**：`ask()` 只在开头写一次，`_chat` 每次都重读。一次提问需串行 5-7 次 LLM 调用。因此 B 一旦写入，**A 剩余的每一次调用都会读到 B 的值**——这不是「竞态窗口」，是**后来者接管先来者的整条流水线**，按必然发生评估。

加重因素：`llm_client.py:112` 每次 `_chat` 开头调 `_load_llm()` → `_activate_llm(default_config)`（`:38-44`），即**每次调用都先把共享态重置为默认模型**再激活候选，共享态写入频率远高于「每请求一次」。

**撕裂窗口**：`_activate_llm:46-51` 先写 `_llm_model`（`:47`）、再写 `_llm_client`（`:48`），而第二次写入是**构造 OpenAI 客户端**（建 httpx client、可能含 DNS/连接池初始化），是一个**有实际执行时长的窗口**，非相邻赋值的纳秒间隙。配合 `:136-137` 的两次独立读取，撕裂概率显著高于普通 TOCTOU。GIL 仅保证单次属性读写原子，**不保证 `(model, client)` 的配对性**。

**三个出口**：

| 出口 | 后果 | 可观测性 |
|---|---|---|
| 1. 模型选错 | 答案质量与用户预期不符；前端仍显示 A 选的模型名 | 无感，trace 可事后查 |
| 2. **凭据/端点串用** | **A 的业务问题 + context 组织架构与销售数据，用 B 的 api_key 发往 B 的服务商端点**；计费错配 | 无感 |
| 3. 撕裂配对 400/404 | 被 `:157` catch；若走 `_chat_json` 则 `:251-261` 吞成 fallback | 无感（静默降级族 SD-1 出口3） |

**为何列为第一优先级**：其余 P0 后果均为「结论不可信」，坏的是决策质量，数据仍在自己家。**出口 2 是本清单唯一一条数据出境级别**——对企业内部 BI 系统，这不是 bug，是数据安全事件。

**修复方向**：LLM 调用态必须请求内隔离——`_chat` 接收显式 config 参数，或每请求构造独立 client，禁止把 `preferred_model_id` / `_llm_model` / `_llm_client` 挂在共享单例上。
**成本**：M　**判定**：推断，未实证

#### SD-6 | P0 | 否决态被伪造为成功态（总监交叉验证发现，本人已逐行核实）

> **来源说明**：本条由总监在对齐后端「不阻断」与前端「零警示」两份结论后追溯根因得出，不是任何单方审计能看到的。我按要求做了独立核实，**核实结论：总监读码无偏差，且实际比他描述的更严重——前端还有一条独立腿。**

**核实项 1：`status: "success"` 是否写在 approved 判断之前？——是。**

```
:8205-8216   _append_trace("pipeline.agent3_result", approved=review.get("approved"), ...)
:8217-8223   steps.append({"title": "Agent3 全量复核", "duration": ..., "status": "success"})
:8224        (空行)
:8225        if review.get("approved") is False:
```

`:8217` 与 `:8225` 之间只有一个空行，无任何条件分支。`status` 是**字面量**，不是变量。

**核实项 2：`:8217` 到 `:8225` 之间有没有别处回写 `steps[-1]["status"]`？——没有，且全文件都没有。**

全文件检索 `steps[-1]` / `steps[len` / `["status"] =` / `['status'] =`，**零命中**。全文件 12 处 `"status": "..."` 全部是 `steps.append()` 时的字面量（`:8090 8104 8136 8159 8221 8330 8347 8355 8372 8401 8750 9048`）。**步骤态一经写入即不可变，不存在事后纠正机制。** 总监的怀疑方向是对的，核实结果是「确实没有后手」。

**核实项 3（我追加的，比上面两条更要命）：步骤对象里根本没有 `approved` 字段。**

`:8217-8223` 构造的 dict 只有三个键：`title` / `duration` / `status`。`approved` 只出现在两个地方——trace 埋点 `:8211`，以及 `dataset_results[].agent3_review`（`:8415`）。

这坐实了总监的归属判断，而且更彻底：**前端不是「忘了读 approved」，是步骤数据里压根没有 approved 可读。** 前端在这条链路上没有任何可能渲染出警示，除非后端先改契约。

**核实项 4（新发现，前端独立的第二条腿）：前端有两条渲染路径，两条都会绿。**

`SmartAsk.vue:4018 getThinkingSteps` 分两支：

- **支 A（刚问完，SSE logs 在）**：`:4043-4049` 走 `mapStatus`。后端 `"success"` → `'completed'` → 绿。**且 `:4026` 的 mapStatus 兜底是 `|| 'completed'`——任何未知或缺失的 status 一律映射为绿色成功。这是呈现层的 fail-open。**
- **支 B（历史消息重渲染 / 刷新后回看）**：`:4052-4088` **完全不读后端 steps**，自己合成步骤，`status` 三处硬编码 `'completed'`（`:4057` `:4064` `:4071`）。

支 B 里最严重的是 `:4060-4066`：
```js
;(msg.data.dataset_results || []).forEach((r) => {
  steps.push({
    text: `已完成数据检索 ${r.dataset_name || '目标数据集'}`,
    detail: r.rows?.length ? `已返回 ${r.rows.length} 行结果数据。` : '已拿到可分析的数据结果。',
    status: 'completed',
  })
})
```
`:4063` 的三元表达式：**rows 为空时，界面输出「已拿到可分析的数据结果。」** 这不是「没提示」，这是一句**主动的虚假陈述**——SD-2 的所有失败场景（Agent2 没出 SQL、Agent3 否决、SQL 执行失败、权限滤空）在历史回看时，全部显示绿色对勾 + 「已拿到可分析的数据结果」。

**后果分级**：不可察觉，且**比单纯的静默降级更坏**。静默降级是不给信号，用户可能存疑；伪造成功态是给错误信号，用户会停止怀疑。对一个供决策使用的问数系统，这直接摧毁了用户自查的最后一道防线。

**修复方向（有严格先后顺序，顺序错了等于白改）**：
1. **后端先改契约**：`:8217-8223` 的 status 由 `review.get("approved")` 决定（`False` → `"warning"` 或 `"error"`），并把 `approved` / `review_summary` 加进步骤对象。**这一步不做，后面两步都是在错误数据上打补丁。**
2. **前端支 A 去掉 fail-open**：`:4026` mapStatus 的兜底从 `'completed'` 改为 `'unknown'` 并渲染中性态，不得把未知当成功。
3. **前端支 B 停止编造**：`:4052-4088` 应复用后端 steps，不能自己合成；在过渡期至少把 `:4063` 的空行文案改为显式降级提示，并把 `:4064` 的 status 改为按 `rows` 与 `degradation` 判定。

**责任归属更正（这条改变了工时估算）**：原判为前端缺一个警示条（前端 S）。实际是**后端契约 S + 前端两处 S**，且存在强顺序依赖，不能并行。

**成本**：S（后端）+ S（前端 ×2），有顺序依赖　**判定**：代码事实为实测（逐行核实 + 全文件检索）；用户认知后果为推断，未实证

实测 `_row_json_text` 走的是 `to_jsonb(row)->>'键名'`，PostgreSQL 对**不存在的键返回 NULL，不报错**。因此：
- `NULL IN ('a','b')` → NULL → WHERE 不成立 → 行被滤除
- `POSITION('x' IN COALESCE(NULL, '')) > 0` → `POSITION('x' IN '')` = 0 → false → 行被滤除

**真实后果比报错更坏**：不是报错，是**全部行被静默滤除 → 零行 → 落入 SD-2 → 显示「未查询到匹配数据」**。权限层本身也是静默降级族成员（§3 SD-5）。报错至少会留下痕迹，静默滤空不会。

**排名类 SQL 泄露路径结论（本节为总监指定的欠项，现结清）**

排名 SQL 由 `ask_engine_sql.py:36-47 _build_ranked_select_sql` 生成，结构为：
```sql
{source_cte},
{output_cte} AS (
    SELECT *, ROW_NUMBER() OVER (ORDER BY {metric} {dir}, {tie_breaker}) AS 全局排名
    FROM {source_name}
    WHERE {where_clause}          -- ← 此处无任何权限谓词
)
SELECT * FROM {output_cte}
WHERE 全局排名 <= {rank_limit}     -- ← 先按全域排名截断
ORDER BY 全局排名, ...
LIMIT {rank_limit}
```
关键：`ROW_NUMBER()` 在**全域数据**上计算，`WHERE 全局排名 <= N` 与 `LIMIT N` 也在**权限过滤之前**执行。权限包裹发生在最外层。执行序为：**全域排名 → 全域截断 TopN → 才按用户权限过滤**。

由此产生两条泄露/失真路径：

**路径 A：排名序号本身构成跨域信息泄露（真泄露）**
`SELECT *` 会把 `全局排名`（双向模式下为 `前排名` / `后排名` / `排名分组`，`ask_engine_sql.py:43-44`）带进结果，外层 `SELECT *` 原样保留。用户即便只被允许看到本部门行，也能读到该行的**全公司排名值**。看到「全局排名 = 47」即可推知全公司至少有 46 个同级单位业绩优于自己——**行级权限限制了「看到哪些行」，却没限制「每行携带的全域统计量」**。这是行级权限模型的经典盲区：过滤了行，没过滤聚合量。

**路径 B：TopN 语义塌缩为静默错误答案（数据正确性）**
用户问「开单金额前 10 的代表处」，内层先取**全公司前 10**，外层再按权限滤成用户可见部分。若用户所属部门无一进入全公司前 10 → **返回零行** → 落入 SD-2 → 显示「未查询到匹配数据」。用户合理理解为「我部门没有代表处数据」，真相是「你部门没人进全国前 10」。若命中 2 个 → 界面按「前 10」的语义呈现 2 行，用户以为这就是本部门前 10 全貌。
**正确语义应是「用户可见范围内的前 10」，实际给出的是「全公司前 10 ∩ 用户可见范围」。两者在任何非超管账号下都不等价。**

补充：路径 B 不受 `to_jsonb` NULL 问题影响——排名 SQL 的 `SELECT *` 通常携带 `节点名称`（`tie_breaker` 默认即 `剩余任务金额 DESC, 节点名称`，`ask_engine_sql.py:36`），故权限条件可正常匹配。真正落入 SD-5 全滤空的是**不携带组织列的聚合查询**（如 `GROUP BY 月份` 的总计）。两条路径互补，覆盖了排名类与聚合类两大主流用法。

**B4-补1：双向排名分支泄露的是字面量文本，不是数字（成立，已验证）**

`ask_engine_sql.py:43` 的 `双向排名结果` CTE 中：
```sql
SELECT *, CASE WHEN 前排名 <= {top_limit} THEN '前{top_limit}' ELSE '后{bottom_limit}' END AS 排名分组
FROM {output_cte}
WHERE 前排名 <= {top_limit} OR 后排名 <= {bottom_limit}
```
输出列 `排名分组` 是**中文字面量**（如 `'后10'`），不是需要推算的序号。用户被权限过滤到只剩本部门一行，仍然直接读到「后10」——**不用推理，界面直接告诉他垫底**。

比路径 A 的「全局排名 = 47」更直白，因为 47 还需要用户自己反应过来「原来我后面只有几家」，而「后10」是已经替他下好的结论。且该分支同时输出 `前排名` 与 `后排名` 两个全域序号（`:43` 两个 `ROW_NUMBER()` 窗口），泄露面是单向分支的两倍。

补充一点总监没提的：`:43` 的截断 `WHERE 前排名 <= {top_limit} OR 后排名 <= {bottom_limit}` 和 `LIMIT {top_limit + bottom_limit}` **也都在权限包裹之内**，所以路径 B 在双向分支上同样成立，且塌缩得更彻底——「前10+后10」二十行先在全域取定，再按权限过滤，用户很可能一行都不剩。

**B4-补2：`LIMIT 10000` 是路径 B 的放大变体，触发面更宽（成立，已验证）**

`:44`（`rank_sides='both'` 但 top/bottom 均为 0）与 `:47`（无 `rank_limit`）两个分支末尾硬编码 `LIMIT 10000`，且前面都带 `ORDER BY 全局排名`（或 `前排名/后排名`）。

执行序：全域按指标排序 → **取全域前 1 万行** → 外层才按权限过滤。

总监的判断成立，并且我要强调触发条件比路径 B 宽得多：**路径 B 需要用户明确问「前 N」才触发，补2 是任何普通查询都在跑。** `:47` 是无 `rank_limit` 的默认分支，也就是用户随便问一句「各代表处开单情况」都会走到。全域行数一旦超过 1 万，排在 1 万名之后的组织，其所属用户**永远查不到自己的数据**，界面稳定显示「未查询到匹配数据」——不是偶发，是**对这批用户永久性的**。

这条的性质因此不同于路径 B：路径 B 是「答案错了」，补2 是「某些用户被系统性地屏蔽在数据之外且无任何提示」。同样落入 SD-2。

**B4-补3：结论成立，但定位需更正——护栏漏的不是那条分支，是主路径（这条请以我的版本为准）**

总监的表述是「`:8249 final_sql = fallback_sql` 之后直奔 `:8253` 包权限、`:8263` 执行，中间没有只读校验」。

**这处定位不准确。** `:8249` 赋值的 `fallback_sql` 在紧邻的 `:8238` 已经过校验：

:8239-47     dataset_results.append(self._build_graceful_dataset_result(...))
:8248        continue
:8249    final_sql = fallback_sql

**Agent3 否决分支是被守住的。**

但总监的结论方向完全正确，而且真相更糟。全文件检索 `_is_read_only_sql` 的全部 8 处调用（`:354` 定义、`:355` 转发、`:6768`、`:7407`、`:7425`、`:7575`、`:8238`、`:8296`），把主 pipeline 的校验覆盖画出来：

| SQL 来源路径 | 可信度 | 是否校验 | 位置 |
|---|---|---|---|
| 维护 SQL / 规则引擎（`review_policy` 为 `trusted_sql` / `rule_sql`） | 高（人工维护或代码生成） | **是** | `:7425` |

还有一处加重情节：`:8188-8190` 的 `_coerce_city_company_level_sql` 在 Agent3 复核**之后**改写 SQL，改写结果既没回炉复核，也没做只读校验。**任何审后改写都使前面的审查结论失效**，这是审查链路的通用反模式。

**B4-补4（本人追加，非总监交办）：外层包裹丢失排序保障**

`data_permission_store.py:514` 的包裹是 `SELECT * FROM (...) AS __smartask_row_scope WHERE {condition}`，**外层没有 ORDER BY**。内层排名 SQL 的 `ORDER BY 全局排名` 位于子查询中。PostgreSQL 不保证子查询的排序会在外层保持（并行计划、Hash 过滤等都可能打乱），仅在简单计划下碰巧保持。

后果：排名结果的**显示顺序可能与排名列不一致**——界面第一行不是排名第一。这类错误对用户完全不可察觉，因为每行的数字都对，只是顺序错了，而用户读排行榜恰恰是**靠行序而不是靠排名列**。

严重度低于补1~补3（不改变数值，只改变顺序），但同属「外层包裹方案根本不成立」的证据链。修复方向与主方案一致：谓词下推后此问题自然消失。
**判定**：推断，未实证（PostgreSQL 子查询排序不保证为文档化行为，但本项目实际计划未观测）

## 6. 修复后如何验证（确定性验证方案）

> 本节方案的性质是**确定性验证**，不是概率性复现。这是它优于活体并发压测的根本原因：活体压测跑十次可能零次命中，无法从「没复现」推出「不存在」；下述方案每次运行结论恒定。

### 6.1 SD-1 的确定性验证

**接缝**：`LLMClient` 的 `_openai_factory` 是**构造注入**的（`four_agent_ask.py:108-118` 传 `openai_factory=OpenAI`；`llm_client.py:48` 调用 `self._openai_factory(...)`）。无需 mock 内部、无需真实端点、无需消耗凭据。

```
1. FakeFactory：记录每次调用收到的 (api_key, base_url)，返回假 client；
   其 chat.completions.create 记录收到的 model，返回假 stream
2. 单个 LLMClient 实例（复刻线上单例语义），两个线程
3. 线程 A 设 _preferred_model_id=9（GLM-5.1）；线程 B 设 =11（DeepSeek-V4-Pro）
4. threading.Barrier 卡在 llm_client.py:113 与 :119 之间强制交错
   —— 把概率性 race 转为确定性 race
5. 断言一：每个线程实际到达 create() 的 model == 该线程自设的 preferred
   断言二：(model, base_url, api_key) 三元组配对一致 —— 抓撕裂（出口 2/3）
```

**当前写不出来**：宿主机缺 `openai`（§5.1）。修 §5.1 是本方案的前置。

### 6.2 静默降级族的验证

对每条 flush 汇总记录断言模型一致性：
```python
models = {e['model'] for e in record['events'] if e.get('model')}
assert len(models) == 1, f"trace {record['trace_id']} 内模型漂移: {models}"
```
**注意断言面选择**：`logs/smartask_trace.jsonl` 实测 79 行，其中 60 行缺 `trace_id`、76 行含 `model`。**不要用那 60 行扁平事件行**——flush 汇总记录**同时带 `trace_id` 和嵌套 `events[]`**，每个 event 自带 `model`，无归并问题。现有唯一一条汇总记录（`trace_id` `99eab3f2…`，67 events，distinct model 单一）可直接作**阴性基线**。

### 6.3 族级回归断言

修复引入 `degradation` 字段后，回归网应断言：**任何非 `genuinely_empty` 的降级，其用户可见文案不得等于真实空结果文案**。这一条断言可一次性守住整个静默降级族。

### 7.1 阶段 5 夹具构造方案（含对基线推断的更正）

**基线推断只对了一半。** 原文称「该段走 `resolved_entity_names(context)` 与 `question_subject_names`，而 PoC 的 context 未提供 `resolved_entities` 键，**分支不可达**」。

逐行核对：
- `resolver.py:254` `resolved_names = self.ports.resolved_entity_names(context)` —— **该行是执行了的，不是不可达**。`_resolved_entity_names`（`ask_engine_profile.py:196-199`）在键缺失时正常返回 `[]`。
- `resolver.py:255-256` **存在兜底**：`if not resolved_names: resolved_names = self.ports.question_subject_names(text, context, include_resolved=False)` —— 基线未提及此兜底，故「分支不可达」表述不成立。
- 兜底为何也无产出？跟进 `_question_subject_names`（`four_agent_ask.py:1835`）：
  - `_has_specific_node`（`ask_engine_entity.py:14-19`）在 `resolved_entities` 缺失时 `flag=None` → 非 bool → **`return True`**，故**未**在 `:1837` 早退；
  - `:1850` `context.get("dataset")` 缺失 → `get_dataset_profile(None, None)` 无 profile → 跳过；
  - `:1868` `_node_index_subject_names_from_question` → `_current_dataset_ids_for_node_index(context)` 无 dataset → **`:1789-1790` 直接 return []**，**恰在触碰 `self._dataset_node_index` 之前返回**——这正是 PoC 261/261 未崩的原因（否则 `object.__new__` 下访问该属性必抛 AttributeError）。

**真实根因**：不是键缺失致不可达，而是**主路径与兜底路径被同一个贫瘠 context 同时饿死**——context 仅有 `report_config`，既无 `resolved_entities` 也无 `dataset`，`resolved_names` 恒为 `[]`，故 L273（40 行 If）与 L316（28 行 If）永不进入。
另注：`resolver.py:313-315` 那处**无兜底**（后接 `if resolved_names and not filter_problem:`），确实只能靠 `resolved_entities` 喂入。

**夹具方案**

Tier A —— 纯数据，无需 `__init__`，解锁 L254 与 L315：

ctx = {

Tier B —— 解锁 L273 的 40 行块。该块按 `specific_names = [n for n in resolved_names if n not in level_like_values]` 分流（`level_like_values` 定义于 `resolver.py:252`）。构造矩阵：

### 7.2 intent 字段稳定性分级

| 档 | 比较方式 | 字段 | 理由 |
|---|---|---|---|
| **A 严格全等** | `assertEqual` | `intent` / `target_level` / `filter_operator` / `direction` / `rank_sides` / `output_mode` | 直接决定走哪条 SQL 生成分支。漂移 = 生成另一条 SQL = 另一个数字 |
| **A 数值全等** | `assertEqual`（不做容差） | `top_n` / `top_limit` / `bottom_limit` / `filter_value` / `filter_value2` | 直接落进 LIMIT 与 WHERE 常量。**金额/比例阈值禁止浮点近似比较** |
| **B 集合比较** | `assertEqual(set(a), set(b))` | `matched_triggers` | 诊断性字段，顺序由匹配次序决定，不应因规则重排而红；但元素集合仍要锁 |
| **C 忽略** | 不断言 | `source` | 溯源字符串，配置重组必变，锁它只造噪音 |
| **键集合** | 按 intent 分类断言 | 整个 dict 的 key set | 基线实测 9 种形状（10~16 键）。**按 intent 类型分别锁**，勿全局锁 |

A 档变化 = 必须人工评审并在 PR 说明业务原因；B/C 档可随实现调整。
