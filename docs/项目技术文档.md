## 1. 项目概览

### 1.1 项目定位

这是一个面向业务分析场景的“智能问数”系统。用户在前端输入自然语言问题后，系统会：

1. 识别业务语义和数据集口径
2. 从“数据集书架”中加载该数据集的业务元数据
3. 由四个 Agent 协作生成 SQL、复核 SQL、执行 SQL、输出分析
4. 将结构化结果、执行轨迹、分析摘要和报告在前端展示

当前系统同时包含三类能力：

- 核心问数链路：`/smart-ask`
- 配置管理链路：数据源、AI 模型、Agent、数据集书架
- 数据接入链路：飞书多维表格同步到 PostgreSQL

### 1.2 实际技术栈

以当前代码为准：

- 前端：Vue 3 + Vite + Vue Router + Element Plus + Axios + Marked + ECharts
- 后端：Flask + Flask-CORS
- AI/问数：OpenAI 兼容 SDK + Vanna + ChromaDB
- 元数据存储：
  - `config/*.json` 存配置
  - PostgreSQL `bs_*` 表存数据集书架元数据
- 业务数据源：SQLite / MySQL / PostgreSQL / SQL Server
- 同步能力：飞书开放平台 API + PostgreSQL

## 3.7 四 Agent 问数主链路

文件：[backend/four_agent_ask.py](/d:/万物云/万物云/AI培训/智能问数流程/火山引擎/智能问数项目_v20260330_004926(3)-566fee42a29e/智能问数项目_v20260330_004926/backend/four_agent_ask.py)

### 3.7.1 整体职责

- 加载默认 LLM
- 基于 Bookshelf 做语义路由
- 管理“老板确认”会话
- 串行执行 Agent1 到 Agent4
- 记录 trace
- 返回前端可展示结果

### 3.7.2 关键对象

- `BookshelfRepository()`：元数据入口
- `_pending_confirmations`：内存中的确认会话池
- `_pending_ttl_seconds = 30 * 60`：确认会话 30 分钟过期
- `smartask_trace.jsonl`：链路追踪日志

### 3.7.3 主执行流程

`ask(question, preferred_dataset_ids=None)`：

1. 校验问题是否为空
2. 检查 Bookshelf 元表是否存在，不存在则尝试自动建表
3. 调用 `route_with_agent1()`
4. 如果需要确认：
   - 创建确认 session
   - 返回 `requires_confirmation = true`
5. 否则调用 `_run_pipeline()`

`_run_pipeline()`：

1. 逐个 `dataset_id` 加载上下文
2. Agent2 生成 SQL
3. Agent3 复核 SQL
4. 执行 SQL
5. Agent4 输出业务分析
6. 汇总为 `dataset_results`

### 3.7.4 Agent 职责落地

Agent1：

- 结合数据集目录、同义词、Golden SQL、LLD 做路由
- 判断是否需要“老板确认”

Agent2：

- 根据 `refined_query + 数据字典 + DDL + 表关系 + Golden SQL + Agent2 Prompt`
- 生成只读 SQL

Agent3：

- 检查 SQL 是否满足口径、只读、安全、字段语义
- 必要时改写为 `final_sql`

Agent4：

- 将结果数据转成老板可读的分析结论

### 3.7.5 当前返回结构

成功执行时，顶层结果主要包含：

- `question`
- `route`
- `confidence`
- `dataset_results`
- `data_source`
- `sql`
- `columns`
- `rows`
- `row_count`
- `analysis`
- `steps`
- `requires_confirmation`
- `total_duration`

其中 `dataset_results[*]` 包含：

- `dataset_id`
- `dataset_code`
- `dataset_name`
- `source_id`
- `agent3_review`
- `columns`
- `rows`
- `row_count`
- `analysis`
- `sql`

### 3.7.6 老板确认链路

确认入口：

- `POST /api/smart-chat/confirm-by-boss`

后端逻辑：

1. 按 `session_id` 找到挂起会话
2. 根据 `option_id` 或 `selected_option` 还原所选确认项
3. 写回 `route.dataset_ids`
4. 追加 `boss_confirmation`
5. 继续走 `_run_pipeline()`
6. 执行完成后删除该 session

## 6. 前后端是怎么打通的

## 6.1 智能问数主链路

### 6.1.1 前端发起

入口：

- `SmartAsk.vue` 收集输入
- `smartAskSession.startAsk()` 统一发请求

流程：

1. `ComposerArea` 触发发送
2. `SmartAsk.vue` 调 `session.startAsk(text, datasetId)`
3. `smartAskSession.js`：
   - 规范化数据集 ID
   - 记录 LocalStorage 会话快照
   - 构建“阶段时间线”
   - 调 `sendSmartChat()`

### 6.1.2 后端处理

1. `controllers/smart_chat.py::smart_chat`
2. `four_agent_ask_service.ask`
3. `route_with_agent1`
4. 如果要确认则返回确认卡
5. 否则继续 `_run_pipeline`

### 6.1.3 前端渲染结果

`smartAskSession.finalizeFromResult()` 会把后端结果转换成时间线事件：

- 路由事件
- SQL 生成
- SQL 复核
- SQL 执行
- 数据处理
- 业务洞察
- 报告生成

`SmartAsk.vue` 再把这些状态和结果喂给：

- `LiveExecutionFeed`
- `LogTimeline`
- `ResultDigestCard`
- `ReportSummary`

## 6.2 老板确认链路

理想链路应该是：

1. 后端返回 `requires_confirmation = true`
2. `SmartAsk.vue` 展示确认问题和确认选项
3. 用户点击确认
4. `smartAskSession.submitBossConfirmation()`
5. 前端调用 `/api/smart-chat/confirm-by-boss`
6. 后端按 `session_id` 恢复路由上下文
7. 继续跑 Agent2-4

但当前代码里存在一个实际问题：

- `smartAskSession.js` 的 `submitBossConfirmation()` 前面还有一段提前 `return startAsk(...)` 的代码块
- 它会直接重新发起问数，而不是优先走后端确认会话接口

这会导致：

- 后端真正的确认 session 机制被前端绕开
- 你想做的“结构化确认选项”很难完整落地

## 6.3 数据集管理链路

1. `DatasetManagement.vue` 加载数据集列表和数据源列表
2. 选择某个数据集时调用 `/api/bookshelves/datasets/{id}/full`
3. 前端把结果拆到多个标签页/集合
4. 用户修改后：
   - 先 `PUT /api/bookshelves/datasets/{id}` 更新基础信息
   - 再 `PUT /api/bookshelves/datasets/{id}/full` 保存全量元数据
5. 后端写回 PostgreSQL `bs_*` 表

这条链路直接决定问数质量，因为 Agent1 到 Agent4 都依赖这些元数据。

## 6.4 数据源管理链路

1. `Databases.vue` 提交表单
2. 调 `POST/PUT /api/datasources`
3. `config_manager.py` 写入 `config/datasources.json`
4. `mark_reinit()` 标记 Vanna 失效
5. 下一次问数时重新初始化

## 6.5 AI 模型管理链路

1. `AIModels.vue` 提交表单
2. 调 `POST/PUT /api/ai-models`
3. 写回 `config/ai_settings.json`
4. `mark_reinit()`
5. 下一次问数时使用新默认模型

## 6.6 飞书同步链路

1. `FeishuSync.vue` 保存配置
2. 后端写入 `config/feishu_sync.json`
3. 点击“同步”后调 `/api/feishu-sync/{id}/start`
4. 控制器起后台线程
5. `FeishuSyncService`：
   - 获取 Token
   - 拉 bitable 数据
   - 连接 PostgreSQL
   - 建表
   - UPSERT
6. 更新状态和日志
7. 前端轮询刷新

## 8. 当前代码里的重要观察

## 8.1 README 与真实代码不完全一致

`README.md` 写的是：

- 后端 Flask + Pydantic + SQLAlchemy

但当前实际可见依赖和代码并不是这个结构：

- 没有真正使用 SQLAlchemy 作为核心数据访问层
- 主要数据访问是 `psycopg2 + JSON 文件`

## 8.2 智能问数主链路已经以 Bookshelf 为中心

虽然仓库里还有 legacy `chat.py`、`training.py` 等模块，但当前真正生效的问数入口已经是：

- `smart_chat.py`
- `four_agent_ask.py`
- `bookshelf_repository.py`

这三者是后续改造的主战场。

## 8.3 当前动态确认改造只落了基础文件，没完全接通

已看到：

- `dataset_dimension_profiles.py`
- `dataset_dimension_profiles.json`
- `four_agent_ask.py` 已 import 这两个 helper

但未看到：

- 画像命中逻辑接入 `route_with_agent1`
- `resolved_members / confirmation_type / scope_mode` 真正写回 route
- `smart_report` 结构返回给前端
- 前端结果卡消费新的结构化报告

所以这部分现在还属于“改造进行中”。

## 8.4 前端确认提交逻辑有截胡问题

`smartAskSession.js` 当前 `submitBossConfirmation()` 存在一段前置代码块，直接：

- 更新前端状态
- 重新调用 `startAsk()`
- 提前 `return`

结果是：

- 后半段真正调用 `/confirm-by-boss` 的代码很难被执行
- 后端的 session 化确认机制等于被绕过

这个问题建议优先修。

## 8.5 当前结构化层级报告还没有真正接到 UI

目前：

- `ResultDigestCard.vue` 还是旧版摘要卡
- 返回结构仍以 `report + dataset` 为主
- `smart_report` 相关结构还没出现在线路里

所以你要做的“当前节点 KPI + 下钻两级/三级”的报告，目前还没有进入真正闭环。

## 9. 建议的下一步改造顺序

结合你现在的目标，建议按下面顺序推进。

### 9.1 先修确认会话闭环

优先级最高。

原因：

- 这是“结构化确认”能不能成立的前提
- 不修它，前端永远只是重发问题，后端 session 会白做

建议动作：

1. 去掉 `smartAskSession.js` 里前置的提前 `return startAsk(...)`
2. 保留真正的 `/confirm-by-boss` 提交
3. 只有 session 失效时才 fallback 为重新发问

### 9.2 再把组织画像接到 Agent1 路由

建议在 `four_agent_ask.py` 中补：

1. 基于 `dataset_code / dataset_name` 读取画像
2. 在 `route_with_agent1()` 里插入画像命中判断
3. 对 “4大分公司” 这类组口径返回结构化确认项

建议把这些字段正式写入 route：

- `confirmation_type`
- `matched_alias`
- `resolved_dimension`
- `resolved_members`
- `scope_mode`

### 9.3 再做结构化报告返回

建议让后端在每个 `dataset_result` 上新增例如：

- `smart_report`
- `current_node`
- `sections`
- `narrative_lines`

并在顶层结果也带一个主 `smart_report`，方便前端只取第一层。

### 9.4 最后改前端卡片与层级展开 UI

前端可以分两层：

1. 摘要卡：
   - 当前节点名称
   - 当前层级
   - 6 个 KPI
   - 一段结论
2. 层级卡：
   - 下一级列表
   - 可展开下二级
   - 必要时下三级

这样和你现在设想的“东部分公司 -> 代表处 -> 业务员”会最贴合。
