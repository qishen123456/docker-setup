# 迁移发布与运行态配置保护方案

更新时间：2026-05-08

当前项目真实 Git 信息：

```text
Gitee remote：https://gitee.com/tailin1/volcano-intelligent-questions.git
当前可拉取发布分支：docker-setup
```

注意：Linux/Git 对分支名大小写敏感。已核验当前本地与 Gitee 远端存在的分支是 `docker-setup`；如果后续你在 Gitee 另建大写 `DOCKER-SETUP` 分支，命令里的 `docker-setup` 才需要替换成 `DOCKER-SETUP`。

本文档解决的问题：

- Windows 测试环境开发完成后，如何发布到 Linux 正式环境。
- 经常发布代码时，如何保证正式系统稳定运行。
- 数据源、数据集、提示词、报告配置等运行态配置如何不丢。
- 如果误删或覆盖生产配置，如何回滚。

Linux Docker 基础部署请看：

```text
docs/Linux_Docker部署运维手册.md
```

运行态配置的前端导出导入和命令行操作请看：

```text
docs/运行态配置导出导入操作手册.md
```

## 1. 总体原则

SmartAsk 发布必须分清两类东西：

### 1.1 代码资产

代码资产放 Git。

包括：

- 前端源码。
- 后端源码。
- Dockerfile。
- docker-compose.yml。
- 部署脚本。
- 文档。
- 默认初始化模板。

### 1.2 运行态资产

运行态资产不要依赖 Git 自动同步。

包括：

- 数据源配置。
- 数据集配置。
- 字段字典。
- Agent 提示词。
- AI 模型配置。
- 报告模板配置。
- 员工权限配置。
- 系统控制台功能开关 `config/feature_flags.json`。
- 用户登录 token。
- PostgreSQL 业务数据。
- Chroma 向量库。
- `config/` 目录。
- `.env`。

代码更新应该是高频动作。

运行态资产更新应该是受控动作，必须可备份、可预览、可回滚。

## 2. 推荐环境结构

### 2.1 Windows 测试环境

用于：

- 开发代码。
- 调整前端体验。
- 调整后端逻辑。
- 测试数据源、数据集、提示词。
- 验证问数流程。

### 2.2 Linux 正式环境

用于：

- 真实用户访问。
- 保存正式数据。
- 保存正式配置。
- 执行稳定版本代码。

正式环境不能直接用测试环境的数据库 volume 覆盖。

正式环境也不能随便执行会覆盖配置的初始化参数。

## 3. 发布类型分类

每次发布前，先判断属于哪一类。

### 3.1 只发布代码

例如：

- 改前端样式。
- 改交互。
- 改 API 逻辑。
- 改 Docker 脚本。
- 改文档。

这种只需要 Git 发布。

不需要迁移数据库配置。

### 3.2 发布代码 + 运行态配置

例如：

- 新增数据源。
- 修改数据集字段。
- 修改 Agent 提示词。
- 修改报告模板。
- 修改 AI 模型配置。
- 修改业务口径配置。

这种不能只推 Git。

还需要导出运行态配置包，并在正式环境导入。

### 3.3 数据库结构变更

例如：

- 新增表。
- 新增字段。
- 修改索引。
- 修改迁移 SQL。

这种需要数据库 migration，并且正式环境发布前必须备份。

## 4. 代码发布 SOP

适用于只改代码，不改运行态配置。

### 4.1 Windows 本地验证

```powershell
cd smartask
npm run build
python scripts/integration_test.py --base-url http://localhost:5002 --frontend-url http://localhost:5173 --no-wait
```

### 4.2 Windows 提交代码

```powershell
git status
git add .
git commit -m "feat: update smartask"
git push gitee docker-setup
```

如果你是第一次把本地 `docker-setup` 分支推到 Gitee：

```powershell
git push -u gitee docker-setup
```

### 4.3 Linux 正式环境备份

即使只发布代码，也建议先做轻量备份。

```bash
cd smartask
mkdir -p backups
docker compose exec -T postgres pg_dump -U postgres -d postgres > backups/smartask_pg_$(date +%Y%m%d_%H%M%S).sql
tar -czf backups/smartask_config_$(date +%Y%m%d_%H%M%S).tar.gz config
git rev-parse HEAD > backups/git_commit_$(date +%Y%m%d_%H%M%S).txt
```

### 4.4 Linux 正式环境更新

```bash
cd smartask
git checkout docker-setup
git pull --ff-only
docker compose up -d --build
docker compose ps
curl http://localhost:5002/api/health
```

### 4.5 验证

必须验证：

- 登录页面正常。
- 超级管理员能登录。
- 普通用户权限正常。
- 问数页面正常。
- 后端健康检查正常。
- 最近一次核心问数能跑通。

如果页面还是旧版本：

```text
Ctrl + F5
```

## 5. 运行态配置发布 SOP

适用于改了数据源、数据集、提示词、报告配置等。

当前项目已提供两条导出导入路径：

```text
前端页面：左侧菜单 -> 迁移发布管理
命令行脚本：scripts/export_runtime_config.py / scripts/import_runtime_config.py
```

Docker 容器内脚本路径：

```text
/app/scripts/export_runtime_config.py
/app/scripts/import_runtime_config.py
```

后端运行态服务实现：

```text
backend/runtime_migration.py
backend/controllers/runtime_migration.py
```

### 5.1 Windows 测试环境导出

目标命令：

```powershell
python scripts/export_runtime_config.py --output backend/imports/runtime_config_20260507.json
```

导出包应包含：

- 数据源。
- 数据集。
- 字段字典。
- Agent 提示词。
- AI 模型配置。
- 报告模板配置。
- 业务口径配置。

不应包含：

- 用户 token。
- 明文密码。
- `.env` 密钥。
- 大量业务交易数据。

### 5.2 传到 Linux 正式环境

```bash
scp backend/imports/runtime_config_20260507.json user@server:/opt/smartask/backend/imports/
```

### 5.3 Linux 正式环境 dry-run

先预览，不落库：

```bash
cd /opt/smartask
docker compose exec -T backend python /app/scripts/import_runtime_config.py \
  --input /app/backend/imports/runtime_config_20260507.json \
  --mode merge \
  --dry-run
```

dry-run 应输出：

- 会新增哪些数据源。
- 会更新哪些数据集。
- 会更新哪些提示词。
- 会修改哪些报告配置。
- 是否存在冲突。
- 是否存在危险覆盖。

### 5.4 Linux 正式环境导入

确认 dry-run 没问题后：

```bash
docker compose exec -T backend python /app/scripts/import_runtime_config.py \
  --input /app/backend/imports/runtime_config_20260507.json \
  --mode merge
```

默认必须自动备份。

不建议生产环境直接使用 overwrite。

## 6. 导入前自动备份设计

运行态配置导入工具必须默认自动备份。

建议每次导入前生成：

```text
backups/runtime/20260507_153000/
  manifest.json
  pg_dump.sql
  config.tar.gz
  runtime_config_before.json
```

### 6.1 manifest.json

记录：

- 导入时间。
- 操作者。
- 当前 Git commit。
- 导入文件名。
- 导入模式。
- 影响的表。
- 备份文件路径。
- dry-run 结果摘要。

### 6.2 pg_dump.sql

完整数据库备份。

用于严重误操作后的灾难恢复。

### 6.3 config.tar.gz

备份 `config/`。

用于恢复员工权限、token 映射、本机 JSON 配置等。

### 6.4 runtime_config_before.json

只备份本次导入会影响的运行态配置。

用于快速回滚提示词、数据源、数据集等配置。

## 7. 导入模式设计

### 7.1 dry-run

只预览，不修改。

```bash
--dry-run
```

生产环境正式导入前必须先 dry-run。

### 7.2 merge

推荐默认模式。

规则：

- 新配置新增。
- 已存在配置按唯一标识更新。
- 不删除正式环境已有但导入包里没有的配置。

命令：

```bash
--mode merge
```

### 7.3 overwrite

危险模式。

规则：

- 允许覆盖正式环境已有配置。
- 可能导致生产配置被测试环境配置覆盖。

必须显式加：

```bash
--mode overwrite --force
```

### 7.4 no-backup

原则上不允许生产环境使用。

如果后续实现，也必须非常醒目：

```bash
--no-backup
```

生产环境默认应该禁止 `--no-backup`。

## 8. 回滚方案

### 8.1 轻量回滚

适用于：

- 提示词覆盖错了。
- 数据集配置错了。
- 数据源配置错了。
- 报告模板错了。

使用导入前自动生成的 `runtime_config_before.json`。

目标命令：

```bash
docker compose exec -T backend python /app/scripts/import_runtime_config.py \
  --input /app/backups/runtime/20260507_153000/runtime_config_before.json \
  --mode overwrite \
  --force
```

### 8.2 完整数据库回滚

适用于：

- 大量配置被覆盖。
- 误删了关键数据。
- migration 失败导致数据异常。
- 无法判断具体影响范围。

步骤：

```bash
docker compose stop backend
cat backups/runtime/20260507_153000/pg_dump.sql | docker compose exec -T postgres psql -U postgres -d postgres
tar -xzf backups/runtime/20260507_153000/config.tar.gz
docker compose start backend
curl http://localhost:5002/api/health
```

### 8.3 代码回滚

查看上一个 Git commit：

```bash
cat backups/git_commit_时间戳.txt
```

回滚代码：

```bash
git checkout 上一个commit
docker compose up -d --build
```

或切回某个 tag：

```bash
git checkout v1.0.0
docker compose up -d --build
```

## 9. 如何保证经常发布代码时系统稳定

### 9.1 每次发布都必须分类

发布前问自己：

```text
这次只改代码吗？
这次改了运行态配置吗？
这次改了数据库结构吗？
```

不同类型走不同 SOP。

### 9.2 发布前必须备份

最低要求：

```bash
pg_dump
config.tar.gz
git commit 记录
```

### 9.3 发布必须可回滚

每次发布要能回答：

```text
代码怎么回滚？
数据库怎么回滚？
config 怎么回滚？
运行态配置怎么回滚？
```

### 9.4 正式环境禁止覆盖初始化

正式环境默认不要使用：

```text
ForceImport
ForceConfig
SMARTASK_BOOTSTRAP_FORCE_IMPORT=1
SMARTASK_BOOTSTRAP_FORCE_CONFIG=1
```

除非已经备份并明确知道后果。

### 9.5 发布后必须验证

验证清单：

- 登录正常。
- 权限正常。
- 数据源存在。
- 数据集存在。
- 提示词存在。
- 问数流程能跑通。
- 报告能生成。
- 历史分析按账号隔离。
- 后端日志没有持续报错。

### 9.6 保留最近 N 次备份

建议保留：

- 最近 7 天每日备份。
- 最近 10 次发布备份。
- 重大版本备份长期保存。

### 10.1 当前仓库已具备



### 10.2 后续可补强

可新增 Linux Shell 脚本：

```text
deploy.sh
update.sh
backup.sh
restore.sh
doctor.sh
```

目标：

- Linux 首次部署一键化。
- Linux 日常更新一键化。
- 更新前自动备份。
- 报错时生成诊断包。
- 与 Windows `deploy.ps1`、`update.ps1` 的行为保持一致。

### 10.3 发布保护机制

增强：

- 导入前显示 diff。
- 危险操作二次确认。
- overwrite 必须 `--force`。
- 生产环境默认禁止 `--no-backup`。
- 记录 manifest。

### 10.4 版本化运行态配置

后续可以把运行态配置包做版本管理：

```text
runtime_configs/
  20260507_sales_prompt_v1.json
  20260510_dataset_update_v2.json
```

但不建议把含敏感信息的配置包直接提交 Git。

## 11. 标准发布流程总览

### 11.1 只改代码

Windows：

```powershell
npm run build
git add .
git commit -m "feat: update code"
git push gitee docker-setup
```

Linux：

```bash
cd smartask
mkdir -p backups
docker compose exec -T postgres pg_dump -U postgres -d postgres > backups/smartask_pg_$(date +%Y%m%d_%H%M%S).sql
tar -czf backups/smartask_config_$(date +%Y%m%d_%H%M%S).tar.gz config
git checkout docker-setup
git pull --ff-only
docker compose up -d --build
curl http://localhost:5002/api/health
```

### 11.2 改代码 + 改运行态配置

Windows：

```powershell
npm run build
git add .
git commit -m "feat: update code and runtime config"
git push gitee docker-setup
python scripts/export_runtime_config.py --output backend/imports/runtime_config_版本.json
scp backend/imports/runtime_config_版本.json user@server:/opt/smartask/backend/imports/
```

说明：运行态配置包可能包含业务连接信息和提示词，不建议直接提交 Git。先推代码，再把运行态配置包传到生产服务器的 `backend/imports/` 目录。

Linux：

```bash
cd smartask
mkdir -p backups
docker compose exec -T postgres pg_dump -U postgres -d postgres > backups/smartask_pg_$(date +%Y%m%d_%H%M%S).sql
tar -czf backups/smartask_config_$(date +%Y%m%d_%H%M%S).tar.gz config .env
git checkout docker-setup
git pull --ff-only
docker compose up -d --build
docker compose exec -T backend python /app/scripts/import_runtime_config.py --input /app/backend/imports/runtime_config_版本.json --mode merge --dry-run
docker compose exec -T backend python /app/scripts/import_runtime_config.py --input /app/backend/imports/runtime_config_版本.json --mode merge
curl http://localhost:5002/api/health
```

### 11.3 改数据库结构

必须：

- 先备份。
- 在测试环境验证 migration。
- 在正式环境低峰期发布。
- 准备数据库回滚方案。

Linux：

```bash
cd smartask
mkdir -p backups
docker compose exec -T postgres pg_dump -U postgres -d postgres > backups/smartask_pg_$(date +%Y%m%d_%H%M%S).sql
tar -czf backups/smartask_config_$(date +%Y%m%d_%H%M%S).tar.gz config .env
git checkout docker-setup
git pull --ff-only
docker compose up -d --build
curl http://localhost:5002/api/health
docker compose logs --tail=200 backend
```

## 12. 当前结论

当前最安全的方向：

- Docker 部署文档和迁移发布文档分开维护。
- 代码发布走 Git。
- 正式数据和配置走备份、导出、导入、回滚机制。
- 后续优先补 Linux 脚本和运行态配置导出导入工具。

这样你就可以在 Windows 本地高频开发，在 Linux 正式环境稳定发布，并且即使误删或覆盖配置，也能通过备份回滚。
