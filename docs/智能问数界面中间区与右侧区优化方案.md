# 智能问数中间区与右侧区增量优化方案

版本：v2.0  
日期：2026-05-11  
定位：基于当前项目继续优化，不推翻现有四 Agent、报告契约和前端组件

## 1. 这版方案的边界

上一版更像目标蓝图，容易让人误解成要重做一套火山引擎。本版改成贴合当前项目的增量优化方案。

明确不做这些事：

1. 不推翻现有四 Agent 链路。
2. 不重写 `SmartAsk.vue`。
3. 不替换当前 SSE 实时执行流。
4. 不把报告模板配置改成大量人工维护。
5. 不新增一套和 `report_spec_builder.py` 平行的报告系统。
6. 不修改 Docker 部署结构，除非后续真的新增系统依赖或启动命令。

本次要做的是：

1. 保留当前能力。
2. 参考火山引擎的“中间区看答案、右侧区看过程”。
3. 在现有组件和现有后端契约上继续打磨。
4. 让智能问数看起来更顺、更可信、更好维护。

## 3. 火山引擎参考点如何落到当前项目

参考资料：

- `火山引擎/中间区.png`
- `火山引擎/右侧区 (1).png`
- `火山引擎/分割图片_中间区`
- `火山引擎/分割图片_右侧区 (1)`

火山引擎值得借鉴的不是具体皮肤，而是信息分工：

| 火山引擎表现 | 当前项目对应位置 | 增量优化方式 |
|---|---|---|
| 中间区先给执行计划 | `PlanCard.vue` | 保留，改成默认简洁、可折叠，不展示技术噪声 |
| 中间区只看关键进展 | `LiveExecutionFeed.vue` | 保留，减少重复“实时进度”文字，只展示当前 5 到 7 个阶段 |
| 完成后给结果入口 | `ResultDigestCard.vue` | 强化为主回答卡，直接回答用户问题 |
| 右侧区展示完整执行详情 | `LogTimeline.vue` | 保留，优化节点命名、默认折叠、错误定位 |
| SQL 和代码放右侧 | `SqlBlock.vue` | 保留，继续只在右侧节点详情展示 |
| 报告作为交付物 | `SmartAsk.vue` 全屏报告 | 保留，统一中间区摘要和全屏报告的内容来源 |

核心原则：

中间区不变成日志区，右侧区不变成第二份聊天答案。

## 4. 当前页面的真实问题

结合当前项目代码和你之前反馈，问题主要不在“没有功能”，而在“功能之间的主次没有完全理顺”。

### 4.1 中间区问题

当前中间区的问题：

1. `LiveExecutionFeed`、`PlanCard`、`ThinkingCard`、`ResultDigestCard` 会连续出现，信息密度有时偏高。
2. `ResultDigestCard` 虽然已经做了对比摘要，但单一组织、两个主体、多主体、排名场景的视觉规则还需要更稳定。
3. 单一分公司问题应该先讲“这个分公司整体怎么样”，不能先被代表处或业务员明细抢走焦点。
4. 多主体问题如果对象超过 4 个，第一屏不能把所有 KPI 都铺满。
5. 中间区和全屏报告有时口径看起来不一致，本质是摘要、KPI、下钻都在不同函数里二次组织。
6. 下钻按钮已经有，但还需要更自然地和组织卡标题、结果摘要并排，减少突兀感。

### 4.2 右侧区问题

当前右侧区的问题：

1. `LogTimeline` 已有节点，但节点默认展开策略还不够“老板友好”。
2. 有些节点会显示重复摘要，比如生成说明重复、实时进度重复。
3. 失败时虽然有错误信息，但用户第一眼不一定知道失败在哪个节点。
4. 右侧区下方还承载 `hasSideReport` 报告预览，执行轨迹和报告预览容易争抢注意力。
5. 表格预览只有前 5 行，够轻量，但复制数据入口还不够顺。
6. 节点名称和中间区流程名称还没有完全统一。

### 4.3 后端契约问题

当前 `report_spec_builder.py` 已经很关键，但前端仍有一部分推断逻辑。

需要优化的是：

1. 继续让 `report_spec_builder.py` 输出页面需要的结构化信息。
2. 前端减少基于问题文本的硬判断。
3. 不让 Agent4 写死页面结构，Agent4 负责业务洞察，页面结构由 `report_spec` 控制。
4. 报告模板配置继续作为指标、层级、口径、阈值的来源，不要求你维护每一种问法的模板。

## 6. 中间区增量优化方案

### 6.1 当前中间区组件关系

当前 `SmartAsk.vue` 中间区大致是：

```text
WelcomeScreen
-> UserBubble
-> LiveExecutionFeed
-> PlanCard
-> ThinkingCard
-> ConfirmationCard
-> ResultDigestCard
-> InlineVisuals
-> ErrorCard
-> ComposerArea
```

这个结构可以保留。

优化重点不是新增组件，而是调整展示优先级。

### 6.2 运行中展示规则

运行中建议只保留三层：

```text
LiveExecutionFeed：轻量流程
PlanCard：执行计划，默认可收起
ThinkingCard：高级细节，默认收起或仅异常时打开
```

建议规则：

1. 正在执行时，`LiveExecutionFeed` 是主展示。
2. `PlanCard` 只展示业务步骤，不展示 SQL。
3. `ThinkingCard` 默认收起，作为“过程明细”补充，不和右侧日志重复。
4. 如果右侧区打开，中间区减少技术细节。
5. 如果右侧区关闭，中间区保留更简洁的 5 到 7 步流程。

涉及文件：

```text
frontend/src/views/SmartAsk.vue
frontend/src/components/smartask/LiveExecutionFeed.vue
frontend/src/components/smartask/PlanCard.vue
frontend/src/components/smartask/ThinkingCard.vue
```

### 6.3 完成后展示规则

完成后中间区以 `ResultDigestCard.vue` 为主。

目标结构：

```text
问题
核心结论
关键指标摘要
下钻入口
操作区
```

当前 `ResultDigestCard.vue` 已经有：

1. 问题。
2. 结论。
3. 对比卡片。
4. 支撑信息。
5. 查看详情。
6. report debug 条。

建议优化：

1. `reportDebugItems` 默认不在老板视角展示，移到右侧区或只在调试开关下展示。
2. 单一组织场景使用 `report_spec.scope.focusNode` 和 `report_spec.kpis` 生成核心结论。
3. 对比场景使用 `report_spec.accordions` 或新增 `entityCards` 生成主体卡。
4. 多主体超过 4 个时，只展示最高、最低、整体和风险数量。
5. 下钻入口直接出现在摘要卡里，不只放到右侧报告。

涉及文件：

```text
frontend/src/components/smartask/ResultDigestCard.vue
frontend/src/views/SmartAsk.vue
backend/report_spec_builder.py
```

### 6.4 单一组织场景

问题示例：

```text
东部分公司业绩怎么样
```

中间区应该直接展示：

```text
东部分公司整体进度偏低，当前达成率 13.37%，年度开单 1270 万，剩余缺口 8230 万。
下级 7 个代表处中，山东代表处表现最好，河南代表处压力最大。
```

页面规则：

1. 第一屏先回答东部分公司整体，不先展示业务员。
2. KPI 卡片控制在 4 个。
3. 展示“可展开 7 个代表处”。
4. 如果 SQL 返回了业务员层级，业务员作为代表处展开后的证据层。

当前落点：

```text
report_spec_builder.py
-> analysisMode: single_focus 或 detail
-> scope.focusNode
-> kpis
-> accordions
ResultDigestCard.vue
-> 读取上述结构组织摘要
```

### 6.5 两个主体对比场景

问题示例：

```text
东部和西部业绩对比
```

中间区应该展示：

```text
东部分公司达成率 13.37%，高于西部分公司 10.68%，领先 2.69 个百分点。
两者整体进度都偏低，建议先看代表处层差异。
```

页面规则：

1. 两个主体颜色固定，比如东部蓝、西部绿。
2. 每个主体一张紧凑卡，展示达成率、开单、任务、缺口。
3. 差异用独立的小条展示，不夹在长句里。
4. 每个主体卡都有“展开代表处”入口。

当前落点：

```text
ResultDigestCard.vue
-> 现有 isComparisonDigest 继续保留
-> visibleComparisonDigestRows 继续保留
-> 优化 comparisonVerdict 和 comparisonGapItems 文案
```

### 6.6 三到四个主体对比场景

问题示例：

```text
三大业务部业绩怎么样
```

页面规则：

1. 允许展示 3 到 4 个主体。
2. KPI 区展示整体指标加各主体达成率。
3. 核心结论要覆盖全部主体，不能只比较两个。
4. 颜色和下方报告保持一致。

当前落点：

```text
report_spec_builder.py
-> compare_count <= 4 分支已经存在
-> 继续优化 summary_parts
ResultDigestCard.vue
-> 对 3 到 4 个 visibleComparisonDigestRows 做等宽布局
```

### 6.7 五个以上主体对比或排名

问题示例：

```text
9 大分公司达成率排名
```

页面规则：

1. 不平铺所有主体。
2. 第一屏展示整体数量、最高、最低、首尾差距、风险数量。
3. 明细放在报告或展开表格里。
4. 中间区只提供“查看完整排名”入口。

当前落点：

```text
report_spec_builder.py
-> compare_count > 4 分支已经存在
-> 继续补充 displayPolicy.entityDisplayLimit
ResultDigestCard.vue
-> 按 displayPolicy 控制摘要数量
```

### 6.8 用户问题操作

`UserBubble.vue` 已经实现：

1. 复制。
2. 修改。
3. 重新问。
4. 悬浮显示图标。
5. 图标 tooltip。

因此这里不需要重做，只建议微调：

1. 保持图标默认隐藏。
2. 悬浮问题气泡时出现。
3. 图标 hover 时显示中文。
4. 修改后回填 `ComposerArea`。
5. 重新问时继续调用现有 `rerunQuestion`，清空上一轮 AI 输出和执行日志。

涉及文件：

```text

frontend/src/views/SmartAsk.vue
```

## 7. 右侧区增量优化方案

### 7.1 当前右侧区结构

当前 `SmartAsk.vue` 右侧区大致是：

```text
面板标题
-> LogTimeline
   -> SqlBlock
   -> 图表预览
   -> 表格预览
   -> markdown 节点摘要
-> hasSideReport 报告预览
```

这个结构可以保留。

优化重点：

1. 让 `LogTimeline` 更像执行证据链。
2. 让报告预览不抢执行轨迹的注意力。
3. 失败时一眼知道哪里失败。

### 7.2 执行节点映射保留

`smartAskSession.js` 已经有节点映射：

```text
request.received -> 开始执行任务
agent1.* -> 理解问题口径
pipeline.dataset_context -> 加载数据集上下文
agent2.* -> 生成 SQL
agent3.* -> 校验 SQL
datasource.execute_sql / pipeline.execute_sql -> 执行 SQL
agent4.* / pipeline.agent4_result -> 生成经营分析结论
request.error -> 执行异常
```

这套映射要保留。

建议把右侧区展示名称统一成：

| 当前节点 | 建议展示 |
|---|---|
| 开始执行任务 | 接收问题 |
| 理解问题口径 | 意图识别 |
| 加载数据集上下文 | 准备数据集 |
| 生成 SQL | 生成 SQL |
| 校验 SQL | 复核 SQL |
| 执行 SQL | 执行查询 |
| 生成经营分析结论 | 生成报告 |
| 执行异常 | 执行异常 |

涉及文件：

```text
frontend/src/state/smartAskSession.js
frontend/src/components/smartask/LiveExecutionFeed.vue
frontend/src/components/smartask/LogTimeline.vue
```

### 7.3 右侧区默认展开规则

建议：

1. 正在执行的节点默认展开。
2. 失败节点默认展开。
3. 最近完成的节点默认展开一项。
4. 已完成且没有 SQL、表格、错误的节点默认收起。
5. 报告生成完成后，全部技术节点默认收起，只保留摘要状态。

当前落点：

```text
SmartAsk.vue
-> logOpen
-> toggleLog
-> session.state.logs
```

### 7.4 去重规则

当前已经有去重函数：

```text
LogTimeline.vue
-> uniqueDisplayLines
-> isRedundantRealtimePrintLine
smartAskSession.js
-> uniqueLiveLines
```

继续优化即可。

建议新增或强化：

1. 同一节点相同 `summary` 不重复显示。
2. `生成说明` 只显示一次。
3. `模型正在实时返回真实内容` 不显示给用户。
4. SQL 片段在中间区只显示“正在生成 SQL”，完整 SQL 只放右侧。
5. Agent4 分析预览如果右侧报告已存在，不再在 `LogTimeline` 重复铺开。

涉及文件：

```text
frontend/src/state/smartAskSession.js
frontend/src/components/smartask/LogTimeline.vue
frontend/src/views/SmartAsk.vue
```

### 7.5 错误展示

失败时右侧区应结构化显示：

```text
失败节点：执行查询
错误原因：SELECT DISTINCT 查询中 ORDER BY 表达式必须出现在查询列表中
建议动作：重新生成 SQL，或检查排序字段是否进入 SELECT
```

当前后端 trace 已能给出：

```text
stage
status
error
traceback
```

建议前端做结构化转换，不要只显示原始异常。

涉及文件：

```text
frontend/src/state/smartAskSession.js
frontend/src/components/smartask/LogTimeline.vue
```

后端可选增强：

```text
backend/four_agent_ask.py
```

当执行 SQL 报错时，在 trace 里额外带：

```json
{
  "error_type": "sql_execution_error",
  "failed_stage": "execute_sql",
  "suggestion": "请重新生成 SQL 或检查 ORDER BY 字段"
}
```

### 7.6 右侧报告预览处理

当前右侧区会在 `hasSideReport` 时展示报告预览。

不建议删除，因为这是当前项目已有功能。

建议优化：

1. 右侧报告预览改成“报告快捷预览”。
2. 默认放在执行轨迹后面。
3. 执行中不展示报告预览。
4. 完成后展示摘要和“全屏报告”入口。
5. 如果右侧空间不足，报告预览默认折叠。

涉及文件：

```text
frontend/src/views/SmartAsk.vue
```

## 8. 后端契约增量优化

### 8.1 不新增新模板系统

报告模板配置当前已经承担这些职责：

1. 指标字段。
2. 层级字段。
3. 条线字段。
4. SQL 标准输出列。
5. 分析维度。
6. 阈值。
7. Agent4 指导。

这部分够用了。不要让你再人工维护“单一问数模板、对比模板、排名模板”的大量文案。

### 8.2 report_spec_builder 继续做页面结构

`report_spec_builder.py` 应继续负责：

1. 判断分析模式。
2. 找到 focus node。
3. 识别比较对象。
4. 生成 KPI。
5. 生成 accordions。
6. 生成 charts。
7. 生成 provenance。

建议增量补充：

| 字段 | 用途 | 前端消费 |
|---|---|---|
| `uiSummary.headline` | 中间区一句话结论 | `ResultDigestCard` |
| `uiSummary.supportLines` | 支撑点 | `ResultDigestCard` |
| `displayPolicy.entityDisplayLimit` | 多主体展示上限 | `ResultDigestCard` |
| `displayPolicy.defaultDrillOpen` | 默认是否展开下钻 | `SmartAsk.vue` |
| `entityCards` | 主体卡片 | `ResultDigestCard` 和报告 KPI |
| `drillHint` | 下钻提示 | 中间区和报告组织卡 |

这些字段只做展示辅助，老字段继续保留。

### 8.3 Agent4 的边界

Agent4 不应该决定前端具体布局。

Agent4 应该输出：

1. 核心结论。
2. 风险解释。
3. 亮点原因。
4. 管理建议。

页面结构由：

```text
report_spec_builder.py + report_config + 前端组件
```

共同决定。

这样可以减少硬编码，也减少你维护报告模板的压力。

## 10. 场景验收标准

### 10.1 单一分公司

问题：

```text
东部分公司业绩怎么样
```

必须满足：

1. 第一屏先回答东部分公司整体业绩。
2. KPI 展示任务、开单、达成率、缺口。
3. 显示下级代表处数量。
4. 代表处优先于业务员展示。
5. 业务员只作为代表处后的证据层。

### 10.2 两个分公司对比

问题：

```text
东部和西部业绩对比
```

必须满足：

1. 清楚说明谁领先。
2. 显示达成率差距。
3. 两个主体颜色不同。
4. 东部和西部都有 KPI。
5. 两个主体都能展开代表处。

### 10.3 三大业务部

问题：

```text
三大业务部业绩怎么样
```

必须满足：

1. 识别并展示 3 个业务部。
2. 不只拿两个业务部做对比。
3. 中间区和全屏报告主体一致。
4. 结论覆盖领先者、落后者和差距。

### 10.4 九大分公司

问题：

```text
9 大分公司达成率排名
```

必须满足：

1. 第一屏不铺 9 个主体 KPI。
2. 展示最高、最低、整体、风险数量。
3. 完整列表进入表格或全屏报告。
4. 下钻入口仍可用。

### 10.5 SQL 报错

问题：

```text
东西部业绩对比
```

如果 SQL 出错，必须满足：

1. 中间区显示执行失败摘要。
2. 右侧区定位失败节点。
3. 展示错误原因。
4. 展示建议动作。
5. 可以重新问。

## 11. 测试清单

每次改完至少跑：

建议手工测试问题：

东部分公司业绩怎么样

5. 下钻入口是否明显但不突兀。
6. 复制、修改、重新问是否正常。
7. 报错是否结构化展示。

## 14. 最终目标

优化后，用户的感受应该是：

1. 中间区像经营分析顾问，直接回答问题。
2. 右侧区像执行审计台，清楚说明过程。
3. 全屏报告像正式交付物，适合汇报。
4. 下钻能力明显，但不打扰主结论。
5. 单一、对比、排名、多主体问题都有稳定展示规则。
6. 维护重点集中在数据集 DDL、字段解释、指标口径、层级口径和少量报告配置，不需要每个问题单独写模板。

当前项目已经有骨架，下一步不是重建，而是把这套骨架磨顺。
