# 稳定版本节点与用户机更新手册

> 用途：记录智能问数项目的稳定 commit 节点，方便以后给用户机锁定稳定版本、回退版本或继续升级。

## 一、当前结论

现在可以先不创建稳定分支，只记录 commit 短哈希也没问题。

但是一旦要给用户机长期使用某个稳定版本，建议把该 commit 建成远端分支，例如：

- `stable-user1`：双流程大改动之前的稳定版。
- `stable-user2`：双流程问数控制器及报告优化完成版。

原因很简单：  
commit 哈希适合“定位历史节点”，分支适合“用户机长期拉取和维护”。

## 二、稳定节点 1：双流程大改动前版本

### 1. 版本说明

这个节点的状态是：

- 飞书 JSON 解析已经完成。
- 准备开始双流程问数大改动。
- 如果后续双流程问数、进阶问数、报告优化改错，可以恢复到这个版本。
- 注意：恢复到这个版本后，后续报告优化、进阶问数功能可能会丢失。

### 2. 提交信息

```bash
git commit -m "chore: update smartask LIn 13"
```

### 3. 查询短哈希

```bash
git log --oneline --all --grep="chore: update smartask LIn 13"
```

当前记录：

```bash
f2d0b22 chore: update smartask LIn 13
```

### 4. 查看完整 commit id

```bash
git rev-parse f2d0b22
```

### 5. 后续如需创建稳定分支

建议在本地开发机上执行：

```bash
git checkout -b stable-user1 f2d0b22
git push -u gitee stable-user1
```

如果本地当前有未提交改动，先不要直接切分支。先确认：

```bash
git status
```

如果当前改动还要保留，先提交或暂存，再创建稳定分支。

## 三、稳定节点 2：双流程问数控制器及报告优化完成版

### 1. 版本说明

这个节点的状态是：

- 双流程问数控制器已经完成。
- 报告优化已经完成。
- 修复了旧 Python 环境下密钥预检查报错问题。
- 适合作为用户机中阶稳定版。

### 2. 提交信息

```bash
fix: skip host secret precheck on old python
```

### 3. 查询短哈希

```bash
git log --oneline --all --grep="fix: skip host secret precheck on old python"
```

当前记录：

```bash
6246230 fix: skip host secret precheck on old python
```

### 4. 查看完整 commit id

```bash
git rev-parse 6246230
```

### 5. 后续如需创建稳定分支

建议在本地开发机上执行：

```bash
git checkout -b stable-user2 6246230
git push -u gitee stable-user2
```

## 四、用户机更新方式

### 1. 最推荐方式

用户机上直接用 `update.sh` 指定稳定分支：

```bash
cd /opt/smartask/smartask
bash update.sh --branch stable-user2
```

如果要使用第一个稳定版：

```bash
cd /opt/smartask/smartask
bash update.sh --branch stable-user1
```

### 2. 为什么必须加 `--branch`

当前 `update.sh` 默认分支是：

```bash
docker-setup
```

所以如果只执行：

```bash
bash update.sh
```

脚本可能会回到默认的 `docker-setup` 分支，而不是你想给用户机使用的 `stable-user1` 或 `stable-user2`。

正确方式：

```bash
bash update.sh --branch stable-user2
```

## 五、用户机手动拉取方式

如果不想直接交给 `update.sh` 切分支，也可以手动执行：

```bash
cd /opt/smartask/smartask
git fetch origin
git checkout stable-user2
git pull --ff-only origin stable-user2
bash update.sh --branch stable-user2
```

如果是 `stable-user1`：

```bash
cd /opt/smartask/smartask
git fetch origin
git checkout stable-user1
git pull --ff-only origin stable-user1
bash update.sh --branch stable-user1
```

## 六、关于远端名：gitee 和 origin

本地开发机通常使用：

```bash
git push -u gitee stable-user2
```

宝塔用户机通常使用：

```bash
git fetch origin
git pull --ff-only origin stable-user2
```

如果不确定当前机器远端叫什么，执行：

```bash
git remote -v
```

如果宝塔机器上没有 `gitee` 这个远端，执行下面命令会失败：

```bash
git pull --ff-only gitee docker-setup
```

这种情况下应使用宝塔机器实际存在的远端名，通常是 `origin`。

## 七、关于宝塔上的配置会不会丢

正常使用 `update.sh` 时，会尽量保护线上运行态配置，包括：

- 数据源配置。
- 数据集配置。
- 权限配置。
- 功能开关。
- 组织树。
- 问数历史。
- 报告历史。
- 进阶能力配置。
- 密钥主文件。

生产环境不要轻易使用：

```bash
bash update.sh --skip-backup
```

推荐始终使用：

```bash
bash update.sh --branch stable-user2
```

## 八、如果宝塔机器上有本地修改

先看状态：

```bash
cd /opt/smartask/smartask
git status
```

如果只是控制台里的数据集、权限、运行态配置，一般交给 `update.sh` 保护即可。

如果是直接改了代码文件，建议先备份或提交，避免切换分支时产生冲突。

可选的手动保护方式：

```bash
git stash push -u -m "backup before switch stable branch"
```

但如果使用项目自己的 `update.sh`，一般优先走：

```bash
bash update.sh --branch stable-user2
```

## 九、常见问题

### 1. 现在不创建分支行不行？

可以。

现在只是记录稳定节点，记录 commit 短哈希就够了。

但如果要让用户机长期停在某个版本，建议创建远端稳定分支。

### 2. 短哈希能不能用？

可以。

例如：

```bash
git checkout -b stable-user2 6246230
```

只要该短哈希在当前仓库中唯一即可。

### 3. 用户机能不能直接 checkout commit？

能，但不推荐长期这样做。

例如：

```bash
git checkout 6246230
```

这样会进入 detached HEAD 状态，不适合作为用户机长期维护方式。

更推荐：

```bash
git checkout stable-user2
bash update.sh --branch stable-user2
```

### 4. 如果用户机已经是其他版本，还能更新到 stable-user2 吗？

可以。

推荐直接执行：

```bash
cd /opt/smartask/smartask
bash update.sh --branch stable-user2
```

脚本会按指定分支更新，而不是默认回到 `docker-setup`。

### 5. 如果后续继续升级进阶问数，会影响 stable-user2 吗？

不会。

只要 `stable-user2` 分支不继续合并新代码，它就会停在 `6246230` 对应的稳定状态。

新的进阶问数升级可以继续在 `docker-setup` 或新的开发分支上推进。
