# 智能问数项目完整改造计划

更新时间：2026-04-28

适用范围：当前仓库完整项目，包括前端 UI、后端问数链路、数据集元数据、老板确认机制、结果报告链路。

---

## 1. 改造目标

这次改造不应该只是“修几个样式、补几个接口”，而应该围绕两个核心目标展开：

1. UI 目标  
把系统从“功能很多但表达杂乱”升级成“层级清晰、结果聚焦、品牌统一、操作稳定”的企业级问数工作台。

2. 问数目标  
把系统从“能问、能出结果”升级成“可控、可解释、可回归、可持续增强”的智能问数平台。

一句话总结：

- UI 要从“组件堆叠”升级成“信息架构”
- 问数链路要从“单文件强驱动”升级成“模块化可增强”

---

## 2. 当前项目诊断

下面这部分不是泛泛而谈，而是基于当前代码结构得出的判断。

## 2.1 UI 现状诊断

### 2.1.1 问数页承担过多职责

文件：`frontend/src/views/SmartAsk.vue`

当前这个页面同时承担了：

- 会话头部
- 消息列表
- 执行轨迹
- 确认卡
- 结果摘要
- 图表预览
- 报告摘要
- 右侧详情面板
- 图表弹窗
- 报告弹窗
- 打印与下载逻辑
- 大量样式定义

问题：

- 页面级文件过大
- 布局问题和业务逻辑高度耦合
- 任何一处样式调整都容易波及结果链
- 结果区宽度、卡片宽度、弹窗逻辑容易互相打架

结论：

`SmartAsk.vue` 现在已经不是“页面容器”，而是“页面 + 编排 + 结果渲染中心”，需要拆分。

### 2.1.2 结果链表达重复

当前问数结果在中间区和右侧区有明显重复：

- 中间区有 `ResultDigestCard`
- 中间区有图表预览
- 中间区有 `ReportSummary`
- 中间区有 `ArtifactStrip`
- 中间区有 `AgentDoneBar`
- 右侧详情区又有完整执行结果汇总
- 还有全屏报告弹窗

问题：

- 一条结果出现太多层次相近的卡
- 用户很难理解“我该看哪张卡”
- 中间区和右侧区边界不清
- 数据摘要、报告摘要、产物摘要存在重复表达

结论：

结果区需要重构成：

- 一张主结果卡
- 一段下钻区
- 一个报告入口

而不是现在这种“同一件事拆成 4 到 6 张卡”。

### 2.1.3 宽度控制去中心化

这次你让我反复改“右边线不齐”，本质原因已经暴露出来了：

- 父级容器控一层宽度
- 子组件再各自控一层 `max-width`
- 单图、双图、右侧详情展开、隐藏详情都有各自规则

涉及文件包括：

- `SmartAsk.vue`
- `ResultDigestCard.vue`
- `ReportSummary.vue`
- `ArtifactStrip.vue`
- `AgentDoneBar.vue`
- `PlanCard.vue`
- `ThinkingCard.vue`
- `LiveExecutionFeed.vue`

问题：

- 宽度规范没有统一源头
- 页面容易出现“左对齐但右边线参差不齐”
- 局部视觉问题会变成全链路样式问题

结论：

后续必须建立统一布局约束：

- 页面级控宽
- 结果链级控宽
- 卡片组件默认 `width: 100%`

不能再让卡片组件自行声明私有 `max-width`。

### 2.1.4 命名层级混乱

当前 UI 命名之前出现过：

- 左上品牌名
- 左侧菜单名
- 页面标题
- 中间会话头

都叫“智能问数”或近似表达。

问题：

- 用户很难建立“品牌 / 模块 / 页面 / 当前会话”的层级关系
- 品牌感弱
- 导航感弱

结论：

命名系统必须分层：

- 品牌名
- 产品模块名
- 页面名
- 会话名

### 2.1.5 视觉语言尚未统一

当前 UI 已经做了不少优化，但仍有几个典型问题：

- 中英文混排风格不统一
- 卡片边框、阴影、圆角规则缺少设计 token 级统一
- 状态徽标样式分散
- 顶部、侧栏、问数主区不是同一套视觉系统

结论：

需要建立一套问数页专属 design tokens 和卡片规范。

## 2.2 问数链路现状诊断

### 2.2.1 主服务过于集中

文件：`backend/four_agent_ask.py`

当前它同时承担：

- Agent1 路由
- 数据集评分
- 老板确认
- 确认 session 管理
- Golden SQL 直出策略
- Rule-based SQL
- 模型调用
- SQL 执行编排
- 结果合并
- 报告文本输出
- trace

问题：

- 单文件职责过多
- 很难做模块级测试
- 后续接 LangChain / MCP 时插点不清晰
- 商用事业部专用逻辑和通用逻辑混在一起

结论：

这是全项目最优先需要模块化拆分的后端文件。

### 2.2.2 Agent1 路由是“混合体”

当前 `route_with_agent1()` 同时混合了：

- 数据集打分
- LLM route
- 画像确认
- 二义性确认
- Golden SQL 直出判断

问题：

- 路由策略不可解释性偏强
- 增加一个新规则很容易影响整体
- 组织类问题和通用问题没有完全分层

结论：

需要拆成明确阶段：

1. 候选集召回
2. 候选集评分
3. 专项规则命中
4. LLM 意图判定
5. 是否确认
6. 是否直出

### 2.2.3 商用事业部逻辑过于硬编码

当前 `four_agent_ask.py` 里已经存在：

- 商用事业部画像
- 商用事业部确认逻辑
- 商用事业部 Rule-based SQL

问题：

- 专项逻辑能跑，但泛化能力弱
- 每多一个事业部，后端代码就更重
- 长期会变成“数据集专项堆积场”

结论：

商用事业部应该成为“模板化专项能力”的第一个样板，而不是长期硬编码特例。

### 2.2.4 老板确认 session 是内存态

从 `four_agent_ask.py` 可以看到：

- `_pending_confirmations` 是进程内字典
- 依赖 TTL 清理

问题：

- 服务重启即丢失
- 多实例部署无法共享
- 不利于后续长流程确认

结论：

如果老板确认要继续做深，session 需要落到可持久层。

### 2.2.5 结果报告仍以 Markdown 分析为主

虽然前端已经有：

- 摘要卡
- 图表卡
- 报告卡
- 弹窗卡

但后端结果主载体仍然是：

- `analysis`
- `dataset_results[].analysis`

问题：

- 结构化程度不够
- 不利于按“当前节点 / 下钻层级 / KPI / 建议”精确渲染
- 报告 UI 容易被 Markdown 牵着走

结论：

需要从“文本为主”升级成“结构化报告为主，Markdown 为辅”。

### 2.2.6 当前缺少稳定回归评估

当前仓库里有不少测试脚本，但没有形成完整问数评估体系。

问题：

- 调整路由、确认、SQL 生成后，很难快速判断是否退化
- UI 改造和问数改造很容易交叉影响

结论：

后续必须建立：

- 组织类问数回归集
- 指标类问数回归集
- SQL 成功率评估
- 路由命中率评估

### 2.2.7 老旧接口与新链路并存

当前后端既有：

- `/api/chat`
- `/api/chat/generate-sql`

又有：

- `/api/smart-chat`
- `/api/smart-chat/confirm-by-boss`

问题：

- 产品边界不够清晰
- 维护成本增加
- 前端若继续扩展，容易混用旧接口

结论：

后续要明确：

- 哪些接口保留
- 哪些接口兼容期保留
- 哪些接口进入废弃计划

## 3. 总体改造原则

## 原则 1：不推倒重来

保留当前四 Agent 主链路，逐步模块化，不做一次性重写。

## 原则 2：先统一结构，再优化效果

先解决：

- 组件层级
- 布局规则
- 数据结构
- 模块边界

再做：

- 提示词优化
- 图表美化
- 品牌升级

## 原则 3：商用事业部先打样

所有组织类问数增强，先在：

- 商用事业部
- 4 大分公司
- 分公司
- 代表处
- 业务部

这条链上打穿。

## 原则 4：所有改造必须可回归

每一阶段都要有：

- 用例
- 指标
- trace
- 回滚点

## 4. UI 改造计划

## 阶段 UI-1：建立统一布局体系

目标：

- 彻底解决问数页宽度、对齐、卡片层级混乱问题

任务：

1. 在 `SmartAsk.vue` 建立统一布局变量
   - `--sa-thread-width`
   - `--sa-thread-width-expanded`
   - `--sa-panel-width`

2. 所有结果组件只保留：
   - `width: 100%`
   - 不再声明私有 `max-width`

3. 将以下组件的宽度规范统一托管给父级：
   - `LiveExecutionFeed.vue`
   - `PlanCard.vue`
   - `ThinkingCard.vue`
   - `ResultDigestCard.vue`
   - `ReportSummary.vue`
   - `ArtifactStrip.vue`
   - `AgentDoneBar.vue`

4. 对“中间主链”和“右侧详情链”建立明确边界

交付：

- 问数页布局规范文档
- 宽度与间距 token

## 阶段 UI-2：重构结果链

目标：

- 把当前结果区从“多卡并列”改成“单主卡 + 下钻区 + 报告入口”

新结构建议：

1. 主结果卡
   - 当前问题标题
   - 数据集口径
   - 关键 KPI
   - 风险提示
   - 下一步动作

2. 图表/下钻区
   - 当前节点 KPI 图
   - 下级节点图
   - 需要时展开表格

3. 报告入口
   - 一张报告卡
   - 一个 PDF 导出入口
   - 一个全屏查看入口

4. 执行完成提示
   - 并入主卡底部，不再单独一张

要删除或合并的重复表达：

- `AgentDoneBar` 独立存在形式
- `ArtifactStrip` 与 `ReportSummary` 的重复产物表达
- 过于碎片的“结果已完成 / 正在整理 / 已生成”多卡

## 阶段 UI-3：重构右侧详情面板

目标：

- 右侧面板从“另一个结果页”变成“诊断与追踪面板”

调整方向：

- 右侧只放：
  - 执行节点
  - SQL
  - 中间表格
  - 模型决策
  - trace

- 中间主区才放：
  - 最终结果
  - 图表
  - 报告

结果：

- 用户会更清楚“中间看结果，右边看过程”

## 阶段 UI-4：统一品牌与命名系统

目标：

- 明确品牌层级，不再多个位置同名

建议命名体系：

- 品牌：`Data Agent`
- 平台副标题：`经营分析工作台`
- 页面：`经营问答台`
- 会话：`当前会话`
- 功能入口：`问数会话`

同时统一：

- 中文优先还是中英混排优先
- badge 的命名口径
- 顶部标题、副标题、模块名的语义边界

## 阶段 UI-5：建立 SmartAsk 设计系统

目标：

- 从“页面修修补补”升级到“可持续样式系统”

建议建设：

- `frontend/src/styles/smartask-tokens.css`
- `frontend/src/styles/smartask-layout.css`
- `frontend/src/styles/smartask-card.css`
- `frontend/src/styles/smartask-state.css`

设计 token 建议包括：

- 间距
- 圆角
- 阴影
- 边框
- 状态色
- 字号层级

## 5. 问数能力改造计划

## 阶段 QA-1：拆分四 Agent 主文件

目标：

- 把 `four_agent_ask.py` 从“大总管”拆成模块化能力

建议拆分文件：

- `backend/agent1_router.py`
- `backend/confirmation_service.py`
- `backend/context_builder.py`
- `backend/sql_generation_service.py`
- `backend/sql_review_service.py`
- `backend/report_builder.py`
- `backend/trace_service.py`

保留：

- `four_agent_ask.py` 作为编排层

## 阶段 QA-2：建立统一上下文包

目标：

- 不再让模型直接吃零散上下文，改为标准化输入

建议统一结构：

```json
{
  "question": "",
  "route": {},
  "dataset_context": {},
  "org_context": {},
  "golden_sql_context": [],
  "retrieved_context": [],
  "confirmation_context": {},
  "execution_policy": {}
}
```

好处：

- 便于后面接 LangChain
- 便于后面接 MCP
- 便于 trace 与调试

## 阶段 QA-3：建立组织类问数专项引擎

目标：

- 不再把商用事业部逻辑散落在主文件里

建议新增：

- `backend/org_query_engine.py`
- `backend/org_profile_service.py`

能力包括：

- 当前组织节点识别
- 上下级层级识别
- 默认下钻深度判断
- 集合口径识别
- 同层对比与汇总

专项先覆盖：

- 事业部
- 分公司
- 代表处
- 业务部
- 业务员

## 阶段 QA-4：结构化报告替代 Markdown 主导

目标：

- 让前端按结构化结果渲染，而不是被 Markdown 牵着走

建议新增后端输出：

```json
{
  "smart_report": {
    "report_type": "hierarchy_insight",
    "current_node": {},
    "metrics": [],
    "charts": [],
    "sections": [],
    "suggestions": [],
    "risk_flags": []
  }
}
```

第一批前端只消费：

- 当前节点
- KPI 卡
- 下级节点列表
- 建议

Markdown 继续保留，但退居为：

- 归档文本
- PDF 文本源

## 阶段 QA-5：把老板确认升级成正式能力

目标：

- 让确认机制从“临时会话控制”升级成正式流程能力

建议：

1. session 落地存储
   - Redis 或 PostgreSQL

2. 确认对象标准化
   - `confirmation_type`
   - `resolved_members`
   - `resolved_dimension`
   - `scope_mode`

3. 增加确认历史
   - 哪次问题
   - 何时确认
   - 确认了什么

4. 前端确认卡统一模板化

## 阶段 QA-6：建立问数评估体系

目标：

- 让改造不靠感觉判断

新增建议：

- `backend/evals/route_eval.json`
- `backend/evals/org_eval.json`
- `backend/evals/sql_eval.json`
- `backend/evals/run_eval.py`

评估指标：

- 数据集路由命中率
- 组织层级识别命中率
- SQL 首次执行成功率
- SQL 修复成功率
- 需要确认的准确率
- 最终答案可用率

## 阶段 QA-7：LangChain 与 MCP 接入

这部分不再重复展开，建议按已有文档推进：

- [LangChain_MCP_问数增强行动计划.md](/d:/万物云/万物云/AI培训/智能问数流程/火山引擎/智能问数项目_v20260330_004926(3)-566fee42a29e/智能问数项目_v20260330_004926/docs/LangChain_MCP_问数增强行动计划.md)

当前项目最合理的顺序仍然是：

1. 先统一上下文包
2. 再加 LangChain 检索与工具层
3. 再加 metadata / org profile MCP

## 9. 验收指标
