# SmartAsk 歧义澄清（Question Clarification）设计方案

> 背景：真实用户提问存在错字（"完成最好不分公司"）、口语极性混乱（"最不好的，还有第二不好的分公司"）、表达残缺。
> 目标：在**必要的时刻**弹出选项式确认，把模糊问题规范化后再执行——提升大模型理解精度，同时控制打扰率。
> 日期：2026-08-27 | 状态：待评审（未动代码）

---

## 一、核心原则

1. **只补歧义，不做问答**——弹的是选择题，不是开放输入框（除非用户点"都不对"）
2. **复用现有确认基础设施**——`requires_confirmation` / `confirmation_options` / `confirm-by-boss` / SSE confirm 帧全部已有，零新通道
3. **三个触发口各自独立、可配置、可关闭**——feature_flag 控制，误弹可一键回退
4. **澄清后的 effective_question 必须是完整规范中文句**——下游 SQL 引擎和 Agent4 拿到的永远是干净输入

## 二、三级触发器（按打扰成本从低到高排序落地）

### T1 极性冲突检测（P0 · 纯规则 · 零 LLM 成本）

**触发条件**（正则即可判定）：
- 同一问题同时出现正向极性词（最好/最高/领先/前三）**与**负向极性词（最差/最低/垫底/落后/最不好/不好）
- 或者负向极性词 + 数量序数混用（"最不好的，还有第二不好的"→ 无法确定取 1 个还是 2 个）

**用户看到的选项**（以"最不好的，还有第二不好的分公司"为例）：
```
您想看的范围是？
 ○ 达成率最差的 1 家分公司（垫底榜首位）
 ○ 达成率最差的 2 家分公司（末两位）
 ○ 全部分公司达成率排名（从低到高）   ← 兜底推荐项
```

**实现要点**：复用现有 `query_intent.direction(asc/desc)` + `top_n`，选项即预填参数组合，点击 = 直接改写 intent 参数，不走二次 LLM。

### T2 实体低置信纠错（P1 · 纯规则）

**触发条件**：
- `get_close_matches(cutoff=0.72)` 当前是硬过滤，改为**灰区间 [0.60, 0.85) 时弹选项**（≥0.85 直接静默采用，≤0.60 按既有 N5 规则提示未找到）

**用户看到的选项**（以"看下河北那边的业绩" 错输成"华北分公司"为例）：
```
没有找到「华北分公司」，您是不是想查？
 ○ 北部分公司
 ○ 西北分公司
 ○ 都不是（重新描述）
```

**实现要点**：候选列表就是 close_matches Top3，数据现成；新增 option_type=`entity_correction`。

### T3 残缺句/缺主语补全（P2 · 轻量 LLM 参与）

**触发条件**：
- 剥离口语前后缀后主体为空或仅剩层级泛称（"情况怎么样""完成最好不分公司"剥离后主体只剩"分公司"且无法定位具体对象集合）
- Agent1 解析 subject_name 为空（现有 fallback 分支已有此信号）

**用户看到的选项**（以"完成最好不分公司情况"为例）：
```
您想了解哪个范围的业绩？
 ○ 四家分公司的完成排名（最好→最差）
 ○ 最完成好的 1 家分公司详情（含下级城市公司）
 ○ 最差的一家分公司（含下级）
```
**实现要点**：选项文案由 Agent1 在既有调用中顺带产出（system_prompt 追加字段），**不增加 LLM 调用次数**。

## 三、打扰控制（回应"不是每个都要"）

| 闸门 | 规则 |
|------|------|
| 白名单直通 | golden sql 命中 / alias 精确命中 / intent 单一明确（如"业务代表 Top10"）→ 永不弹 |
| 一次会话一次 | 同一会话同一歧义类型只弹一次，用户的选择进短期记忆，后续同类问题沿用 |
| 澄清策略可配 | feature_flag 增加 `smart_clarify_enabled` + `min_entity_clarify_score`，超管可随时全局关闭 |
| 默认倾向直接回答 | 规则判定必须"≥2 种合理解释"才弹；只有一种合理解释时按解释执行并在结果尾部附一句"如果您想要的是XX，请这样问" |

## 四、数据流（与现有架构衔接）

```
用户问题
  → Agent1 主体解析（已有）
  → 【新增】clarifier 三级触发检查（T1 规则 / T2 规则 / T3 依赖 Agent1 输出）
      ├─ 无歧义 → 走原流程
      └─ 有歧义 → 构造 confirmation_options（扩展 option_type + 重写后的问题文本）
            → requires_confirmation=true 走现有 SSE confirm 帧
            → 用户点选 → effective_question=选项预置的重写句 → 回归原流程
```

改动面估计：`four_agent_ask.py` 新增 clarifier 模块约 200 行（建议外移至 `ask_engine_clarify.py`，符合 AGENTS.md 公约"不在上帝文件增类"）；前端确认 UI 内联在 `SmartAsk.vue`（无独立确认卡组件，约 10 处 `requires_confirmation` 触点），新增 option_type 需在此加样式分支。【v4 核实修正：原文误写为 ResultDigestCard】

## 五、验证计划

1. **回归基线**：confirmed_behaviors_baseline.md 全量重跑，确认白名单直通不被误弹
2. **专项用例集**：收集 15~20 条真实脏问题（含你给的三个例子）建 clarify_cases.json，断言"该弹的弹、不该弹的不弹"
3. **打扰率指标**：上线后统计 澄清弹窗次数/总问数次数，目标 <8%，超过则收紧触发阈值

## 六、明确不做的事

- ❌ 不做开放式自由输入框澄清（保持选择题交互一致性）
- ❌ 不改 SQL 引擎和 Agent4 提示词（澄清层输出的已是规范问题）
- ❌ 不为错字单独建拼音纠音表（T2 的模糊匹配 + T1/T3 已覆盖主要场景，避免过度工程）

## 七、评审修订 v2（2026-08-27 专家评审补丁，必读）

> 首版评审发现 4 个会翻车的坑 + 1 个与现有确认机制的消费细节。此节为修订结论，覆盖前文。

### 7.1 与现有机制会不会冲突（代码核实结论）

核实了 `four_agent_ask.py` 的确认链路（14 处 `requires_confirmation`、5 种 `option_type/confirmation_type`、`confirm_by_boss` 消费逻辑）：

| 现有确认类型 | 触发点 | 与澄清方案关系 |
|-------------|--------|--------------|
| `dataset_disambiguation` | 数据集歧义 | **互斥不同层**，无撞车 |
| `member_set_confirmation` | 成员集合确认 | 互斥 |
| `organization_tree_scope` | 组织树范围 | 互斥 |
| `dataset_similarity_confirm` | 相似数据集 | 互斥 |

**结论：不会撞车，但要加两处处理：**

1. **消费逻辑扩展（必做）**：`confirm_by_boss` 当前消费逻辑**围绕"选数据集 + 主体替换"硬编码**（认 `dataset_ids` / `resolved_subject_name`），而澄清方案要落地的是**意图参数**（`top_n`/`direction`）和**实体名替换**。新增 option_type 时必须在 `_normalize_confirmation_options` 和 `confirm_by_boss` 各加对应分支——即"复用 UI 通道，扩展消费分支"，不是零改动套用。
2. **触发优先级仲裁（必做）**：同一问题可能同时命中多类歧义，需定死优先级，**一次只弹一种**：
   `数据集歧义 > 组织范围 > 排名范围(T1) > 实体纠错(T2) > 残缺补全(T3)`
   （先解决"查哪个数据集"这种大问题，再解决"取几名"这种小问题）

### 7.2 坑1 修复：comparison 意图整体豁免 T1

`comparison`/`对比`/`比较`/`vs`/`和…比` 是正常查询，正则看到"最好"+"最差"不能弹。**T1 触发前先判 intent，comparison 直接放行**。

### 7.3 坑2 修复：T1 改名 + 定位收紧

- T1 改名 **`ranking_scope`（排名范围歧义）**，只解决一件事："取了 1 个还是 N 个 / 升序还是降序"
- 触发条件收紧为：**ranking 意图下**，出现「负向极性 + 序数/数量词混用」或「正负极性同现且无 comparison 信号」
- "完成最好不分公司"这类错字残缺 → **归 T3**，不指望 T1 正则

### 7.4 坑3 修复：T2 弃用 difflib，改拼音编辑距离

`get_close_matches`（SequenceMatcher）对中文词相似度不可靠。T2 落地前：
1. 先建 20 条真实错字样例，实测 difflib ratio 分布（预计灰区会空）
2. 改用**拼音全拼编辑距离**（或 pypinyin + Levenshtein）做候选召回，再用别名索引精排

### 7.5 坑4 修复：clarifier 必须 fail-open

**硬原则（写入代码契约）**：clarifier 任何异常/规则未命中/LLM 超时 → **静默放行原问题**，绝不因澄清层 bug 卡住主流程。澄清层是"增强"，不是"闸门"。

### 7.6 其他修订

- **确认通道继承技术债**：复用 confirm 通道 = 继承"`_pending_confirmations` 单 worker 内存 dict"的丢状态缺陷，开发环境无碍，文档注明
- **8% 打扰率去掉硬目标**：先上线采集 2 周真实歧义占比，再定阈值
- **"第二不好的"文案**：选项必须写死"末两位（第 1、第 2）"，消除二次歧义

### 7.7 修订后落地顺序（不变，但每步带前置门禁）

| 阶段 | 内容 | 前置门禁 |
|------|------|---------|
| P0 | ranking_scope（T1） | ①comparison 豁免 ②fail-open ③消费分支扩展 |
| P1 | 实体纠错（T2） | ④拼音编辑距离实测通过 |
| P2 | 残缺补全（T3） | ⑤选项文案策略打磨 |

## 八、架构修订 v3（2026-08-27 二次评审：方向性升级，覆盖前文形态选择）

> v2 解决的是"规则细节不翻车"，v3 解决的是**方向问题**：三层拦截式确认天花板低、打扰率高、与现有确认机制叠加风险大。
> v3 核心变更：**拦截式 → 非阻断"先答后纠"为主；三层规则 → LLM 守门员 + 书架接地 + 代码校验层**。

### 8.1 主形态变更：非阻断"先答后纠"（answer-then-correct）

**行业借鉴结论**（按借鉴价值排序）：

| 借鉴对象 | 抄什么 | 对应需求 |
|---------|--------|---------|
| Google "Did you mean" | 事后非阻断纠正条 + "已按 X 理解"明示声明 + ✕ 撤销 | 意图歧义（最好/最不好）——一期主形态 |
| Perplexity / ChatGPT | 假设声明前置 + 回答下方挂追问 chips | 纠错与引导下钻合并成一个组件 |
| ThoughtSpot Sage | 输入框实时补全/错字下划线，错字在**输入阶段**消化 | T2 实体纠错——二期前移形态 |
| Power BI Q&A | "Showing: top5 + 分公司 + 达成率"理解转述条，逐 token 可点改 | 远期参考，暂不做 |

**交互形态**（替代 v1/v2 的弹窗确认，作为默认路径）：

```
已按「达成率最好的 1 家分公司」理解 ✕ ｜ 换个问法：[最不好的] [前 3 名] [各分公司对比]
```

- 按最可能理解**直接回答**，结果上方挂非阻断纠正条
- 猜对（大多数）→ 用户零成本；猜错 → 点一下换理解，**复用已查数据只换排序/范围**，响应秒出
- 纠正条不进 `_pending_confirmations`、不设 `requires_confirmation`、无 session——**与确认机制代码路径零交集**，只是结果里多带 `alternative_interpretations` 字段
- 拦截式选项确认只保留给**一种情况**：完全无法理解、任何解释都拿不出结果时才弹

### 8.2 与现有确认机制的关系（v3 终版结论）

形态不冲突（零交集，见上），但要守三条仲裁规则：

| 场景 | 走哪个 | 理由 |
|------|--------|------|
| 数据集/组织范围歧义（现有 4 类） | **照旧阻断式确认** | 答错了是查错表的事故，有代价 |
| 意图拿不准但能给出一个合理解释 | **先答 + 纠正条** | 答错了重排即可，无代价 |
| 完全无法理解 | 阻断式澄清选项（复用确认 UI） | 此时才新增 option_type |

补充两条防打扰规则：
1. ~~本轮已走过阻断式确认的问题，不再挂纠正条~~ **【v4 已修订，见 9.1-B2】**：该规则会静默吞掉意图歧义（用户只钦定了数据集）。改为——阻断确认只钦定其自身维度（去哪查），其余维度（怎么理解）的歧义仍允许挂纠正条；同轮阻断+非阻断可共存，但必须落在不同维度
2. 纠正条点击后走新 ask 时，已确认的数据集/主体经 `conversation_session_id` 链路带过去，**不得触发第二轮数据集确认**

原则一句话：**确认机制管"去哪查"（阻断），纠正条管"怎么理解"（非阻断），按维度解耦、可共存不重叠。【v4 修订】**

### 8.3 书架接地（grounding）：对着数据集内容做题，不靠 LLM 猜

守门员的所有输出必须从"书架"选，书架即项目现有资产：

| 书架资产 | 位置 | 用途 |
|---------|------|------|
| 节点索引（83 节点/166 别名，ds=2） | `config/dataset_node_index.json` | 实体纠错的封闭词表 |
| 报告配置 metrics/levels/analysisDimensions | `bs_dataset_report_config` | 纠正条选项的实例化来源 |
| businessContext / LLD | 配置 + context | 守门员判断"问题靠不靠谱"的口径依据 |
| 查询历史 | `config/query_history.json` | 冷启动语料 + 影子模式验证集 |

四根支柱：

1. **实体纠错代码做**：错字用编辑距离在别名表里匹配（封闭词表，正确答案一定在其中）。LLM 只判断"像不像实体名"，匹配归代码。v2 的拼音方案降级为兜底。
2. **选项从书架实例化**：层级←levels、指标←metrics、业务线←analysisDimensions。选项永远指向真实可查的东西，杜绝 LLM 编出数据集里不存在的字段（如"按回款率排名"）。
3. **守门员 prompt 带书架摘要**：businessContext + 指标清单 + 别名表喂给小模型，判断"数据集里没这口径"时给出精准纠正而非硬答。
4. **代码校验层（书架否决权）**：LLM 输出的实体名回查节点索引、指标名回查 metrics 清单，**查不到直接丢弃该条理解 → fail-open**。LLM 负责生成候选，书架负责否决——猜错了也漏不到用户面前。

### 8.4 三层规则收敛为一层 LLM 守门员

v1/v2 的 T1 正则 + T2 拼音 + T3 残缺检测（三套机制三份维护）收敛为：

- **一次小模型调用**（非主模型，便宜快），输入"原句 + 书架摘要"，强制结构化输出：
  `{"理解": ..., "置信度": 0~1, "备选理解": [...], "疑似错字纠正": ...}`
- 置信度高 → 直接过（零打扰）；中 → 先答后纠条；低 → 阻断式选项
- 规则只保留硬规则做前置短路：comparison 豁免、golden sql/别名精确命中直通
- P0/P1/P2 三期合并，实测成本从"校准三套规则"变"调一个 prompt"

### 8.5 会话记忆继承

澄清结果进短期记忆：用户对"最不好的分公司"确认过方向后，追问"那代表处呢"**继承方向（最差）不再重问**。挂在现有 `short_term_memory.resolve_followup` 链路。

### 8.6 落地顺序（v3 终版）

| 阶段 | 内容 | 前置门禁 |
|------|------|---------|
| **P-1 影子模式** | 只加日志：记录"若守门员在场会拦吗/理由/置信度"，用户不可见。跑 1~2 周 | 无代码风险，先行 |
| **P-1 产出** | 真实错字分布、误拦率、澄清频次——**用证据决定做不做、阈值定多少** | 用 query_history.json 离线先过一遍 |
| **P0** | LLM 守门员 + 书架接地 + 代码校验层 + 先答后纠条（一期上线） | 影子数据支持；fail-open 契约；comparison 豁免 |
| **P1** | 输入框实时补全/错字下划线（ThoughtSpot 式前移） | P0 稳定后 |
| 不变项 | 拦截式澄清只留"完全无法理解"；会话记忆继承 | 随 P0 一起 |

### 8.7 v3 覆盖声明

- v1 的 T1/T2/T3 三级触发器、v2 的拼音编辑距离实测门禁 → **被 8.4 收敛替代**，不再独立实施
- v2 的 fail-open 契约、comparison 豁免、确认通道技术债注明 → **保留有效**
- v2 的触发优先级仲裁 → 被 8.2 的"阻断/非阻断分流"替代（维度更准确：按"答错有无代价"分，不按触发器类型分）

### 9.1 落地硬约束（B1-B5，来自专家团评审）

#### B1 守门员接入红线（最高优先级 · 架构师+Reviewer 交叉确认）

**守门员绝不能复用现有 `_chat` 链路**（`_candidate_llm_configs` 会把 6 个激活模型当备胎，单模型 timeout=180s，失败还按白名单轮询切换，最坏 N×180s）。

| 项 | 约束 | 代码依据 |
|----|------|---------|
| 客户端 | 新建独立 `GatekeeperLLMClient`，**禁复用 `_chat`/候选链** | `llm_client.py:59-91` |
| 模型 | `gatekeeper_model_id` 锁**单个快模型**（不从激活列表轮询） | 实测 GLM-5.1 要 64s，不能用 |
| 超时 | `timeout=3~5s`（绝不继承 180s） | `llm_client.py:151` |
| 重试 | **零重试**（失败不重切模型） | `llm_client.py:166-179` |
| 输出 | `stream=False`，`max_tokens≤256`，仅 `{action, confidence, reason}` | 结构化 |
| 共享状态 | **禁共享** `_preferred_model_id` 单例（并发污染实锤，独立构造 client） | 审计 A-03 / `llm_client.py:37` |
| 接入点 | `ask():9341` 之后、`9347` Agent1 之前；串行靠硬超时压到 ~2s | `four_agent_ask.py:9341-9352` |
| 职责边界 | 只做**置信度分流**，不产出 rewritten_question，**不与 Agent1 争主体解析** | `four_agent_ask.py:7823+` |
| fail-open | 复用 `_chat_json` 的 fallback 模式：异常/超时/JSON 解析失败 → 静默放行原问题 | `llm_client.py:244-268` |

**三条红线**：禁复用 `_chat`/候选链 ｜ 禁共享 `_preferred_model_id` 单例 ｜ 必须 fail-open。

#### B2 多歧义仲裁矩阵（Reviewer 发现 v3 丢失约束，必补）

8.2 只按"答错代价"分阻断/非阻断，**丢失了"阻断+非阻断同命中"的处理**。反例："华北最差的两家分公司"同时命中数据集歧义（阻断）+实体错字+排名范围（非阻断）。

**修订**：阻断确认与纠正条**按维度解耦，允许共存**——

```
阻断确认管"去哪查"（数据集/组织范围）
纠正条管"怎么理解"（意图/实体/排序）
同轮可同时存在，但必须落在不同维度
```

**必须删除/修正 8.2 防打扰规则 1**："本轮走过阻断确认不再挂纠正条"会**静默吞掉意图歧义**（用户只钦定了数据集，意图歧义没被确认也没提示）。改为：**阻断确认只钦定其自身维度，其余维度的歧义仍允许挂纠正条**。

#### 阶段 P-1：影子模式（零代码风险，先行 1~2 周）

**数据源结论（QA 核实）**：`config/query_history.json` 存在但**陈旧**（最近 2026-03-30，159 条/34 去重问题）且**无 intent/答案字段**——离线预跑**只能验证"守门员会不会触发"，无法验证"拦得对不对"（无 ground truth）**。影子模式**必须在线采集新数据**，离线预跑降级为冒烟检查。

**影子日志**：写 `config/shadow_gatekeeper_log.jsonl`，挂载点 `backend/disambiguation/`。
