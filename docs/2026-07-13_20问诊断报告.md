## 3. 核心结论

当前单数据集的常规 Overview、明确节点下钻、TopN 和歧义确认已具备基础稳定性；主要故障集中在四条共享链路：

1. **跨数据集对比不可用。** 基础流程可能只取得单边数据；涉及电商时还会因空维度画像直接崩溃。
2. **组织范围不是统一的树查询。** 直接父级、目标层级和命中实体由不同分支拼装，导致“山东下级”扩大成全局、“消费者下城市公司”又被缩成根节点。
3. **指标与层级约束可能在改写中丢失。** 毛利率被替换成达成率，代表处排名混入业务部。
4. **结果和文案缺少最终契约校验。** 第 4 问描述与实际数据范围相反，第 20 问描述了并不存在的确认状态。

## 4. 根治建议

### P0：统一问数执行契约

在进入 SQL 生成前形成不可变的结构化契约：`dataset_ids`、`metric`、`scope_node_ids`、`target_level`、`operation`、`direction`、`limit`、`comparison_mode`。LLM 负责语义拆解，节点索引负责实体候选，规则只做冲突校验；后续步骤不得静默替换已确认字段。

### P0：修复维度画像空值和跨数据集聚合

- `backend/four_agent_ask.py:7441` 在 `profile` 可能为 `None` 时调用 `profile.get`，必须统一使用空画像对象或显式能力判断。
- 多数据集对比必须先为每个数据集生成同粒度汇总行，再进行合并；任一侧失败应整体返回结构化错误，不能删除错误后展示单边比较。
- “电商事业部的业绩”和“电商事业部整体业绩”语义不同，跨数据集比较必须选择后者对应的根汇总口径，不能拿第一个业务部代替事业部。

### P1：组织树范围统一为节点 ID 运算

节点索引应生成稳定 `node_id`、`parent_id`、`dataset_id`、`level` 和祖先路径。范围查询统一表达为“命中节点的自身/直接子级/全部后代 + 目标层级”，禁止再通过名称和单层 `上级名称` 临时拼接。城市分公司、代表处、服务商等未来层级因此可以自然扩展。

### P1：执行后进行结果契约校验

在生成报告前校验：返回数据集是否齐全、层级是否唯一符合、TopN 行数是否正确、实体是否位于范围内、指标列是否存在、重复业务键是否归并。校验失败应重试或返回明确错误，不能让模型根据错误结果继续生成肯定结论。

### P2：扩展指标注册表和回归基线

指标不应只围绕任务额、开单额、达成率和差额。为每个数据集维护可迁移的指标元数据、别名、聚合方式和单位，例如电商毛利率。将本报告 20 问固化为真实数据库语义回归，至少断言路由、确认状态、数据集、目标层级、行数、排序、关键节点和错误为空。

## 5. 验收标准

- 20 问全部不崩溃，跨数据集问题不允许单边成功伪装成完整结果。
- 第 3、4、7、11 问严格满足组织范围、层级、指标和数量约束。
- 第 12 问业务承接人按稳定业务键无重复。
- 第 13、16、17、18、19 问使用同粒度汇总值完成对比。
- 报告文案中的数据集、范围、行数和确认状态必须可由结构化结果直接验证。

## 7. 补充诊断结论

### 7.1 层级复制是当前混乱的重要来源

`backend/dataset_copilot/syyb_rule_generator.py:139-140` 明确把业务部叶子节点额外映射为“分公司”，目的是让公共办公业务部参与“分公司”筛选。这个兼容逻辑使同一个实体同时拥有业务部和分公司身份，直接导致第 29 问层级错误，也解释了代表处结果中反复混入“餐饮”。应保留真实组织层级，通过“条线类型”或可选业务集合表达横向比较，不能篡改层级。

### 7.2 排名分支存在确定性代码错误

`backend/four_agent_ask.py:6609-6627` 只在 `configured_limit > 0 or asks_extreme_rank` 时赋值 `rank_where`，但随后无条件使用。普通“某分公司代表处排名”不满足该条件，因此第 36 问必然崩溃。这不是模型随机性问题。

### 7.3 年份目前是硬编码而非受控能力

消费者和电商 SQL 多处固定 `当前年 = '2026'`，例如 `backend/four_agent_ask.py:7435`、`:7755`。用户指定 2023 年时没有能力校验或冲突提示，报告模型又复用了用户年份，最终把 2026 数据包装成 2023 结论。时间维度必须进入 Query Contract，并在数据集不支持时明确拒绝。

### 7.4 结构化结果与报告使用了不同数据视图

第 28、31、38、39、48 问均出现“报告能回答，但结果行数没有按问题收敛”。这会导致左侧卡片、历史恢复、导出和报告正文各自显示不同范围。SQL 执行结果必须是唯一事实源，报告不得依赖额外的隐式切片。

### 7.5 规则兜底正在覆盖真实语义

Top0 被替换为 Top3、多条件筛选丢失第二条件、不存在实体被近似改写，说明当前规则倾向于“尽量给结果”，而非验证 LLM 拆解是否忠实。建议调整为：LLM 产出完整结构化意图；规则校验非法值、冲突和能力边界；发现冲突时确认或拒绝，不能静默改写。

## 8. 更新后的发布门槛

- 将累计 50 问全部固化为结构化语义回归，严格通过率达到 100% 后再视为基线稳定。
- 任何显式年份、指标、层级、实体、阈值和 TopN 都必须出现在 Query Contract 和最终 SQL 中。
- SQL 结果、左侧卡片、历史恢复、导出和报告正文必须共享同一结果集与单位转换。
- 不存在实体、非法 TopN、不支持指标和不支持年份必须确认或明确报错，禁止自动伪造可执行语义。
- 同数据集及跨数据集对比不得依赖可选维度画像存在，任一子查询失败时整体不得生成成功结论。
