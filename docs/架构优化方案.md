# SmartAsk 代码库架构分析与优化方案（v4）

> 修订日期：2026-08-02
> 目标：保持 `FourAgentAskService` 公共签名和现有业务调用点不变，分阶段把生产 Python 文件收敛到单文件不超过 300 行。
> 当前门禁：P1-4 已通过独立 QA（133 passed + 29 subtests，新镜像构建通过）；P1-5 待 v4 架构裁决完成后启动。

---

## 一、约束与现状

### 1.1 硬约束

1. `FourAgentAskService` 类名、模块导入路径、公共方法签名不变。
2. 依赖只能从装配层流向业务层、领域层和基础设施层，禁止下层反向导入 facade。
3. 生产 Python 文件按非空非注释代码统计不超过 300 行；入口和 facade 只装配、校验与委托。
4. 每个阶段先补 characterization test，再迁移，再做独立 QA；最多 3 轮，超过即回滚到阶段起点。
5. 不改 prompt、SQL 语义、API、配置格式、错误吞并策略和 OpenAI 请求参数。
6. 前端功能图标统一锁定 `@element-plus/icons-vue@2.3.2` SVG 图标库，沿用当前 `frontend/package.json` 依赖；不得混用其他图标库或用 emoji 代替功能图标。
7. 禁止紫色到粉色渐变设计方案。本次后端重构不包含视觉改版。

### 1.2 现状诊断

`backend/four_agent_ask.py` 当前约 1 万行，`FourAgentAskService` 同时承担追踪、模型访问、意图识别、路由、SQL 生成、报告、执行编排和会话入口职责。当前超过 100 行的方法有 15 个，其中必须优先消除的 8 个主干方法如下。

| 方法 | 当前约行数 | 最终职责位置 |
|------|-----------:|--------------|
| `_build_rule_based_sql` | 1040 | `sql/rule_router.py` + 数据集 builder |
| `_resolve_query_intent` | 777 | `intent/resolver.py` + 规则模块 |
| `_build_consumer_business_sql` | 667 | `sql/consumer/` |
| `route_with_agent1` | 667 | `routing/service.py` + 评分模块 |
| `_run_pipeline` | 610 | `orchestration/pipeline.py` + stage 模块 |
| `_build_layered_management_report` | 576 | `reporting/layered_report.py` + section 模块 |
| `_build_ecommerce_sql` | 405 | `sql/ecommerce/` |
| `ask` | 375 | `orchestration/request_service.py` |

其余超过 100 行的方法同样不能原样装入单个聚合文件：`_select_sql_strategy`、`_chat`、`_build_dataset_profile_confirmation`、`_detect_ambiguity`、`_agent2_generate_sql`、`_agent3_review`、`confirm_by_boss`。它们分别进入下文对应职责模块，并以 300 行门禁约束最终文件。

## 二、方案选择

### 2.1 方案对比

评分采用 1 到 5 分，5 分最好；权重优先顺序为行为兼容、测试可证、维护成本、交付速度。

| 方案 | 行为兼容 | 测试可证 | 维护成本 | 交付速度 | 结论 |
|------|---------:|---------:|---------:|---------:|------|
| 多继承 Mixin | 3 | 2 | 2 | 3 | MRO 与隐式状态依赖增加，不采用 |
| 一次性重写 | 1 | 2 | 4 | 1 | 变更面过大，无法形成可靠回滚点，不采用 |
| 分阶段组合、委托、领域分包 | 5 | 5 | 5 | 4 | 采用 |

采用第三种方案，但“调用点零改动”只用于迁移期兼容，不代表长期保留巨型类。最终 `four_agent_ask.py` 是不超过 300 行的兼容 facade；业务实现必须迁出。

### 2.2 分层架构

```text
Controllers / ask_flow
          |
          v
four_agent_ask.py: FourAgentAskService facade
          |
          +---------------------+
          |                     |
          v                     v
orchestration services      tracing / llm infrastructure
          |
          v
intent / routing / sql / reporting domain services
          |
          v
repository / config / OpenAI / filesystem
```

禁止 `intent`、`routing`、`sql`、`reporting`、`tracing`、`llm` 反向导入 `four_agent_ask.py`。跨域交互使用构造参数传入的窄接口或纯值对象，不传入整个 `FourAgentAskService`。

## 三、P1-5 TraceLogger 修正版边界

### 3.1 真实方法与状态

`TraceLogger` 接管 6 个活跃方法：`_new_trace`、`_write_trace_line`、`_emit_live_trace`、`_append_trace`、`_append_llm_delta`、`_flush_trace`。

`_build_trace_snapshot` 已经由 `FourAgentAskService` 委托到 `ask_engine_utils`，真实实现属于 `ask_engine_display.py` 的纯函数，继续留在工具层。`_build_trace_logger` 创建的 `logging.Logger` 和 `_trace_logger` 当前仅初始化、没有实际消费点；为保持初始化副作用，P1-5 暂留 facade，后续单独清理，不把它们计作活跃 TraceLogger 状态。

`TraceLogger` 初始化只持有 `file_path`。`_new_trace` 还需要当次 `model` 和 `base_url`，由 facade 读取 LLM 兼容属性后按值传入；禁止 `TraceLogger` 读取 LLMClient 或 facade。

### 3.2 调用点口径

`four_agent_ask.py` 文件内 AST Call 节点共 95 个。

| 方法 | 调用点 | 迁移处理 |
|------|-------:|----------|
| `_append_trace` | 65 | facade 同名薄委托，原调用点不改 |
| `_flush_trace` | 16 | facade 同名薄委托，原调用点不改 |
| `_append_llm_delta` | 4 | facade 同名薄委托，原调用点不改 |
| `_emit_live_trace` | 3 | facade 同名薄委托，原调用点不改 |
| `_write_trace_line` | 2 | facade 同名薄委托，原调用点不改 |
| `_new_trace` | 2 | facade 同名薄委托，原调用点不改 |
| `_build_trace_snapshot` | 2 | 保持工具层委托，不迁 TraceLogger |
| `_build_trace_logger` | 1 | 保留 legacy 初始化，不迁 TraceLogger |

结论：95 个文件内调用中，92 个由 TraceLogger 委托覆盖，2 个留在工具层，1 个保留 legacy 初始化。仓库级另有 `smartask_basic/service.py` 对 `_write_trace_line` 的 1 个调用，也由 facade 兼容入口保持零改动。

### 3.3 最小委托接口与测试

facade 必须保留原签名的 `_new_trace`、`_write_trace_line`、`_append_trace`、`_append_llm_delta`、`_flush_trace`；为私有兼容同时保留 `_emit_live_trace`。测试必须覆盖 event/summary JSONL 字段与顺序、`_live_callback` 不落盘、result 包含规则、content/reasoning delta、空 trace no-op、callback 和文件异常的既有吞并行为，以及 `BasicAskService.write_controller_probe`。

## 四、P1-6 LLMClient 修正版边界

### 4.1 真实方法与状态

`LLMClient` 接管 7 个活跃方法：`_load_llm`、`_activate_llm`、`_candidate_llm_configs`、`_chat`、`_chat_json`、`_stream_delta_value_to_text`、`_extract_stream_delta`。

`_get_agent_prompt` 依赖 `agent_registry`，属于 prompt 业务域，留在 facade，后续迁到 `prompt/service.py`。`_should_retry_with_another_model` 已委托 `ask_engine_utils` 纯函数，留在工具层。

LLMClient 是 `_llm_client`、`_llm_model`、`_preferred_model_id` 的单一状态所有者。facade 保留三个同名双向 property：getter 读取 collaborator，setter 写入 collaborator。不得在 facade 和 LLMClient 各保存一份状态。`ask()` 继续在原时点写 `_preferred_model_id = model_id`，不改变当前请求行为。

### 4.2 调用点口径

以 `git HEAD:backend/four_agent_ask.py` 为不可变基线，严格筛选 `ast.Call(func=ast.Attribute(value=Name(id="self"), attr=<指定方法>))`，文件内指定 LLM 相关调用节点共 23 个。

| 方法 | 调用点 | 迁移处理 |
|------|-------:|----------|
| `_chat_json` | 9 | facade 同名薄委托，原调用点不改 |
| `_get_agent_prompt` | 6 | 留 prompt 域，原调用点不改 |
| `_load_llm` | 2 | facade 同名薄委托，原调用点不改 |
| `_activate_llm` | 2 | facade 同名薄委托，原调用点不改 |
| `_should_retry_with_another_model` | 1 | 留工具层，原业务调用点不改 |
| `_chat` | 2 | facade 同名薄委托，原调用点不改 |
| `_candidate_llm_configs` | 1 | facade 同名薄委托，原调用点不改 |

结论：HEAD 基线的 23 个 `self` 调用中，16 个由 LLMClient 高层委托覆盖（`_chat_json` 9 + `_load_llm` 2 + `_activate_llm` 2 + `_chat` 2 + `_candidate_llm_configs` 1），6 个 `_get_agent_prompt` 调用留 prompt 域，1 个 `_should_retry_with_another_model` 业务调用留工具层。流式解析 helper 随 `_chat` 迁入 LLMClient 内部，避免 LLMClient 反向依赖 facade。

旧版 24 来自混用未提交工作树和任意 receiver 的 `ast.Attribute` Call 统计：既计算业务侧 `self._should_retry_with_another_model(...)`，又计算薄包装内部 `ask_engine_utils._should_retry_with_another_model(...)`，将同一职责链重复计数。迁移后新增的 `self._llm_component().<method>(...)` 属于组件包装调用，必须附带 `HEAD` 或具体提交号、receiver 形态和阶段信息单独报告，不得与 HEAD 的 `self.<method>(...)` 行为调用基线相加。

### 4.3 最小委托接口与测试

facade 保留原签名的 `_chat`、`_chat_json`、`_load_llm`、`_activate_llm`、`_candidate_llm_configs`，并保留三个兼容 property。测试必须覆盖候选模型排序、inactive 排除、signature 去重、secret decode、无模型错误、content/reasoning 流式合并、末尾 delta flush、可重试切换、不可重试抛错、JSON 成功与 fallback、Trace request/response/retry/error/parsed/fallback 形状，以及现有 `service._chat_json = fake` 的 monkeypatch 能力。


## 六、迁移顺序、轮次和回滚点

每个阶段最多 3 轮：第 1 轮补基线测试并提取；第 2 轮修复非预期差异；第 3 轮仅允许修复门禁失败。第 3 轮仍失败时，整阶段回滚到阶段起点，不带失败实现进入下一阶段。每阶段一个独立提交或等价可恢复点，禁止把多个阶段混在同一回滚单元。

| 阶段 | 前置 | 迁移内容 | 必过证据 | 回滚点 |
|------|------|----------|----------|--------|
| P1-4 | P0 | 纯工具职责分包 | AST 定义/调用清单、全量测试 | P0 完成提交 |
| P1-5 | P1-4 QA pass | TraceLogger 6 方法，92 个调用走委托 | AST 95 口径、JSONL golden、callback/IO 异常、全量测试 | P1-4 pass 提交 |
| P1-6 | P1-5 pass | LLMClient 7 方法、3 个兼容 property | HEAD 严格 self.Attribute AST 23=16+6+1；组件包装调用按 provenance 单列；LLM fake stream/retry/fallback、trace 契约、全量测试 | P1-5 pass 提交 |
| P2-A | P1-6 pass | intent resolver 与 routing 分包 | AST 方法唯一性、intent/route golden、Agent1 fake LLM、全量测试 | P1-6 pass 提交 |
| P2-B | P2-A pass | 三套 SQL builder 与 strategy 分包 | AST 依赖方向、SQL diff 100%、错误分支、全量测试 | P2-A pass 提交 |
| P2-C | P2-B pass | reporting 与 Agent2/Agent3 分包 | AST 调用清单、report JSON、Agent2/3 fake LLM、trace 顺序、全量测试 | P2-B pass 提交 |
| P3-A | P2-C pass | pipeline、ask、confirm 编排迁出 | 公共签名快照、端到端问句、确认流、权限/空问题异常、trace golden | P2-C pass 提交 |
| P3-B | P3-A pass | facade 清理和 legacy 状态清理 | 所有生产 Python 文件 <=300、import smoke、依赖 DAG 扫描、全量测试 | P3-A pass 提交 |

阶段内一旦出现 SQL 语义差异、Trace 字段/顺序差异、LLM 候选顺序差异、公共签名差异或新反向依赖，立即停止后续迁移。差异没有被现行需求明确批准时，不得用更新 golden 的方式掩盖回归。

## 七、统一门禁

### 7.1 AST 与依赖门禁

1. 提取方法在生产代码中只有一个真实实现；facade 只能是薄委托。
2. 迁移前后调用点清单有机器统计，未列入规格的调用点变化为失败。
3. `smartask_engine` 子包不得 import `four_agent_ask`。
4. facade 公共方法通过 `inspect.signature` 快照比对。
5. 单文件非空非注释代码不超过 300 行；入口和 facade 不包含业务分支、SQL 模板或 prompt 正文。

### 7.2 行为契约门禁

| 契约 | 必测成功路径 | 必测失败或边界路径 |
|------|--------------|--------------------|
| SQL | 三数据集固定问句 SQL diff 100% | 空条件、只读校验、未知数据集 |
| Trace | event、delta、summary JSONL golden | 空 trace、callback 抛错、文件写失败 |
| LLM | Agent1/2/3 fake stream，候选顺序 | 无配置、retry、非 retry、JSON fallback |
| 路由 | dataset、entity、confidence 一致 | 多候选、权限过滤、确认分支 |
| API | `ask`、`confirm_by_boss` 签名和返回结构 | 空问题、schema 不可用、确认过期 |

现有“20 问句 18/20”不能作为重构通过标准。重构必须做到基线通过项零回归；已知失败项必须固定记录，不能新增失败。

### 7.3 文档与 P0 门禁

1. 架构和 API 文档不使用 emoji 作为图标。
2. Spec 锁定单一 SVG 图标库，不混用。
3. 不出现紫色到粉色渐变建议。
4. 所有文案必须具体指向真实职责、接口或验收证据。
5. 规格与实现冲突时先修规格，再改代码。

---

## 八、明确不做

1. 不在 P1-5/P1-6 修复 singleton `_preferred_model_id` 的并发串扰；另立行为变更任务。
2. 不改变 trace 顶层 model/base_url 的记录时点。
3. 不借重构删除 legacy logger、修改异常吞并、调整超时或改 OpenAI 参数。
4. 不改 SQL、prompt、API、配置格式、权限语义和会话语义。
5. 不在同一阶段同时迁移两个尚无独立 characterization test 的领域。
6. 不接受“类内注释分区”作为最终架构结果；最终门禁是 facade 和所有生产 Python 文件均不超过 300 行。

---

## 九、成本与交付判断

这是既有 AI 应用的高风险结构重构，不是新功能开发。Trace/LLM 两阶段各按 1 到 2 个工程日估算；intent/routing、SQL、report/review、orchestration/facade 四组按每组 2 到 4 个工程日估算，另计独立 QA。总计约 10 到 20 个工程日，取决于当前回归基线稳定度和 SQL golden 覆盖率。此估算不包含并发模型选择修复、新增业务测试数据或产品行为变更。
