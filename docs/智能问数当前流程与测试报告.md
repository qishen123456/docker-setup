# 智能问数当前流程与测试报告

生成时间：2026-05-11

## 1. 本次开发目标

本次不是重写问数主链路，而是在现有链路上增加“可观测”和“可校验”能力：

```text
1. 明确每次问数走的是哪种报告场景
2. 明确报告契约是否被使用
3. 明确报告契约缺失了什么
4. 前端把本次链路展示出来
5. 保持原有 SQL 生成、执行、报告渲染结构不被推翻
```

## 2. 当前完整执行流程

当前智能问数链路如下：

```text
用户输入问题
  ↓
Agent1：数据集路由与口径判断
  - 判断命中哪个数据集
  - 判断是否需要用户确认
  - 输出 decision / refined_query / dataset_ids
  ↓
加载数据集上下文
  - DDL
  - 数据字典
  - LLD
  - Golden SQL
  - Agent Prompt
  - 报告契约 report_config
  ↓
Agent2：SQL 生成
  - 使用 DDL / 字典 / LLD / Golden SQL
  - 使用报告契约约束标准输出列
  - 生成只读 SQL
  ↓
Agent3：SQL 复核
  - 校验只读
  - 校验语法和口径风险
  - 必要时修正 final_sql
  ↓
执行 SQL
  - 使用当前数据集绑定的数据源
  - 返回 columns / rows / row_count
  ↓
report_spec_builder：报告结构生成
  - 构建动态父子树
  - 识别场景 detail / comparative / ranking / diagnostic
  - 根据报告契约识别指标、层级、风险规则
  - 生成 report_spec
  ↓
Agent4：业务解读
  - 基于 SQL 结果输出文字结论和建议
  ↓
前端 SmartAsk / ResultDigestCard
  - 根据 report_spec.layoutTemplate 渲染报告
  - 显示本次链路调试信息
```

## 3. 报告场景识别机制

新增模块：

```text
backend/report_scene_registry.py
```

当前支持四类场景：

| 场景 key | 中文名 | layoutTemplate | 触发方式 |
|---|---|---|---|
| detail | 单体/常规分析 | detail | 未触发特殊场景，或命中单个可下钻主体 |
| comparative | 对比分析 | comparison | 命中多个主体，或问题包含“对比/比较/分别/差异”等 |
| ranking | 排名分析 | ranking | 问题包含“排名/最高/最低/Top/最好/最差”等 |
| diagnostic | 诊断/风险分析 | detail | 问题包含“为什么/原因/异常/风险/缺口”等 |

场景识别结果会进入：

```text
report_spec.debug.scene
dataset_result.report_debug.scene
```

## 4. 报告契约校验机制

新增模块：

```text
backend/report_contract_health.py
```

它不会阻断问数，只负责告诉系统和用户：

```text
报告契约有没有被用上
标准列是否出现在 SQL 结果中
指标列是否出现在 SQL 结果中
是否配置了 analysisDimensions
是否配置了 signalRules
是否有缺失项
健康度是多少
```

返回结构示例：

```json
{
  "used": true,
  "score": 100,
  "level": "healthy",
  "missing": [],
  "warnings": [],
  "standard_columns_detected": ["节点名称", "上级名称", "层级", "达成率"],
  "metric_count": 4,
  "analysis_dimension_count": 1,
  "signal_rule_count": 2
}
```

### 6.6 报告契约生效测试

测试目标：

```text
确认报告契约不是只显示健康度，而是真的参与 report_spec 生成。
```

测试方法：

```text
使用一套非默认字段名和非默认指标名：
- nameColumn: 对象名称
- parentColumn: 父对象
- levelColumn: 对象层级
- trackColumn: 业务线
- metrics: 目标额 / 成交额 / 完成率 / 待完成额
```

测试问题：

```text
华东区和华西区对比
```

通过标准：

```text
1. 场景识别为 comparative
2. layoutTemplate 为 comparison
3. 契约健康度为 100
4. 标准列命中包含：对象名称、父对象、对象层级、业务线
5. 指标列命中包含：目标额、成交额、完成率、待完成额
6. KPI 标签使用契约指标，而不是默认的任务/开单/达成率/缺口
```

## 7. 本次没有做的高风险测试

本次没有自动调用真实大模型完整问数接口。

原因：

```text
1. 真实问数会消耗模型额度
2. 输出受模型实时结果影响，不适合作为稳定自动测试
3. 本次改动重点是场景注册、契约校验和前端展示，不改变 Agent2/Agent4 主提示词行为
```

但本次已经验证：

```text
1. 前端可构建
2. 后端可运行
3. 场景识别可用
4. report_spec 可生成
5. debug 信息可返回
6. 契约缺失可识别
```

## 9. 现在整个流程如何维护

你以后维护数据集时，建议顺序：

```text
1. 数据集管理：维护 DDL
2. 数据集管理：智能补齐
   - 字段字典
   - Agent2
   - Agent4
   - Golden SQL
3. SQL 测试：验证真实数据
4. 报告契约配置：维护或智能补齐
   - 标准输出列
   - 核心指标
   - 分析层级
   - 风险规则
5. 智能问数：提问验证
6. 看结论卡片下方链路信息
   - 场景是否正确
   - 契约健康是否正常
   - 是否用了数据集配置
```

## 10. 判断是否正常的标准

一个问题跑完后，建议看这几项：

```text
场景：是否符合问题意图
界面：是否匹配场景
报告契约：最好是“数据集配置”，如果是“默认配置”说明这个数据集没单独维护
契约健康：建议 85 分以上
缺失项：最好为空
```

示例：

```text
东部和西部对比
场景：对比分析
界面：comparison
报告契约：数据集配置
契约健康：100/100
缺失：无
```

这表示链路比较健康。
