# 智能问数自适应分析与动态报告升级方案

> 文档版本：v1.0  
> 日期：2026-05-01  
> 目标：在现有数据集配置、四 Agent 问数链路和报表配置能力之上，升级为可维护、可扩展、可由大模型辅助生成数据集资料的自适应分析系统。

## 1. 方案结论

当前项目已经不是“没有数据集配置”的阶段。系统已经具备数据集管理、LLD、DDL、Golden SQL、常见问题、四个 Agent Prompt、报告配置和四 Agent 问数链路。下一步不应该再把某个事业部、某个组织层级、某几个字段写死到 Agent4 或前端里，而应该引入一套稳定的中间协议。

我建议采用以下架构：

```text
数据集配置中心
  -> Dataset Profile 数据集画像
  -> Metric Schema 指标语义
  -> Hierarchy Schema 层级语义
  -> Prompt Pack 四 Agent 提示词包
  -> Golden SQL / FAQ / DDL / LLD

用户问题
  -> Agent1 数据集路由与歧义确认
  -> Agent2 生成结构化 SQL
  -> Agent3 安全与口径校验
  -> 执行 SQL
  -> Result Profiler 结果剖析
  -> Analysis Mode Detector 分析模式识别
  -> Report Planner 生成 ReportSpec
  -> Agent4 只负责基于 ReportSpec 写管理层洞察
  -> 前端按 ReportSpec 动态渲染左文右图
  -> PDF 导出同源生成
```

最关键的设计判断是：不要让 Agent4 直接决定报表结构，也不要让前端直接从原始 SQL 行里猜业务含义。Agent4 容易编造，前端硬猜不可维护。更优做法是由确定性程序先生成 `ReportSpec`，Agent4 只在这个结构内补充洞察、风险和建议。

## 2. 对参考方案的取舍

你给的参考方案里有一个方向是对的：要解耦硬编码报表，不能继续写死“区域条线、行业条线、代表处、业务员”。但是它把所有数据集强行约束成 4 个标准列：`node_name`、`parent_name`、`metric_value`、`metric_rate`，这个方案不够稳。

原因如下：

1. 真实经营分析通常不只有一个 `metric_value`。你已经提到目标、完成、完成率、人数、剩余任务等多个指标。如果只保留一个核心值，右侧 KPI 和组合图会丢语义。
2. 多体对比不能只靠父子树表达。比如“东分和南分对比”，它是并列主体对比，不应该被合并成一个根节点。
3. 异构组织架构需要保留层级语义。分公司、代表处、业务员是一种结构；业务部、业务员是另一种结构。只靠 `parent_name` 可以建树，但不足以判断“这层代表什么”。
4. 不同数据集的指标口径不同。消费者事业部和商用事业部可能都有“完成率”，但计算口径、风险阈值、组织层级、默认拆解维度不同。
5. 你已经有数据集配置中心，不需要通过“极简 4 列”绕开配置。更合理的是把配置能力升级成数据集画像，让配置为动态分析服务。

因此，我建议采用“标准协议 + 可配置映射”的中间路线：

- SQL 可以输出标准字段，也可以输出业务字段。
- 后端 Result Profiler 负责把 SQL 结果标准化为 ReportNode 和 ReportMetric。
- 数据集配置里明确哪些列是节点名、父节点、层级、指标、对比主体、时间、组织口径。
- 前端永远只消费标准化后的 ReportSpec，不直接绑定原始 SQL 字段。

这比“强制所有 SQL 只输出 4 列”更可维护，也更适合你后续多数据集、多部门、多组织结构的目标。

## 3. 当前系统应该保留的能力

以下能力已经有基础，不建议推倒重来：

1. 保留四 Agent 主链路。
   - Agent1：数据集路由、歧义确认。
   - Agent2：基于数据集上下文生成 SQL。
   - Agent3：SQL 安全、语法、口径复核。
   - Agent4：业务分析。

2. 保留数据集配置入口。
   - LLD、DDL、Golden SQL、常见问题、四 Agent Prompt 都是有价值资产。
   - 后续应该增强“自动生成”和“自动质检”，而不是让用户手写更多复杂配置。

3. 保留报告配置表。
   - 当前已有 `bs_dataset_report_config` 和相关 API。
   - 后续应该把它升级为 Dataset Report Profile，而不是另起一套孤立配置。

4. 保留前端 SmartAsk 主界面。
   - 当前左侧问答、右侧渲染的产品方向是对的。
   - 后续重点是把右侧从硬编码报表升级为 DynamicReportView。

## 4. 新增核心概念

### 4.1 Dataset Profile 数据集画像

Dataset Profile 是每个数据集的“机器可读说明书”。它不是替代 LLD，而是把 LLD、DDL、Golden SQL、业务字段、层级结构、指标口径浓缩成系统可执行的配置。

建议结构：

```json
{
  "dataset_id": 1,
  "dataset_name": "商用事业部经营数据集",
  "business_domain": "商用事业部经营分析",
  "entity_aliases": ["商用", "商用事业部", "商用线"],
  "ambiguity_terms": ["东部分公司", "南部分公司", "业务部"],
  "default_time_policy": {
    "type": "current_year",
    "description": "默认分析当前年度"
  },
  "hierarchy_schema": {
    "node_column": "节点名称",
    "parent_column": "上级名称",
    "level_column": "层级",
    "track_column": "条线",
    "known_paths": [
      ["事业部", "分公司", "代表处", "业务员"],
      ["事业部", "业务部", "业务员"]
    ]
  },
  "metric_schema": [
    {
      "key": "target",
      "label": "目标",
      "column": "总任务金额",
      "format": "amount",
      "role": "bar_target"
    },
    {
      "key": "actual",
      "label": "完成",
      "column": "年度开单金额",
      "format": "amount",
      "role": "bar_actual"
    },
    {
      "key": "rate",
      "label": "完成率",
      "column": "达成率",
      "format": "percent",
      "role": "line_rate"
    },
    {
      "key": "remaining",
      "label": "剩余任务",
      "column": "剩余任务金额",
      "format": "amount",
      "role": "kpi"
    },
    {
      "key": "people_count",
      "label": "人员数",
      "column": "业务员数量",
      "format": "integer",
      "role": "kpi"
    }
  ],
  "signal_rules": [
    { "metric": "rate", "op": ">=", "value": 100, "status": "excellent", "label": "优秀" },
    { "metric": "rate", "op": ">=", "value": 80, "status": "normal", "label": "关注" },
    { "metric": "rate", "op": "<", "value": 80, "status": "risk", "label": "预警" }
  ],
  "report_preferences": {
    "default_view": "left_narrative_right_visual",
    "expand_policy": "expand_risk_and_top_nodes",

  }

```

这个 Profile 可以存放在现有 `bs_dataset_report_config.config_json` 中，也可以后续拆成独立表。短期建议复用现有表，降低改造成本。

### 4.2 ReportSpec 动态报告协议

ReportSpec 是问数结果最终交给前端的唯一协议。左侧文字、右侧图表、PDF 导出都从它生成。

建议结构：

```json
{
  "version": "1.0",
  "question": "东部分公司业绩怎么样？",
  "dataset_id": 1,
  "analysis_mode": "single_entity_drilldown",
  "mode_reason": "用户查询单个分公司，SQL 结果包含分公司、代表处、业务员三级结构。",
  "root_entities": ["东部分公司"],
  "metric_schema": [],
  "hierarchy": {
    "depth": 3,
    "paths": [["分公司", "代表处", "业务员"]],
    "nodes": []
  },
  "visual_spec": {
    "layout": "left_narrative_right_visual",
    "kpi_cards": [],
    "charts": [],
    "accordions": []
  },
  "narrative": {
    "summary": "",
    "sections": []
  },
  "export_spec": {
    "pdf_enabled": true,
    "default_expand": "risk_and_top"
  }
}
```

关键约束：

- 前端不再从原始 SQL 行里猜报告结构。
- Agent4 不再生成图表配置和指标数值。
- 所有 KPI 和图表数据来自后端标准化节点。
- Agent4 只输出 `narrative.sections`，并且必须引用已有 `node_id` 或 `comparison_id`。

### 4.3 ReportNode 标准节点

无论 SQL 原始字段是什么，后端都要转换为标准节点：

```json
{
  "node_id": "node_east_branch",
  "name": "东部分公司",
  "level": "分公司",
  "depth": 1,
  "parent_id": "node_syyb",
  "track": "区域条线",
  "metrics": {
    "target": 95000000,
    "actual": 13000000,
    "rate": 13.68,
    "remaining": 82000000,
    "people_count": 36
  },
  "status": "risk",
  "children": []
}
```

前端只认 `ReportNode`，不关心原始 SQL 是中文列名、英文列名，还是 JSONB 展开字段。

## 5. 三种动态场景的处理方案

### 5.1 场景 A：单体下钻模式

触发条件：

- Agent1 识别用户问题指向单个主体。
- Result Profiler 发现 SQL 结果中只有一个主要根主体，或者主体过滤条件明确。
- 结果可构造成父子层级树。

处理方式：

```text
整体 KPI
  -> 下一级节点概览
  -> 风险节点与优秀节点
  -> 可展开到更低层级
  -> Agent4 输出整体结论、层级洞察、管理建议
```

示例：用户问“东部分公司业绩怎么样？”

```text
东部分公司
  -> 代表处列表
    -> 业务员列表
```

示例：用户问“安徽代表处业绩怎么样？”

```text
安徽代表处
  -> 业务员列表
```

注意：系统必须从实际数据深度开始分析。如果查询主体已经是代表处，就不能再生成“分公司层分析”这种空节。

### 5.2 场景 B：多体对比模式

触发条件：

- 用户问题包含“对比、比较、哪个更好、A 和 B、A vs B”等意图。
- SQL 结果中存在两个或多个同级主体。
- Agent1 或 Result Profiler 判断这些主体不能被简单合并。

处理方式：

```text
主体 A vs 主体 B KPI 对比
  -> 目标、完成、完成率、缺口、人员数
  -> 各自主体内部结构拆解
  -> 优势与短板对比
  -> 分别给出管理建议
```

关键规则：

- 多体对比模式下禁止只给合计值。
- 可以展示合计作为背景，但主结论必须基于主体间差异。
- 图表默认展示并列柱状图和完成率折线。
- 每个主体可以展开自己的下级结构。

### 5.3 场景 C：异构架构适配

触发条件：

- 一个数据集内存在多条不同层级路径。
- 不同数据集的组织结构不同。
- 同一问题返回的结果中既有分公司，也有业务部，且下钻深度不同。

处理方式：

```text
按实际树结构渲染
  -> 有 children 的节点才可展开
  -> 没有对应层级就不生成空节
  -> 每条路径独立分析
  -> 汇总层只做可解释的聚合，不做无意义求和
```

示例：商用事业部下有四个分公司和三个业务部。

```text
商用事业部
  -> 东部分公司
    -> 代表处
      -> 业务员
  -> 创新业务部
    -> 业务员
```

前端渲染时不应该问“这一层是不是代表处”，而应该问“这个节点有没有 children、它属于什么 level、它有哪些 metrics、它的 status 是什么”。

## 6. Agent4 的新职责

Agent4 应从“报表结构生成者”降级为“结构化洞察撰写者”。这不是削弱 Agent4，而是让它专注做大模型真正擅长的事情：解释、归纳、归因假设、管理建议。

### 6.1 Agent4 输入

Agent4 不再只拿原始 SQL rows，而是拿 AnalysisContext：

```json
{
  "question": "东部分公司业绩怎么样？",
  "analysis_mode": "single_entity_drilldown",
  "mode_reason": "查询单个分公司，结果存在代表处和业务员下钻层级。",
  "dataset_profile": {},
  "report_spec_draft": {},
  "important_nodes": {
    "root_nodes": [],
    "risk_nodes": [],
    "top_nodes": [],
    "comparison_nodes": []
  },
  "result_evidence": {
    "row_count": 120,
    "columns": [],
    "sample_rows": []
  }
}
```

### 6.2 Agent4 输出

Agent4 输出必须是 JSON，且只能引用 ReportSpec 已有节点：

```json
{
  "summary": "东部分公司整体完成率偏低，缺口主要集中在部分代表处。",
  "sections": [
    {
      "section_id": "overall",
      "title": "整体表现",
      "linked_node_ids": ["node_east_branch"],
      "paragraphs": ["东部分公司当前目标规模较高，但完成进度不足，需要优先关注缺口较大的下级节点。"]
    },
    {
      "section_id": "risk_nodes",
      "title": "重点风险",
      "linked_node_ids": ["node_anhui_office", "node_henan_office"],
      "paragraphs": ["安徽代表处和河南代表处完成率低于预警线，是后续管理动作的重点。"]
    }
  ],
  "suggestions": [
    {
      "linked_node_ids": ["node_anhui_office"],
      "text": "建议对安徽代表处进行客户池和项目阶段拆解，优先追踪高概率未开单项目。"
    }
  ]
}
```

### 6.3 Agent4 铁律

1. 不重新计算指标。
2. 不新增 ReportSpec 中不存在的节点。
3. 不输出图表数据。
4. 不在多体对比时给出简单合计结论。
5. 不为不存在的层级生成空章节。
6. 结论必须绑定证据节点。
7. 不确定时输出“证据不足”，而不是编造原因。

## 7. 前端动态渲染方案

### 7.1 组件结构

建议新增一套动态报告组件：

```text
frontend/src/components/dynamic-report/
  DynamicReportView.vue
  NarrativePanel.vue
  VisualReportPanel.vue
  KpiCardGrid.vue
  ComboChart.vue
  NodeAccordion.vue
  ComparisonBoard.vue
  ReportExportToolbar.vue
```

职责划分：

- `DynamicReportView.vue`：接收 ReportSpec，负责整体布局。
- `NarrativePanel.vue`：左侧文字分析，支持点击高亮右侧节点。
- `VisualReportPanel.vue`：右侧可视化容器。
- `KpiCardGrid.vue`：顶层 KPI 卡片。
- `ComboChart.vue`：目标 vs 完成柱形图 + 完成率折线图。
- `NodeAccordion.vue`：递归渲染下级节点。
- `ComparisonBoard.vue`：多主体对比专用视图。
- `ReportExportToolbar.vue`：PDF 导出入口。

### 7.2 渲染规则

单体下钻模式：

```text
根主体 KPI
  -> 下级节点组合图
  -> 下级节点 Accordion
  -> 展开后展示该节点 children 的组合图和专项分析
```

多体对比模式：

```text
主体 A/B/C KPI 对比卡
  -> 主体级组合图
  -> 每个主体的优势/风险摘要
  -> 每个主体可展开自己的下级结构
```

异构模式：

```text
按 root node 分组
  -> 每个 root node 按自身 children 递归渲染
  -> 不按固定层级名生成章节
```

### 7.3 左文右图一致性

左侧文字和右侧图表必须通过 ID 绑定：

- 左侧每个 section 有 `linked_node_ids`。
- 右侧每个卡片、图表、折叠项有 `node_id`。
- 点击左侧段落，右侧对应节点高亮并滚动定位。
- 展开右侧节点，左侧对应分析段落高亮。
- PDF 导出读取同一份 ReportSpec。

这样可以避免“左边说安徽代表处风险，右边图表却展示河南代表处”的不一致问题。

## 8. 大模型自动生成数据集配置

你提到“已经有地方配置数据集”，所以这里不是再造一个配置入口，而是在现有数据集维护页上新增“AI 生成/补齐”能力。

### 8.1 自动生成目标

大模型应该帮助管理员自动生成以下内容：

1. Dataset Profile 数据集画像。
2. Agent1 路由提示词。
3. Agent2 SQL 生成提示词。
4. Agent3 SQL 校验提示词。
5. Agent4 分析提示词。
6. 建议的 Golden SQL 样本。
7. 常见问题。
8. 报告配置和指标映射。
9. 数据质量检查建议。

### 8.2 自动生成输入

AI 生成器可以使用现有数据集资产：

```text
DDL
  -> 表结构、字段类型、主外键、索引

数据字典
  -> 字段业务含义、枚举值、单位

LLD
  -> 业务口径、组织架构、指标定义

样例数据 profile
  -> 字段 TopN、空值率、数值范围、日期范围

已有 Golden SQL
  -> 典型查询模式

用户补充说明
  -> 默认时间口径、领导关注点、风险阈值
```

### 8.3 自动生成流程

建议新增 Dataset Copilot 工作流：

```text
管理员点击“AI 生成数据集配置”
  -> 后端读取 DDL / LLD / 字段字典 / 样例数据
  -> LLM 生成 Dataset Profile 草稿
  -> LLM 生成四 Agent Prompt 草稿
  -> LLM 生成 5-10 条 Golden SQL 草稿
  -> 系统自动试跑 Golden SQL
  -> Agent3 校验 SQL 安全和可执行性
  -> 失败项标红，成功项进入待确认
  -> 管理员审核后保存到现有数据集配置
```

### 8.4 生成结果必须经过校验

大模型生成的数据集配置不能直接入库，必须经过自动校验：

1. 字段是否真实存在。
2. SQL 是否只读。
3. SQL 是否可执行。
4. 指标列是否能转为数值。
5. 层级字段是否能构成树。
6. Golden SQL 是否能返回非空结果。
7. Agent4 Prompt 是否包含禁止编造、证据绑定、按 ReportSpec 输出等规则。

## 9. 后端改造计划

### 9.1 新增 reporting 模块

```text
backend/reporting/report_schema.py
backend/reporting/result_profiler.py
backend/reporting/analysis_mode_detector.py
backend/reporting/report_planner.py
backend/reporting/agent4_adapter.py
backend/reporting/pdf_exporter.py
```

职责：

- `report_schema.py`：定义 DatasetProfile、ReportSpec、ReportNode、MetricSchema。
- `result_profiler.py`：把 SQL rows 转成标准 ReportNode 树和指标集合。
- `analysis_mode_detector.py`：识别单体下钻、多体对比、异构架构。
- `report_planner.py`：生成 ReportSpec 草稿。
- `agent4_adapter.py`：组装 Agent4 输入、解析 Agent4 JSON、合并 narrative。
- `pdf_exporter.py`：后期支持服务端 PDF 导出。

### 9.2 修改 four_agent_ask.py

建议在 `_run_pipeline()` 的 SQL 执行后、Agent4 前插入：

```text
result
  -> result_profiler.profile(result, dataset_profile)
  -> analysis_mode_detector.detect(question, profile)
```

### 9.3 修改 dataset_report_config.py

当前它已经能读写报告配置，建议升级为：

## 10. 前端改造计划

### 10.1 SmartAsk.vue

原因：

- 后端更容易访问 Dataset Profile、LLD、Agent 结果和 SQL 元信息。

## 11. PDF 导出方案

建议两阶段实现。

第一阶段：前端导出。

- 使用当前页面 DOM 导出。
- 导出前可提供“全部展开风险节点 / 全部展开 / 保持当前展开状态”。
- 图表使用 canvas 截图或 ECharts dataURL。
- 适合快速交付。

第二阶段：服务端导出。

- 后端接收 `report_spec` 或 `report_id`。
- 使用 Playwright/Chromium 渲染同一套报告页面。
- 输出稳定 PDF。
- 适合正式经营报告、定时推送、飞书归档。

建议第一阶段先做前端导出，ReportSpec 稳定后再做服务端导出。

## 14. 质量保障

### 14.1 回归测试题库

每个数据集至少维护以下测试题：

1. 单主体查询。
2. 下级主体查询。
3. 两个同级主体对比。
4. 顶层主体查询。
5. 异构结构查询。
6. 歧义主体查询。
7. 时间口径查询。
8. 无数据查询。

### 14.2 ReportSpec 校验

返回前必须校验：

- 所有 `linked_node_ids` 必须存在。
- 所有图表引用的 metric key 必须存在。
- comparative 模式必须有两个以上主体。
- single_entity_drilldown 模式必须有 root entity。
- 没有 children 的节点不能生成展开图表。
- 风险状态必须由 signal_rules 计算，不能由 Agent4 编造。

### 14.3 大模型输出校验

Agent4 输出必须经过 JSON Schema 或 Pydantic 校验：

- JSON 格式合法。
- section 数量合理。
- 不包含不存在的节点 ID。
- 不包含 ReportSpec 外的指标数值。
- 建议项不能为空话。

校验失败时允许重试一次；仍失败则降级为后端规则生成的基础报告。

## 15. 推荐优先级

我建议不要先做 PDF，也不要先大改 UI。优先级应该是：

1. ReportSpec 协议。
2. Result Profiler。
3. Analysis Mode Detector。
4. Agent4 结构化 narrative。
5. DynamicReportView。
6. 左文右图联动。
7. Dataset Copilot 自动生成配置。
8. PDF 导出。

原因很简单：只要 ReportSpec 没稳定，前端图表、PDF、自动生成配置都会反复返工。先把“后端如何理解结果、如何表达报告结构”定住，后面所有能力都会变得更顺。

## 16. 最终目标形态

改造完成后，一个新数据集接入流程应该变成：

```text
上传或填写 DDL / LLD / 数据字典
  -> AI 生成 Dataset Profile
  -> AI 生成四 Agent Prompt
  -> AI 生成 Golden SQL / FAQ
  -> 系统自动试跑和校验
  -> 管理员审核保存
  -> 用户问数
  -> 系统自动识别单体、对比、异构模式
  -> 生成左文右图动态报告
  -> 一键导出 PDF
```

这套方案的核心价值是：

- 数据集配置继续复用已有体系。
- Agent 不再背负硬编码报表职责。
- 前端不再绑定某个事业部的字段和层级。
- 多数据集、多组织结构、多查询场景都通过统一协议适配。
- 大模型从“每次现场猜”变成“配置生成 + 结构化分析”的可控生产力。
