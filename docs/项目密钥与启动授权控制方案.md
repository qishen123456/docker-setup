# 项目密钥与启动授权控制方案

## 1. 目标

本方案用于解决以下问题：

- 项目部署到公司 Linux / Docker 服务器后，不希望 `.env`、`config/*.json` 中出现明文超管密码、数据库密码、AI Key、飞书 Secret。
- 不希望其他人拿到项目文件后，可以直接复制、启动、复刻一套完整系统。
- 希望项目启动、密钥轮换、授权控制仍由项目所有者掌握。

需要先明确边界：

如果对方拥有 Linux root 或 Docker 管理员权限，并且项目已经正常运行，那么他理论上仍有机会读取运行时环境、进入容器、调试进程、查看内存或替换代码。也就是说，本机加密不能做到绝对防 root。

本方案主要防护的是：

- 静态配置泄露。
- 项目被复制后直接运行。
- 非项目所有者随手重启、迁移、复刻系统。
- 应用后台管理员看到明文密钥。

## 2. 不建议采用隐藏后门脚本

不建议在项目中放“藏得很深”的隐藏控制脚本、后门开关或隐蔽停服逻辑。

原因：

- 容易被安全扫描或审计认定为后门。
- 一旦被公司运维发现，解释成本很高。
- 隐藏逻辑会增加后续维护风险，可能在正常升级、备份、迁移时误伤业务。
- 如果脚本被别人发现并复用，反而会变成攻击入口。

更稳妥的做法是使用透明、可解释的“部署授权机制”和“启动解锁机制”。它们不是后门，而是正常的软件授权和密钥保护手段。

## 3. 推荐方案一：启动解锁密钥

### 3.1 思路

服务器上只保存密文，不保存明文密钥。

例如 `.env` 中只保留：

```env
SMARTASK_ADMIN_PASSWORD_ENC=加密后的超管密码
SMARTASK_AI_API_KEY_ENC=加密后的 AI Key
SMARTASK_FEISHU_APP_SECRET_ENC=加密后的飞书 Secret
SMARTASK_DB_PASSWORD_ENC=加密后的数据库密码
```

真正用于解密的启动密钥不写入 `.env`，由项目所有者在启动时临时输入：

```bash
./scripts/start_secure.sh
```

脚本提示：

```bash
请输入项目启动密钥:
```

输入正确后，应用启动并在内存中解密敏感配置。输入错误则应用无法启动或关键功能不可用。

### 3.2 效果

可以做到：

- 打开 `.env` 看不到明文密码。
- 拷走项目文件无法直接启动可用系统。
- 服务器重启后，如果没有启动密钥，项目无法恢复完整功能。
- 应用后台只显示 `***已保存***`，不回显真实密钥。

不能做到：

- 项目已经运行时，完全防住 root 级别人员从运行时环境中提取秘密。

### 3.3 示例启动脚本

```bash
#!/usr/bin/env bash
set -euo pipefail

read -s -p "请输入项目启动密钥: " SMARTASK_UNLOCK_KEY
echo

if [ -z "$SMARTASK_UNLOCK_KEY" ]; then
  echo "启动密钥不能为空"
  exit 1
fi

export SMARTASK_UNLOCK_KEY
docker compose up -d
unset SMARTASK_UNLOCK_KEY

echo "SmartAsk 已提交启动。"
```

建议文件权限：

```bash
chmod 700 scripts/start_secure.sh
```

## 4. 推荐方案二：超管密码只保存哈希

超管密码不建议可逆加密保存。

更好的方式是：

```text
用户输入超管密码 -> 后端计算 hash -> 与保存的 hash 比对
```

服务器只保存：

```env
SMARTASK_ADMIN_PASSWORD_HASH=...
SMARTASK_ADMIN_PASSWORD_SALT=...
```

这样即使别人看到配置，也看不到超管明文密码。

注意：这只能保护“密码本身不泄露”。如果对方有 root，他仍然可以改代码、改 hash 或直接操作容器，所以它不是授权控制的完整替代。

## 5. 推荐方案三：远程授权服务

如果后续想更强地掌控项目，可以做远程授权。

流程：

```text
项目启动
  -> 读取本机机器码 / 授权码
  -> 请求你控制的授权服务
  -> 授权服务校验是否允许启动
  -> 返回短期启动令牌或临时解密密钥
  -> 项目进入可用状态
```

服务器上只保存：

```env
SMARTASK_LICENSE_CODE=授权码
SMARTASK_LICENSE_SERVER=https://your-license-server.example.com
```

这样你可以做到：

- 不授权则项目无法完整启动。
- 授权可按机器、公司、有效期绑定。
- 项目迁移到另一台服务器后需要重新授权。
- 发现风险时可以吊销授权。

这是比“隐藏脚本”更正规、更安全、更容易解释的掌控方式。

## 6. 推荐方案四：运维控制脚本

可以提供一组透明的运维脚本，而不是隐藏控制脚本。

建议脚本：

```text
scripts/start_secure.sh       输入启动密钥后启动项目
scripts/stop.sh               停止项目
scripts/status.sh             查看容器、端口、健康检查
scripts/backup_secure.sh      备份数据库和配置，自动脱敏日志
scripts/rotate_secret.sh      轮换启动密钥并重新加密配置
scripts/license_check.sh      检查授权状态
```

这些脚本可以由你掌握，也可以给公司运维有限使用。

## 7. 推荐落地顺序

### 阶段一：不改核心功能，只改暴露风险

- 管理后台不返回任何明文密钥。
- 飞书 `app_secret` 改为脱敏展示。
- AI Key、数据库密码、飞书 Secret 编辑时不回显，留空表示不修改。

### 阶段二：本地启动解锁

- 新增统一 `secret_manager.py`。
- 支持 `SMARTASK_UNLOCK_KEY`。
- 配置文件中保存密文。
- 启动时解密，失败则拒绝启动或禁用关键功能。

### 阶段三：远程授权

- 增加授权服务地址和授权码。
- 启动时校验授权。
- 支持授权吊销、有效期、机器绑定。

## 8. 建议采用的最终组合

建议组合如下：

```text
超管密码：哈希保存，不保存明文，不做可逆加密
AI Key：启动密钥加密保存
飞书 Secret：启动密钥加密保存
数据库密码：启动密钥加密保存，或使用 Docker Secret 文件
应用后台：所有敏感字段只显示脱敏状态
项目启动：必须输入启动密钥
商业化/强控制：增加远程授权服务
```

## 9. 一句话结论

如果只是防止别人看到配置、复制项目、随手启动，使用“启动解锁密钥 + 密钥脱敏 + 超管密码哈希”就足够。

如果要防 root 级别人员长期接管服务器后的深度分析，只能把关键授权能力放到你控制的远程服务里，不能依赖服务器本机隐藏脚本。
