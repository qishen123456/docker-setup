# 智能问数界面火山引擎对标小步改造计划

版本：v2.0  
日期：2026-05-11  
原则：参考火山引擎的交互骨架，但不推翻当前项目；一次只改一个点；每一步可验收、可回退。

## 1. 这版和上一版的区别

上一版“小步计划”偏安全，但没有把火山引擎的结构拆透。  
这版先对标火山引擎，再映射到当前项目已有组件。

参考资料：

```text
火山引擎/中间区.png
火山引擎/右侧区 (1).png
火山引擎/分割图片_中间区
火山引擎/分割图片_右侧区 (1)
火山引擎/中间区.md
火山引擎/右侧区.md
```

本次不是照抄火山引擎的数据分析内容，而是参考它的页面节奏：

```text
用户提问
-> 思考完成 / 执行计划
-> Agent 执行完毕
-> 查看详情
-> 报告文件 / 结果入口
-> 右侧执行事件详情
```

当前项目已经有很多对应组件，关键是没有按火山引擎的节奏串起来。

## 2. 火山引擎中间区骨架

从 `火山引擎/中间区.md` 和截图看，中间区大致是这个顺序：

| 顺序 | 火山引擎表现 | 作用 |
|---|---|---|
| 1 | 顾问问候 | 建立“经营分析顾问”身份 |
| 2 | 用户问题气泡 | 只展示用户问题，不混日志 |
| 3 | `思考完成` 折叠块 | 告诉用户系统制定了执行计划 |
| 4 | 详细执行计划 | 步骤 1、1.1、2、2.1 这种层级计划 |
| 5 | `Agent 执行完毕` 横条 | 明确告诉用户任务完成，可查看详情 |
| 6 | 报告文件卡 | 把结果包装成交付物，如 HTML 报告 |
| 7 | 结束语与下一步按钮 | 查看下一个、继续修改、申请试用等 |

它最强的地方不是卡片多，而是“过程像一个顾问在交付任务”。

## 3. 火山引擎右侧区骨架

从 `火山引擎/右侧区.md` 和截图看，右侧区不是业务结论区，而是执行事件详情区。

右侧区节点大致是：

| 火山引擎节点 | 展示内容 |
|---|---|
| 选择数据表并执行 SQL 语句查询数据 | 任务说明、模型生成 SQL、实际 SQL、结果预览 |
| 复杂查询 pandas 代码到 SQL 转换 | 代码/SQL 转换过程 |
| 通过 Python 解决问题 | 代码生成、代码执行、计算结果 |
| 更新事实&计划 | 当前事实、下一步计划 |
| 生成初版报告 | 报告生成过程 |
| 报告智能纠错 | 报告检查过程 |
| 报告智能润色 | 报告优化过程 |
| 生成最终报告 | 最终交付 |

它的特点：

1. 每个节点像一个独立任务卡。
2. 卡片头部有标题和状态。
3. 技术细节在卡片内部。
4. SQL、结果数据、耗时都放右侧。
5. 中间区只给入口，不把右侧内容全部塞进去。

## 5. 当前差距清单

对比火山引擎，当前主要差在这些地方：

1. 中间区缺少明显的“任务交付节奏”。
2. `PlanCard` 还不像火山引擎的 `思考完成`。
3. `AgentDoneBar.vue`、`ArtifactStrip.vue` 已经有，但没有接到主流程里。
4. 完成后直接进入业务卡和报告，缺少“Agent 已完成，产物已生成”的过渡。
5. 右侧 `LogTimeline` 有执行轨迹，但视觉上还不像“事件详情卡片列表”。
6. 中间区和右侧区的分工还不够像火山引擎：中间区应是交付流，右侧区应是审计流。

## 6. 小步改造总表

每一步都只动一个体验点。

| 步骤 | 对标火山引擎 | 当前项目落点 | 目标 |
|---|---|---|---|
| 0 | 固定当前基线 | Git + 本地问数 | 方便回退 |
| 1 | 中间区顺序对齐 | `SmartAsk.vue` | 调整消息流顺序，不改样式大结构 |
| 2 | `思考完成` 卡 | `PlanCard.vue` | 把执行计划做得更像火山 |
| 3 | `Agent 执行完毕` | `AgentDoneBar.vue` | 接入现有完成横条 |
| 4 | 报告文件交付 | `ArtifactStrip.vue` | 接入报告/执行轨迹/结果入口 |
| 5 | 业务结论卡 | `ResultDigestCard.vue` | 保留你的经营分析特色 |
| 6 | 右侧事件详情 | `LogTimeline.vue` | 节点卡片更像火山右侧 |
| 7 | SQL/结果详情 | `SqlBlock.vue` + 表格预览 | 技术细节留右侧 |
| 8 | 全屏报告入口 | `SmartAsk.vue` | 和报告交付卡打通 |

## 8. 第 1 步：中间区流程顺序对齐火山

### 对标火山引擎

火山中间区不是一上来就堆结果，而是：

```text
用户问题
-> 思考完成 / 执行计划
-> Agent 执行完毕
-> 报告文件
-> 最终回答
```

### 当前项目问题

当前中间区已有：

```text
LiveExecutionFeed
PlanCard
ThinkingCard
ResultDigestCard
InlineVisuals
ErrorCard
```

但完成态缺少“交付过渡”，导致用户感觉是系统突然把一堆内容吐出来。

### 改动文件

```text
frontend/src/views/SmartAsk.vue
```

### 具体改法

只调整顺序，不先大改样式。

建议完成态顺序：

```text
ResultDigestCard             先给业务答案
AgentDoneBar                 告诉用户 Agent 已完成
ArtifactStrip                提供报告、执行轨迹、结果入口
InlineVisuals                图表预览，如有
```

运行态顺序：

```text
LiveExecutionFeed
PlanCard
ThinkingCard 默认收起
```

### 为什么不是完全照火山

火山把报告文件放在最终回答前后都可以；你的系统是经营问数，老板更关心答案，所以 `ResultDigestCard` 仍然放在完成态最前。  
但要补上火山的“Agent 完成”和“产物交付”感觉。

### 验收

1. 完成后能看到“经营分析结论”。
2. 能看到类似“Agent 执行完毕”的交付横条。
3. 能看到报告/执行轨迹入口。
4. 不影响原来的查看详情、全屏报告。

### 回退文件

```text
frontend/src/views/SmartAsk.vue
```

## 12. 第 5 步：ResultDigestCard 保留经营分析特色

### 对标火山引擎

火山的最终报告入口很好，但它的中间区业务摘要并不一定适合你的业绩分析。  
你的系统要保留“老板一眼看懂”的经营结论。

### 当前项目重点

继续优化：

```text
frontend/src/components/smartask/ResultDigestCard.vue
```

### 具体改法

1. 单一组织：先讲整体。
2. 两主体对比：给差异条。
3. 三到四主体：全部列出但控制密度。
4. 五个以上主体：只展示最高、最低、整体、风险数量。
5. Debug 条默认不在老板视角显示。

### 和火山的关系

火山负责“交付流程感”，`ResultDigestCard` 负责“经营答案质量”。  
这一步不是照抄火山，而是把你的业务价值保留下来。

### 验收问题

```text
东部分公司业绩怎么样
东部和西部业绩对比
三大业务部业绩怎么样
9大分公司达成率排名
```

### 回退文件

```text

```


```text

```
