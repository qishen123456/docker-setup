## 3. Phase 0：Dataset Copilot + 一键重建 syyb（最先做、当前已实施）

### 3.1 目标

1. 新建 Dataset Copilot：用大模型把 `提示词和数据.md`（或任何业务输入）转成完整数据集 payload（synonyms / LLD / DDL / data_dictionary / golden_sql / agent_prompts / common_questions / regression_cases）。
2. 一键重建 syyb：把 syyb 数据集旧的脏 LLD / 老 Agent prompt / 历史 Golden SQL 全量替换成 Copilot 重新生成的版本（利用现有 `PUT /api/bookshelves/datasets/<id>/full` 已有的"DELETE 后 INSERT"原子语义，天然完成清理）。
3. 命令行运行，无前端依赖；产物先打到本地 JSON 备份再写库，便于回滚。
4. 后续新增数据集时，可以同一个 CLI + 不同输入文档直接生成。

### 3.5 验收标准

1. 前端 `数据集管理 → 商用事业部` 打开后：LLD、DDL、字段字典、Golden SQL、四个 Agent Prompt 都已被刷新成 Copilot 输出的版本，质量分≥85。
2. 不再看到旧版本残留的"东部分公司"特殊处理 prompt 或与本次方案冲突的旧 Golden SQL。
3. SmartAsk 用以下三类问题问数都能正常返回结果：
   - 单体下钻：东部分公司业绩怎么样
   - 下级单体：安徽代表处业绩怎么样
   - 多体对比：东部分公司和南部分公司哪个完成得更好
4. 报告内容和 SQL 复核都没有 hard fail；如果失败，按 3.6 自愈。

### 3.6 失败自愈流程（不要停，按这个顺序处理）

1. Copilot 生成 JSON 缺字段：调整 [copilot_prompts.py](../backend/dataset_copilot/copilot_prompts.py) 的 schema 描述，重新跑 `--dry-run`，直到 JSON 通过校验。
2. PUT 接口 400（validation failed）：看响应里的 details，缺哪类补哪类，最常见是 Golden SQL 不足 3 条或 Agent4 prompt 为空。在 Copilot prompt 中强制要求 ≥5 条 Golden SQL、4 个 Agent prompt 全配齐。
3. 问数返回 SQL 报错：把错误注入到下一轮 Copilot 生成的 LLD/Agent2 prompt 中作为反例（"以下写法是错误的，禁止再产出"），重跑 regenerate。
4. 问数返回结果但分析空泛：在 Copilot prompt 里给 Agent4 prompt 增加禁止编造、必须按层级展开、必须给出可执行动作的硬约束，重跑。
5. 多体对比被错误合并：暂时通过 Agent2 prompt 增加"涉及多个分公司时禁止聚合，必须保留主体维度"的硬规则；这是 Phase 1 才能彻底解决的问题，Phase 0 用提示词兜底即可。

### 3.7 复制到新数据集

任何新数据集，准备好"业务底稿"（一篇 md 里写明：表名、字段含义、组织层级、典型业务问题、口径、风险阈值、样例数据），然后：

```powershell
python regenerate_dataset_from_doc.py `

    --doc docs/<新底稿>.md `
    --dry-run

python regenerate_dataset_from_doc.py `

```

## 9. 模块 4：智能化数据集配置助手 Zero-Touch Onboarding

把"AI 自动配置"做成端到端工作流，覆盖三种触发点：

1. **新数据集向导**：粘贴/上传业务底稿 → AI 一键产出 Profile + 四 Agent Prompt + Golden SQL + 报告配置 → 管理员审核 → 保存。

## 10.5 模块 5：对话上下文 + 智能歧义确认（必须做、随 Phase 1 落地）

### 10.5.1 现状问题

1. 现在 `four_agent_ask.ask` 只接单条 question，没有对话上下文；用户连续问"那东部呢？""跟去年比？"会被当作全新问题。
2. 已有的 `dataset_disambiguation` 是基于硬编码 dataset_profile 关键词组的，识别范围窄、命中率低，多数歧义场景实际上没触发。
3. 当多个数据集都可能命中时，没有让 LLM 结合"上下文 + 候选数据集摘要"做主动澄清，导致路由经常猜错。

### 10.5.2 设计要点

#### A. 对话上下文（短时记忆，挂在 SmartAsk session_id 上）

后端：

- 新增 `backend/memory/short_term_memory.py`：内存（首版）+ 可选 Redis（后期），按 `session_id` 存最近 N=8 轮 `(role, question, sql, brief_result, dataset_id, resolved_entities, mode)`。
- `four_agent_ask.ask(question, session_id, history=None, dataset_id=None, ...)`：
  - 入参新增 `session_id`。
  - 若上层未传 history，从 short_term_memory 读取。
  - Agent1 路由前把 history 注入 prompt（"用户上一轮问的是 X，使用了数据集 Y，主体是 Z"），实现指代消解（"那东部呢" → 指代上一轮的"分公司维度"）。
  - 路由完成后回写一条记录。
- 老板确认 `confirm_by_boss` 也要绑定 session_id，保证确认结果对后续追问继续生效。

前端：

- `frontend/src/state/smartAskSession.js` 增加 `sessionId`，首次进入页面自动生成（uuid）；调用 `/api/smart-chat/stream` 时透传。
- "新建会话"按钮强制刷新 sessionId，避免上下文越积越乱。

#### B. 智能歧义确认（替换硬编码组匹配）

候选数据集打分阶段保留现状（同义词命中 + 字典命中 + 黄金 SQL 相似度），但触发条件改为：

```python
top1, top2 = ranked_candidates[0], ranked_candidates[1] if len(ranked_candidates) > 1 else None
need_confirm = (
    top1.score < HARD_CONFIRM_THRESHOLD  # 70
    or (top2 and (top1.score - top2.score) < CLOSE_GAP_THRESHOLD)  # 12
    or _question_has_ambiguous_terms(question, history)  # 见下
)
```

`_question_has_ambiguous_terms` 改成由 **LLM 兜底裁决**（小模型快速调用），输入：

```text
- question
- 最近 2 轮对话摘要
- top3 候选数据集的 (dataset_name, business_domain, top synonyms, 3 个代表性 golden_sql 问题)
- 每个候选的命中证据（命中的同义词/列/golden_sql_id）
```

输出严格 JSON：

```json
{
  "need_confirm": true,
  "confirm_question": "你问的『东部』是指 syyb 数据集里的『东部分公司』，还是 angel_warehouse 数据集里的『东部仓』？",
  "options": [
    {"option_id": "syyb_east", "dataset_id": 1, "label": "syyb·东部分公司", "scope_filter": {"分公司": "东部分公司"}},
    {"option_id": "warehouse_east", "dataset_id": 7, "label": "angel_warehouse·东部仓", "scope_filter": {"仓库区域": "东部"}}
  ],
  "auto_pick_option_id": null
}
```

如果 LLM 返回 `need_confirm: false` 且 `auto_pick_option_id`，直接采纳并把澄清结论挂到 history 上，下一轮自动复用，不再追问。

新增文件：

```text
backend/disambiguation/__init__.py
backend/disambiguation/llm_arbiter.py        # LLM 仲裁
backend/disambiguation/scoring.py            # 候选打分整合
backend/disambiguation/option_builder.py     # 把仲裁结果转成 confirmation_options
```

`four_agent_ask.py` 改造：用 `disambiguation.evaluate(question, history, candidates)` 替换 `_build_dataset_profile_confirmation` 的硬编码分支；保留旧分支作为 LLM 失败兜底。

#### C. 用户体验

- 当后端返回 `requires_confirmation`，前端 ChatStream 把"问题卡片 + 候选选项"渲染成可点击按钮。点击 → 调用 `/api/smart-chat/confirm-by-boss`，附带 session_id；后端记忆这次澄清，对后续 N 轮内同类问题不再追问（沉淀进 short_term_memory 的 `clarifications` 字段）。
- "我来描述更清楚的问法"的自由输入选项保留，作为兜底。

### 10.5.4 验收

1. 连续问：① "东部分公司业绩怎么样" ② "那南部呢" ③ "两个相比哪个更好"  → 第二、三轮不再触发"请选择数据集"，且第三轮被正确识别为对比模式。
2. 新数据集上线后，相同实体名（如"东部"）出现在两个数据集 → 第一次提问触发 LLM 澄清；选定后接下来 N=8 轮不再追问。
3. 路由置信度 ≥ 70 时不打断；< 70 或 top1-top2 ≤ 12 时一定追问；不再因为关键字没在硬编码 dataset_profile group 里就漏问。
4. `confirm-by-boss` 选项里 dataset_id 与 scope_filter 一并落到 `_pending_confirmations[session_id]`，下游 Agent2 自动注入到 SQL WHERE。

### 10.5.5 与其它 Phase 的耦合

- 与 Phase 0：Copilot 生成 Agent prompt 时已经按 §10.5.2 的口径，把"上下文指代消解"+"必要时主动澄清"的规则写进 Agent1/Agent4 prompt（见 [copilot_prompts.py](../backend/dataset_copilot/copilot_prompts.py) §SYSTEM_PROMPT 第 8/9 条）。
- 与 Phase 3：本模块的 short_term_memory 是 Phase 3 RAG/记忆的最小可用版；Phase 3 落地时直接把 `short_term_memory.py` 升级为持久化 + 检索式即可。
