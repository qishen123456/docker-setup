# SmartAsk 智能问数项目演讲稿（比赛路演版）

> 适用场景：创新应用大赛、数字化转型比赛、AI 应用路演  
> 建议时长：8-10 分钟  
> 讲述风格：问题清晰、方案有亮点、技术可信、价值可落地

---

## 1. 开场

各位评委、各位老师，大家好。今天我汇报的项目是 **SmartAsk 智能问数系统**。

它面向企业经营分析场景，解决一个非常真实的问题：业务人员每天都在问数，但数据往往藏在系统、表格、数据库和不同口径里。一个简单问题，比如“哪些分公司达成率低于 30%”，过去可能需要找人、找表、写 SQL、核口径、再整理结果。

SmartAsk 要做的，就是让业务人员用自然语言直接提问，系统自动完成数据集识别、SQL 生成、执行复核、结果解释和报告展示，把“找人要数”变成“开口即得”。

---

## 2. 项目痛点

我们观察到传统经营分析里有三个典型痛点。

第一是响应慢。业务问题常常发生在晨会、周会和经营复盘现场，但数据响应依赖数据团队，很多问题不能当场得到答案。

第二是门槛高。业务人员懂业务，但不一定懂 SQL、表结构和字段口径；数据人员懂技术，但不一定理解每个业务问题背后的管理意图。

第三是口径乱。同样是“分公司达成率”，在消费者事业部、商用事业部、电商事业部里，层级、字段、统计方式都可能不同。如果系统没有确认机制，很容易给出一个看似有数、实际口径错误的答案。

所以我们不是简单做一个聊天机器人，而是做一个可解释、可复核、可落地的企业级智能问数工作台。

---

## 3. 解决方案

SmartAsk 的核心方案可以概括为一句话：

**用自然语言作为入口，用四 Agent 流程保证查询可靠，用 ReportSpec 报告契约保证展示稳定。**

用户只需要输入问题，比如：

- “消费者事业部哪些分公司年度开单金额低于 3000 万？”
- “商用事业部北部分公司达成率低于 50% 的代表处有哪些？”
- “电商事业部年度目标营收超过 1 亿的业务承接角色有哪些？”

系统会自动判断应该查哪个数据集，是否需要用户确认口径，然后生成 SQL、执行查询、输出结果表和经营分析报告。

---

## 4. 技术架构

项目采用前后端分离架构。

前端使用 Vue 3、Element Plus 和 ECharts，负责智能问数工作台、执行过程展示、结果卡片、报告图表和历史记录。

后端使用 Flask，核心是 AskFlowController 和四 Agent 问数引擎。数据层使用 PostgreSQL，业务数据和元数据统一存储；系统通过 Docker Compose 部署，包含 backend、frontend、postgres 三个容器，方便本地测试和交付部署。

当前项目已经接入三个实际可用数据集：

- 消费者事业部任务达成分析；
- 商用事业部阶段一经营数据；
- 飞书电商事业部经营预算数据。

这三个数据集覆盖了分公司、城市公司、代表处、业务部、业务承接角色等多种组织层级，能够较好验证智能问数的泛化能力。

---

## 5. 四 Agent 流程

SmartAsk 的核心不是“直接让大模型写 SQL”，而是一个分工明确的四 Agent 流程。

**Agent1 负责路由和口径确认。**  
它会判断问题应该命中哪个数据集。如果用户问“哪些分公司达成率低于 30%”，系统会发现消费者事业部和商用事业部都可能回答，于是弹出口径确认卡片，让用户选择，而不是直接猜。

**Agent2 负责 SQL 生成。**  
它结合数据字典、字段说明、规则 SQL 和历史样例生成只读 SQL。对于高频问题，系统优先走确定性规则，减少大模型随机性。

**Agent3 负责 SQL 复核。**  
它检查 SQL 是否只读、字段是否存在、层级过滤是否正确、金额单位是否正确。如果发现问题，会进入修复链路。

**Agent4 负责经营解读。**  
它基于查询结果生成业务结论，例如指出哪些区域承压、哪些业务表现较好、后续应关注哪些指标。

这样的设计让系统既有 AI 的灵活性，又有工程上的稳定性。

---

## 6. 项目创新点

本项目有三个创新点。

第一，**口径确认机制**。  
系统不是只追求“快答”，而是在不确定时主动停下来确认。对企业经营分析来说，口径正确比回答速度更重要。

第二，**规则 SQL 与大模型协同**。  
常见问题走规则 SQL，复杂问题再交给大模型。这样既保证高频问题稳定，也保留自然语言问数的泛化能力。

第三，**确定性报告契约 ReportSpec**。  
我们不让大模型自由生成页面，而是由后端输出结构化 report_spec，前端按契约渲染 KPI、表格、图表和下钻结构。这让结果可追溯、可测试、可复用。

---

## 7. 实测效果

目前我们围绕三个数据集做了多轮真实问数测试。

例如，用户问“消费者事业部哪些分公司年度开单金额低于 3000 万”，系统会正确识别为消费者事业部数据集，并返回京津分公司、江浙沪分公司、黑吉辽分公司等结果。

用户问“商用事业部公共办公业务部剩余任务最多的人员”，系统会下钻到业务代表层级，返回王志军及对应指标。

用户问“电商事业部年度目标营收超过 1 亿的业务承接角色”，系统会把“1 亿”正确换算成数据库中的金额口径，返回净水业务、京东直营、天猫直营。

同时，不指定数据集时，系统能够触发口径确认；无结果时，也能返回空状态而不是报错。

当前后端 78 个自动化测试已通过，前端生产构建通过，Docker 三容器运行健康。

---

## 8. 业务价值

SmartAsk 对企业的价值主要体现在四个方面。

第一，降低使用门槛。业务人员不需要懂 SQL，也能直接查经营数据。

第二，提高响应效率。常规经营问题从“等人出数”变成“现场提问、现场返回”。

第三，沉淀统一口径。通过数据集配置、规则 SQL、复核机制和确认卡片，减少各部门口径不一致。

第四，形成可持续演进的 AI 数据底座。未来可以继续扩展更多数据集、更多指标、更多权限规则和主动预警能力。

---

## 9. 后续规划

后续我们计划从三个方向继续优化。

第一，扩充业务问法测试集，把常见经营问题沉淀为自动化回归测试。

第二，完善指标别名词典，让系统更好理解“销售额”“开单金额”“营收”“目标”“预算”等业务表达。

第三，增强无结果解释和主动建议，比如当“超过 100 亿”没有结果时，系统可以提示当前最大值是多少，并建议用户调整阈值。

---

## 10. 结尾

总结一下，SmartAsk 智能问数系统解决的不是简单的聊天问题，而是企业经营分析中“数据难问、口径难控、结果难解释”的问题。

它用四 Agent 保证查询链路可靠，用口径确认保证业务正确，用报告契约保证结果稳定，最终让经营分析从“找人要数”走向“开口即得”。
