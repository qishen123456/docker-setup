## P2 项目定位：我们到底在做什么

- 不是“做一个聊天机器人”
- 不是“替代 BI 工具”
- 而是：在企业经营分析场景下，构建一个“自然语言入口 + 可解释数据链路 + 确定性报告输出”的 Autonomous BI 最小闭环
- 当前聚焦：验证“问题 → 数据集 → SQL → 数据 → 报告”这条链路可以稳定跑通

**视觉建议**：一句话定位居中，四周环绕四个关键词：可信、闭环、可控、可演进。

## P3 传统经营分析的三重困境

| 困境 | 具体表现 | 代价 |
|---|---|---|
| 响应慢 | 小问题也要经历找表、找人、写 SQL、整理结论 | 决策滞后 |
| 门槛高 | 业务人员不会 SQL，必须依赖数据团队 | 分析资源 bottleneck |
| 口径乱 | 不同人出的数不一致，重复对口径 | 决策依据不可靠 |

**视觉建议**：左侧三个痛点图标，右侧一张“传统流程”长箭头图，强调环节多、时间长。

## P4 设计原则一：先跑通最小闭环

- 不把“智能问数”做成一个大而全的平台
- 基础版先聚焦一件事：**让一句自然语言问题，稳定地变成一份可解释的经营报告**
- 闭环四节点：
  - 问题理解
  - 数据集锁定
  - SQL 生成与执行
  - 报告输出与沉淀

**视觉建议**：四个节点连成圆环，强调“闭环”而不是“功能堆叠”。

---

## P5 设计原则二：基础流程稳定、进阶流程增强

- 不是把现有链路改复杂，而是新增一套“进阶问数流程”
- `AskFlowController` 统一决策：本轮走基础还是进阶
- 基础流程：稳定四 Agent 引擎，服务 80% 常规问题
- 进阶流程：Skill / 工具 / 数据加工链路，服务复杂分析，异常时自动回退基础流程
- 前端无感知：统一结果契约 `dataset_results` / `report_spec` / `analysis`

**视觉建议**：一个流程控制器分叉为两条流水线，最终汇入同一个结果契约。

---

## P6 设计原则三：三层解耦

```text
第一层：数据集知识层
  DDL / 数据字典 / LLD / Golden SQL / Agent Prompt
  → 回答：AI 是否懂这个数据集？

第二层：报告契约层
  指标 / 标准列 / 层级 / 阈值 / 信号灯 / 写作口径
  → 回答：SQL 结果如何变成报告？

第三层：场景渲染层
  detail / comparative / ranking / diagnostic / trend
  → 回答：这个问题该用哪种展示方式？
```

**视觉建议**：三层金字塔图，越底层越稳定、越上层越动态。

## P8 四 Agent 协作流水线

| Agent | 职责 | 输出 |
|---|---|---|
| Agent1 | 意图识别、数据集路由、歧义确认 | `dataset_ids` / `requires_confirmation` / `refined_query` |
| Agent2 | SQL 生成 | 只读 SQL + 生成说明 |
| Agent3 | SQL 复核 | `approved` / `final_sql` / `risks` / `fixes` |
| Agent4 | 业务解读 | `analysis` 文字结论与建议 |

- 关键设计：前一 Agent 不通过，后一 Agent 不执行
- 路由不确定时，系统返回确认卡片，不强行生成答案

**视觉建议**：四个节点横向排列，中间加“通过/确认/复核” gate，下方标注“环环相扣、可中断”。

## P9 Agent1 路由：不只是“选表”

Agent1 综合以下信号做路由决策：
- 数据集名称、别名、业务域
- 组织树解析（事业部 / 分公司 / 代表处 / 业务员）
- 数据集画像（成员集合、层级口径）
- 用户手动选择 / 历史会话上下文
- Golden SQL 相似度

歧义处理：
- 组织树明确 → 自动锁定
- 画像集合明确 → 自动锁定
- 别名强命中 → 自动锁定
- 候选接近 / 多口径 → 返回确认卡片

**视觉建议**：输入信号汇总到“候选评分”，再分叉为“自动锁定”和“确认卡片”。

## P10 SQL 生成三层策略

```text
用户问题 + 路由结果 + 数据集上下文
  ↓
_select_sql_strategy
  ├─ 高匹配 Golden SQL → sample_direct 直执行
  ├─ 规则 SQL 覆盖     → rule_based 确定性生成
  ├─ Golden SQL 模板   → sample_template seed 改写
  └─ 无模板            → Agent2 动态生成
  ↓
Agent3 复核
```

设计意图：
- 越常见的问题，越不依赖大模型随机性
- 人工沉淀的口径通过 Golden SQL 复用
- 新问题仍有 LLM 的泛化能力

**视觉建议**：漏斗图，从上到下稳定性递减、灵活性递增。

## P11 Agent3 复核与 Agent2Repair

**Agent3 复核重点**：
- 是否只读
- 是否包含危险语句
- 字段是否存在
- JSONB 字段读取是否合理
- 聚合、过滤、排序、TopN 是否合理
- 是否符合报告配置需要的输出列

**执行失败后的修复闭环**：
1. 捕获数据库真实错误
2. Agent2Repair 读取 `failed_sql + error + DDL`
3. 生成修复 SQL
4. Agent3 再次复核
5. 重新套行级权限并执行
6. 仍失败则优雅降级，保留诊断信息

**视觉建议**：左侧复核检查清单，右侧修复闭环流程图。

## P12 报告契约与 ReportSpec v2

**核心设计**：不让大模型自由生成 HTML，而是由后端输出确定性报告协议。

报告契约（`dataset_report_config`）定义：
- `nameColumn` / `parentColumn` / `levelColumn`
- `metrics` 指标与口径
- `signalRules` 风险阈值与信号灯
- `sqlOutputContract` 标准输出列

`report_spec_builder` 根据契约和问题场景动态生成 `report_spec`：
- `analysisMode`：detail / comparative / ranking / diagnostic
- `layoutTemplate`
- `kpis` / `sections` / `charts` / `accordions`
- `provenance`：可追溯的数据来源

前端按 `report_spec` 渲染，报告结构稳定、可解释。

**视觉建议**：左侧“报告契约”输入，中间“report_spec_builder”加工，右侧“前端渲染”输出。

## P13 前端信息分工：中间区看答案，右侧区看过程

参考火山引擎 DataAgent 体验设计：
- **中间区**：回答用户真正关心的问题，展示执行计划、关键进展、结果摘要、报告卡片
- **右侧区**：展示完整执行详情，包括 Skill 轨迹、路由分数、SQL、表格预览、自检提示
- **原则**：中间区不变成日志区，右侧区不变成第二份答案

**视觉建议**：左右分屏示意图，中间区标“答案”，右侧区标“过程与证据”。

## P14 场景识别：一个问题该用哪种展示方式

`report_scene_registry.py` 根据问题意图识别四类场景：

| 场景 | 触发词 | 展示重点 |
|---|---|---|
| detail | 单一主体、业绩怎么样 | 整体 KPI + 趋势 + 可下钻层级 |
| comparative | 对比、比较、分别、差异 | 左右对称布局，突出差异值和对比率 |
| ranking | 排名、最高、最低、Top | 名次、差距、红绿灯 |
| diagnostic | 为什么、原因、异常、风险 | 缺口、风险节点、改进建议 |

测试验证：四类场景识别准确率 100%，报告契约健康度 100/100。

**视觉建议**：四个场景卡片，每个配一张报告样式缩略图。

## P15 企业级安全设计

| 安全层 | 机制 | 作用 |
|---|---|---|
| 数据集访问权限 | `allowed_dataset_ids` 过滤 | 没权限的数据集不进入执行 |
| 组织提及权限检查 | `org_mention_permission_check` | 问题中提到未授权组织直接拦截 |
| 行级权限过滤 | `apply_row_level_filter` | SQL 外层包组织范围 WHERE |
| SQL 只读执行 | 危险语句黑名单 | 禁止 INSERT/UPDATE/DELETE/DROP/ALTER |
| 异常自动修复 | Agent2Repair + 复核 | 减少因字段/语法问题导致的失败 |

**视觉建议**：盾牌分层图，五层安全网从外到内。

## P16 行级权限落地方式

三种方式适配不同数据现状：

| 方式 | 适用场景 | 实现 |
|---|---|---|
| 源表直接有组织编码 | 业务表已有 org_code / branch_code | `WHERE 组织编码 IN (授权范围)` |
| 源表只有组织名称 | 业务表有分公司名称等 | `WHERE 分公司名称 IN (授权范围)` |
| 新增业务组织映射表 | 组织关系复杂或缺少编码 | `JOIN business_org_mapping` |

推荐路线：先明确每个数据集的组织口径，再配置权限映射，最后做权限预检。

**视觉建议**：三种方式三列对比，标注推荐度。

## P17 部署形态与运行环境

- **交付形态**：预置数据源、模型、数据集、报告模板，用户只看见“智能分析工作台”
- **运行环境**：Docker Compose 三容器
  - `smartask-postgres`：PostgreSQL 16
  - `smartask-backend`：Flask API + bootstrap 自动初始化
  - `smartask-frontend`：nginx 静态托管 + `/api` 反代
- **首次启动**：自动完成 schema 迁移、元数据导入、业务数据快照导入
- **访问地址**：`http://localhost:8888`

**视觉建议**：Docker 容器拓扑图 + 一键部署命令。
