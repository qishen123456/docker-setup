# 基础版智能问数演讲稿（安吉尔经营分析场景版）

> 适用对象：面向安吉尔（或家电/净水行业）内部经营管理人员、区域销售负责人  
> 演讲时长：约 20–25 分钟

---

## P1 封面

各位领导、各位同事，大家好。今天我来介绍 SmartAsk 智能问数系统基础版，以及它如何帮助安吉尔各级经营人员更快、更稳地拿到销售数据。

安吉尔业务线多、渠道多、区域多。大区总监、省区经理、城市主管每天都有大量经营问题。SmartAsk 要做的就是：让这些人开口问一句，系统直接给出数据和结论，从“找人要数”变成“开口即得”。

---

## P2 项目定位

先明确我们的目标。

SmartAsk 不是做一个聊天机器人，也不是替代 BI，而是在企业经营分析场景下，构建一个“自然语言入口 + 可解释数据链路 + 确定性报告输出”的 Autonomous BI 最小闭环。

对安吉尔来说，这意味着：区域经理在手机上、在晨会上、在出差路上，用一句话就能问到自己想看的经营数据，而不用等总部出表。

---

## P3 传统经营分析的三重困境

我们先看一个最真实的场景。

假设华东大区总监周一早会时问了一句：“上周华东大区净水器零售额达成率是多少？哪些城市掉队了？”

在传统流程里，他要先找销售运营或 BI 同事，确认应该看哪张表——是出货数据、零售数据，还是安装完成数据；然后再由会写 SQL 的同事把语句写出来；跑完数还要人工整理成能看的结论。这个过程中，只要口径理解有一点偏差，比如把“出货”当成“零售”，数字就完全不同。

所以这里有三个痛点：

第一，响应慢。一个简单的问题，可能要等几个小时。
第二，门槛高。区域销售主管不懂 SQL，必须依赖总部数据团队。
第三，口径容易乱。大区、省区、城市公司各自拉表，出来的数可能对不上。

SmartAsk 基础版，就是要把这个流程变短、变快、变稳定。

---

## P4 设计原则一：先跑通最小闭环

基础版的定位非常聚焦：把“自然语言问数”这个最小闭环真正跑通。

什么是闭环？就是问题能进来、数据能查到、结果能展示、报告能沉淀。

对安吉尔来说，这意味着：一个省区经理输入“华东大区上周净水器达成率”，系统就能自动判断该查哪个数据集、生成 SQL、执行查询、返回一份包含 KPI、趋势、城市排名和风险提示的经营报告。

只有这个闭环先稳住了，后续增强准确率、增强可控性、增强平台治理能力才有意义。

---

## P5 设计原则二：基础流程稳定、进阶流程增强

围绕这个闭环，我们定了第二个设计原则：基础流程稳定、进阶流程增强。

系统内部有一个 AskFlowController，它决定本轮问题走基础流程还是进阶流程。

基础流程是稳定的四 Agent 引擎，服务 80% 的常规经营分析问题，比如“达成率是多少”“哪个大区最好”“某城市下面哪些经销商表现差”。

进阶流程则是通过 Skill 和工具链路处理更复杂的分析需求，比如跨数据集对比、归因分析、异常检测。进阶流程异常时，会自动回退到基础流程，不影响用户。

两套流程最终输出统一的结果契约，前端无感知。用户看到的始终是同一个问数界面和同一种报告格式。

---

## P6 设计原则三：三层解耦

第三个设计原则是三层解耦。

第一层是数据集知识层，包括 DDL、数据字典、LLD、Golden SQL、Agent Prompt。它回答的问题是：AI 是否懂安吉尔这个数据集？比如“净水器零售数据”里有哪些字段、字段含义是什么、常用口径怎么算。

第二层是报告契约层，定义指标、标准列、层级、阈值、信号灯、写作口径。它回答的问题是：SQL 结果如何变成安吉尔经营报告？比如达成率低于 80% 应该标红，高于 100% 应该标绿。

第三层是场景渲染层，根据问题动态识别 detail、comparative、ranking、diagnostic 等展示方式。它回答的问题是：这个问题该用哪种界面？比如“华东和华北对比”走对比布局，“哪个省区最好”走排名布局。

越底层越稳定，越上层越动态，这样报告既可控又灵活。

---

## P7 总体架构

整体架构上，前端是 Vue 3 + Element Plus + ECharts，后端是 Flask，核心模块包括 smart_chat 接口、AskFlowController、四 Agent 编排、ReportSpec v2 构建、报告契约配置和多数据源路由。数据层使用 PostgreSQL 存储元数据和业务数据，Chroma 做向量检索。整套环境通过 Docker Compose 一键部署。

对安吉尔而言，业务数据可以来自已有的销售系统、零售系统或安装系统，通过数据源配置接入 PostgreSQL，再由 SmartAsk 统一对外提供自然语言问数能力。

---

## P8 四 Agent 协作流水线

系统内部由四个 Agent 协作完成一次问数。

Agent1 是路由。它理解问题，并结合安吉尔的数据集元数据，判断应该查哪个业务口径。如果系统不确定，比如用户问“华东”但多个数据集都有华东口径，它会主动停下来让用户确认，而不是强行给出一个可能错误的答案。

Agent2 是 SQL 生成。路由确定后，Agent2 根据字段、字典、样例 SQL 写出查询语句。

Agent3 是复核。SQL 写出来之后，Agent3 会做安全检查：是不是只读？字段是否存在？聚合和过滤是否合理？

Agent4 是解读。SQL 执行成功后，Agent4 基于结果生成经营分析，比如“华东大区整体达成 92%，南京、杭州超额完成，合肥、济南低于预期”。

这四个 Agent 环环相扣，前面一个没通过，后面就不会继续。

---

## P9 Agent1 路由：不只是“选表”

Agent1 的工作不只是选表。它会综合多个信号：

- 数据集名称和别名，比如“净水器零售”“商用事业部”“消费者事业部”；
- 业务域命中，比如用户问的是销售额、达成率还是出货量；
- 组织树解析，比如“华东大区”“江苏省”“济南城市公司”分别对应哪个层级；
- 数据集画像，比如这个数据集包含哪些成员集合、统计口径是什么；
- 历史会话上下文，比如上一轮问的是哪个事业部；
- Golden SQL 相似度，比如这个问题和已沉淀的标准查询有多像。

当这些信号明确时，系统自动锁定数据集。当信号冲突或接近时，系统会返回确认卡片，让用户选择口径。

比如用户问“华东怎么样”，系统可能问：你想看净水器华东零售达成，还是商用事业部华东出货达成？

---

## P10 SQL 生成三层策略

这里我想特别说明一点：SmartAsk 不是每次遇到问题都完全依赖大模型去“蒙”一个 SQL。

系统内部有三层生成策略。

第一层是 Golden SQL 直执行。对于安吉尔已经沉淀下来的高频问题，比如“各大区月度达成率”“各城市公司零售额排名”，系统会直接匹配并执行人工维护的标准 SQL。这一层最快、最稳。

第二层是规则 SQL 兜底。对于高频模式，比如按事业部、大区、省区、城市公司、经销商层级下钻，系统有确定性规则可以直接生成 SQL，减少模型随机性。

第三层才是 Agent2 动态生成。只有当上面两层都覆盖不到时，才由大模型根据上下文动态生成 SQL。

这三层策略组合，既保证常见经营问题的稳定性，又保留了对新问题的泛化能力。

---

## P11 Agent3 复核与 Agent2Repair

Agent3 的复核非常关键。它会检查：

- SQL 是否只读，有没有危险语句；
- 字段是否存在，JSONB 字段读取方式是否正确；
- 聚合、过滤、排序、TopN 是否合理；
- 输出列是否符合报告契约的要求。

如果执行失败，系统会进入自动修复闭环。它会捕获数据库的真实错误，由 Agent2Repair 基于 failed_sql、error 和 DDL 尝试修复，修复后的 SQL 再经过 Agent3 复核、套行级权限、重新执行。如果仍然失败，系统不会崩溃，而是返回优雅降级结果，保留 SQL、review、错误诊断，方便排查。

---

## P12 报告契约与 ReportSpec v2

报告输出是我们非常重视的环节。我们不让大模型自由生成 HTML，因为那样不可控、不可解释、不可复现。

相反，我们让后端输出一个确定性报告协议，叫 ReportSpec v2。

报告契约定义了每个安吉尔数据集的标准输出列、核心指标、组织层级、风险阈值和信号灯规则。`report_spec_builder` 根据契约和问题场景动态生成 report_spec，包括：

- `analysisMode`：是单体分析、对比分析、排名分析还是风险诊断；
- `layoutTemplate`：用哪种页面布局；
- `kpis`：核心指标卡片；
- `sections` / `charts` / `accordions`：报告章节、图表、下钻结构；
- `provenance`：数据来源和口径说明。

前端按 report_spec 渲染，保证同一个问题每次展示结构一致，并且可以追溯到 SQL、数据集和字段。

---

## P13 前端信息分工：中间区看答案，右侧区看过程

前端设计上，我们参考了火山引擎 DataAgent 的体验。

中间区回答用户真正关心的问题，展示执行计划、关键进展、结果摘要和报告卡片。用户不需要看日志，就能看到“系统正在理解问题”“正在生成 SQL”“正在复核”“报告已生成”。

右侧区展示完整执行详情，包括 Skill 轨迹、路由分数、候选数据集、SQL、表格预览和自检提示。技术人员或运营人员可以在这里排查问题。

核心原则是：中间区不变成日志区，右侧区不变成第二份答案。

---

## P14 场景识别：一个问题该用哪种展示方式

`report_scene_registry.py` 会根据问题意图识别四类场景：

第一类 detail，单体分析。比如“华东大区上周业绩怎么样”，展示整体 KPI、趋势和可下钻的城市层级。

第二类 comparative，对比分析。比如“华东和华北的零售额对比”，用左右对称布局突出差异值和对比率。

第三类 ranking，排名分析。比如“各省区零售额排名”，展示名次、差距和红绿灯。

第四类 diagnostic，风险诊断。比如“为什么华东达成率低”，展示缺口、风险节点和改进建议。

测试验证显示，这四类场景识别准确率 100%，报告契约健康度 100/100。

## P15 企业级安全设计

在安吉尔这样的企业里，数据安全一定是最重要的。基础版做了五层控制。

第一是数据集访问权限。用户只能查询自己有权限的数据集，没授权的数据集系统会直接过滤掉。

第二是组织提及权限检查。如果用户问题中提到未授权组织，比如一个省区经理问到了其他省区的数据，系统会直接拦截。

第三是组织行级权限。即使能访问某个数据集，系统在执行 SQL 前也会自动包一层组织范围过滤，确保不会返回授权范围外的数据。

第四是 SQL 只读执行。系统禁止任何增、删、改操作，只允许查询。

第五是异常自动修复。如果 SQL 执行失败，系统会尝试自动修复并再次复核执行。

这五层组合起来，保证基础版在企业内网环境中可以放心使用。

## P16 行级权限落地方式

针对安吉尔的数据现状，行级权限有三种落地方式。

第一种，源表直接有组织编码。如果业务表里已经有 org_code、branch_code 这类字段，实现最简单，性能最好。

第二种，源表只有组织名称。如果业务表里没有编码，但有分公司名称、省区名称，可以作为过渡方案。

第三种，新增业务组织映射表。当组织关系比较复杂，或者业务数据缺少编码时，通过一张映射表把业务对象和组织树节点关联起来。这是我们最推荐的长期方案。

落地路线建议：先明确每个数据集的组织口径，比如净水器零售数据按“城市公司”归属；再配置权限映射；最后做权限预检，确保每个角色看到的数据范围正确。

## P17 部署形态与运行环境

基础版面向安吉尔业务用户时，交付形态非常轻量。

数据源、AI 模型、数据集和报告模板由交付方提前配置好。用户登录后，左侧菜单里基本上只看到一个入口：智能分析工作台。

用户在这个工作台上可以提问、看执行过程、查看报告、恢复历史。所有的后台管理工作，比如数据集维护、模型配置、报告模板调整，都不暴露给普通用户。

部署上推荐 Docker 一键部署，三个容器：PostgreSQL 数据库、Flask 后端、nginx 前端。首次启动会自动完成数据库迁移，并导入预置的知识库、运行配置和业务数据快照。

部署完成后，用户在浏览器里访问指定地址就可以登录使用。

## P19 基础版价值总结

对安吉尔来说，基础版带来五个价值。

第一，降低门槛。大区总监、省区经理、城市主管不用懂 SQL，也能自己查经营数据。
