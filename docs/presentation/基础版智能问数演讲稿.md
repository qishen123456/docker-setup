## P1 封面

【讲】

各位领导、各位同事，大家好。今天我来介绍 SmartAsk 智能问数系统的基础版。

我们过去做经营分析，经常遇到这样的情况：业务人员有一个很简单的问题，比如“上周达成率是多少”，但为了得到这个数，要经历找表、找人、写 SQL、对口径、整理表格这一长串过程。SmartAsk 基础版要解决的，正是把这个过程压缩成一句话：用户开口问，系统直接给答案。

---

## P2 从一个日常场景说起

【讲】

我们先看一个最真实的场景。

假设周一上午，商用事业部总监会后问了一句：“上周商用事业部整体达成率到底多少？”

在传统流程里，这个问题要经过几步：先找 BI 或数据同事，确认应该看哪张表；然后由会写 SQL 的同事把语句写出来；跑完数据还要人工整理成领导能看懂的结论。这个过程中，只要口径理解有一点偏差，出来的数字就可能不一样。

所以这里有三个痛点：

第一，响应慢。一个简单的问题，可能要等几个小时甚至半天。
第二，门槛高。业务人员不懂 SQL，必须依赖数据团队。
第三，口径容易乱。不同的人、不同时间出的数，可能对不上。

SmartAsk 基础版，就是要把这个流程变短、变快、变稳定。

---

## P3 基础版定位：先跑通最小闭环

【讲】

在介绍具体功能之前，我想先明确基础版的定位。

它不是要一步替代所有分析工作，也不是要做一个万能的数据机器人。它的目标非常聚焦：把“自然语言问数”这个最小闭环真正跑通。

什么是闭环？就是问题能进来、数据能查到、结果能展示、报告能沉淀。我们用一句话概括基础版：

“用户输入一句经营问题，系统自动识别数据集、生成 SQL、执行查询、生成经营报告。”

只有这个闭环先稳住了，后续增强准确率、增强可控性、增强平台治理能力才有意义。

---

## P4 基础版核心能力

【讲】

基础版面向业务用户，核心能力可以总结为六件事。

第一，自然语言提问。用户不需要写 SQL，直接像聊天一样输入业务问题。

第二，数据集自动路由。系统根据问题内容，自动判断应该查询哪个数据集。

第三，SQL 自动生成。系统会读取数据集的字段字典、样例 SQL 和上下文，生成可执行查询。

第四，SQL 安全复核。生成之后不是直接执行，而是先审核字段是否存在、语句是否只读、有没有风险。

第五，结果自动展示。查询结果会组织成表格、KPI、图表和文字解读。

第六，报告可沉淀。每一次问答都会留下历史记录，用户可以恢复当时的完整报告。

这六项能力组合在一起，就构成了一个业务人员可以直接使用的智能分析工作台。

---

## P5 四 Agent 协作：系统是怎么“思考”的

【讲】

下面我简单讲一下系统内部是怎么工作的。SmartAsk 基础版采用了四 Agent 协作的流水线。

Agent1 是路由。它的任务是理解用户的问题，并结合数据集元数据和会话上下文，判断应该查哪个数据集。如果系统对路由不够确定，它会主动停下来，让用户确认，而不是强行给出一个可能错误的答案。

Agent2 是 SQL 生成。路由确定之后，Agent2 根据数据集的字段、字典、样例 SQL 和报告配置，写出可执行的 SQL。

Agent3 是复核。SQL 写出来之后，Agent3 会做安全检查：是不是只读？字段是否存在？聚合和过滤是否合理？如果复核不通过，会返回诊断说明。

Agent4 是解读。SQL 执行成功后，Agent4 基于结果生成业务分析文本，把冷冰冰的表格变成可读的经营结论。

这四个 Agent 环环相扣，前面一个没通过，后面就不会继续，保证整个流程是可控的。

## P6 实际能问什么

【讲】

基础版能回答的问题，主要是经营分析中常见的几类。

第一类，总体达成。比如“商用事业部整体达成率是多少”。

第二类，排名对比。比如“哪个分公司完成最好”。

第三类，指标排行。比如“各分公司年度开单金额排名”。

第四类，下钻明细。比如“东部分公司下面哪些城市公司表现较好”。

这些问题都不需要用户写 SQL，也不需要用户提前知道表名和字段名。系统会根据问题自动完成后续所有步骤。

## P7 用户看到的界面

【讲】

从产品界面来看，用户主要和三块区域打交道。

左侧是历史分析区。这里保存了最近的问答记录，点击任何一条，都可以恢复到当时的报告状态。

中间是对话式问数区。用户在这里输入问题，系统会实时展示执行过程，比如“正在理解问题”“正在生成 SQL”“正在复核”等。

右侧或下方是经营报告区。这里展示最终的结果，包括摘要卡片、核心 KPI、趋势图表，以及可以下钻的组织层级结构。

整个界面非常简洁，业务人员不需要学习复杂操作，登录之后就能直接开始问数。

## P8 稳定策略：不是每次都靠大模型“蒙”

【讲】

这里我想特别说明一点：SmartAsk 不是每次遇到问题都完全依赖大模型去“蒙”一个 SQL。

系统内部有三层生成策略。

第一层是 Golden SQL 直执行。对于一些常见、口径已经沉淀下来的问题，系统会直接匹配并执行人工维护的标准 SQL。这一层最快、最稳。

第二层是规则 SQL 兜底。对于一些高频模式，比如组织层级排名、下级明细下钻，系统有确定性规则可以直接生成 SQL，减少模型随机性。

第三层才是 Agent2 动态生成。只有当上面两层都覆盖不到时，才由大模型根据上下文动态生成 SQL。

这三层策略组合，既保证常见问题的稳定性，又保留了对新问题的泛化能力。

## P9 安全与权限

【讲】

在企业管理场景里，数据安全一定是最重要的。基础版在几个关键环节都做了控制。

第一是数据集访问权限。用户只能查询自己有权限的数据集，没授权的数据集系统会直接过滤掉。

第二是组织行级权限。即使用户能访问某个数据集，系统在执行 SQL 前也会自动包一层组织范围过滤，确保不会返回授权范围外的数据。

第三是 SQL 只读执行。系统禁止任何增、删、改操作，只允许查询。

第四是异常自动修复。如果 SQL 执行失败，系统会尝试根据数据库的真实错误自动修复，并再次复核和执行。

这四点组合起来，保证了基础版在企业内网环境中是可以放心使用的。

## P10 基础版交付形态

【讲】

基础版面向最终业务用户时，交付形态是非常轻量的。

数据源、AI 模型、数据集和报告模板由交付方提前配置好。用户登录后，左侧菜单里基本上只看到一个入口：智能分析工作台。

用户在这个工作台上可以提问、看执行过程、查看报告、恢复历史。所有的后台管理工作，比如数据集维护、模型配置、报告模板调整，都不暴露给普通用户。

这种形态非常适合作为 first shot：先让业务人员用起来，验证问数闭环，再逐步开放更多管理能力。

## P11 部署方式

【讲】

部署方面，基础版推荐 Docker 一键部署。

整个运行环境由三个容器组成：PostgreSQL 数据库容器、Flask 后端容器，以及 nginx 前端容器。

首次启动时，后端会自动完成数据库迁移，并导入预置的知识库、运行配置和业务数据快照。也就是说，只要机器上装了 Docker，拿到代码和配置，执行一条命令就能跑起来。

部署完成后，用户在浏览器里访问 `http://localhost:8888` 就可以登录使用。

## P12 基础版价值总结

【讲】

最后总结一下基础版带来的价值。

第一，降低门槛。业务人员不需要懂 SQL，也能自己查经营数据。

第二，缩短响应时间。常规问题可以在几分钟甚至几十秒内得到结果。

第三，沉淀口径。通过 Golden SQL 和复核机制，减少不同人出数不一致的问题。

第四，建立底座。基础版跑通之后，我们可以继续往上叠加准确率增强、权限治理、平台化管理等能力。

---

## P13 当前局限与下一步

【讲】

当然，基础版并不是终点。它解决的是“能不能跑通”的问题，但“跑得多准、控得多稳”还需要后续版本持续提升。

当前基础版还有几个局限：

第一，组织名称识别有时候还不够准，尤其是简称、跨层级组织。
第二，当候选数据集接近或问题有歧义时，虽然系统会停下来确认，但确认体验还可以更自然。
第三，异常、日志、追踪等信息还没有完整暴露到管理面板。

这些正是中阶版要重点解决的问题。中阶版会在基础版之上，增强组织树识别、数据源锁定、二次确认、执行日志追踪和更细粒度的权限治理能力。
