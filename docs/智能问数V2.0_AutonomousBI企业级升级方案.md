# 智能问数 V2.0：AI 驱动的自主商业智能（Autonomous BI）企业级升级方案

> 文档版本：v1.0  
> 日期：2026-05-01  
> 状态：规划稿，未进入代码改造  
> 目标：把当前智能问数系统从“能回答是什么”升级为“能识别场景、解释为什么、自动归因、动态生成可视化报告、可审计、可恢复、可迁移、可运维”的企业级 Autonomous BI 平台。

---

## 1. 先说结论

当前系统已经具备四 Agent 问数链路、数据集配置、LLD、DDL、Golden SQL、报告配置、短期记忆、歧义确认、前端结构化报告和飞书同步基础。V2.0 不应该推倒重来，而应该在现有体系上做“企业级协议化升级”。

核心判断如下：

1. **不能继续写死组织层级和业务字符串**。例如“分公司、代表处、业务员”只能作为某个数据集配置里的枚举值，不能作为代码判断依据。
2. **Agent4 不应该决定报告结构**。报告结构必须由确定性引擎根据 `report_config + SQL rows + 用户问题意图` 生成，Agent4 只负责在受控结构里补充管理层洞察。
3. **准确率不能只靠 Prompt**。要靠语义层、Golden SQL、结果剖析、SQL 审核、回归题、数据溯源、用户反馈和自动修复形成闭环。
4. **新数据集接入必须是 AI 辅助、人工点选确认**。管理员不应手写复杂 JSON，而是由 AI 先识别，再由人点选确认，保存为结构化配置。
5. **权限、飞书、备份、迁移、审计从第一天纳入设计**。否则后期会变成补丁式治理，越改越难。

V2.0 的目标不是“多加几个图表”，而是形成以下闭环：

```text
数据集资料 -> AI 生成配置 -> 人工点选确认 -> 语义层固化
用户问题 -> 模式识别 -> SQL 生成/审核 -> 结果剖析 -> ReportSpec
ReportSpec -> 动态图表/文字/归因 -> 数据溯源 -> 用户反馈
反馈/失败/成功样本 -> 回归集/记忆库/Golden SQL -> 下一次更准
```

任何 V2.0 代码改造前，必须先做备份和基线记录。这个动作不是形式主义，而是为了保证“改坏了能回去、换服务器能复刻、上线前能比对”。

### 2.1 Git 备份流程

改造前执行：

```powershell
git status
git diff --stat
git branch backup/autonomous-bi-v2-before-YYYYMMDD-HHMM
git tag backup-autonomous-bi-v2-before-YYYYMMDD-HHMM
```

如果需要提交 AI 生成的改造代码，提交信息第一行必须以 `[#AI] ` 开头，例如：

```text
[#AI] Add Autonomous BI report specification engine
```

| 类型 | 位置/对象 | 备份目标 |

改造前必须保存一份基线报告：

- 当前能启动的前后端命令。
- 当前可用的 AI 模型配置。
- 当前可用数据集列表。

## 4. 模块一：动态组织架构与自适应分析引擎（The Brain）

### 4.1 分析模式识别

系统需要通过 Agent1、Agent2、上下文和结果结构共同判断分析模式，而不是单纯靠关键词。

| 模式 | 触发条件 | 输出形态 | 核心算法 |
|---|---|---|---|
| 下钻模式 Drill-down | 查询单体对象，如“东部分公司” | Root -> Branch -> Leaf 纵向拆解 | 问题实体匹配 + 组织树子节点展开 |
| 对比模式 Comparative | 查询多个同级对象，如“东分 vs 南分” | 并列对比、差异值、差异率、驱动因素 | 同级实体识别 + Delta 分解 |
| 全局模式 Top-down | 查询事业部整体、总体表现 | 分布、排名、风险、贡献度 | 全量节点分布 + Pareto |
| 穿透模式 Bottom-up | 查询极值，如“最差业务员” | 从叶子节点反推上级影响 | Leaf ranking + 上级链路回溯 |
| 诊断模式 Diagnostic | 查询“为什么、原因、下滑、异常” | 根因候选、差值贡献、管理建议 | Variance attribution + 异常检测 |

### 4.2 模式识别信号

模式识别不能只靠 LLM，要结合四类信号：

1. **问题文本信号**：是否出现“为什么、对比、哪个更好、最差、整体、下钻、原因”。
2. **实体匹配信号**：命中的实体数量、实体层级、是否同级、是否父子关系。
3. **结果结构信号**：SQL rows 是否包含 `nameColumn / parentColumn / levelColumn / metrics`。
4. **历史上下文信号**：用户上一轮是否正在看某个分公司或某张图。

### 4.3 下钻模式

下钻模式的核心不是写死“分公司 -> 代表处 -> 业务员”，而是：

```text
当前问题命中节点 -> 该节点直接子节点 -> 子节点叶子明细
```

例如：

- 商用事业部数据集：东部分公司 -> 代表处 -> 业务代表。
- 门店数据集：华东大区 -> 门店 -> 店员。
- 项目数据集：事业群 -> 项目组 -> 项目。

输出要求：

- 第一屏先展示当前节点总 KPI。
- 第二屏展示子节点组合图：金额柱 + 比率线。
- 点击子节点展开叶子明细组合图。
- 每个图必须有一段管理层文字说明。
- 所有层级名来自配置和数据，不来自代码常量。

### 4.4 对比模式

对比模式禁止 `Sum(A) + Sum(B)` 式偷懒。系统必须输出：

| 指标 | 说明 |
|---|---|
| A 值 | 对象 A 的指标值 |
| B 值 | 对象 B 的指标值 |
| Delta | `A - B` 或 `B - A` |
| Delta Rate | 差异率 |
| Contribution | 差异贡献因素 |
| Driver Nodes | 拉开差距的下级节点 |

对比模式图表：

- 两个对象：并列双轴图或镜像柱状图。
- 多个对象：分组柱状图 + 达成率折线。
- 下级驱动因素：Top positive / Top negative contribution。

### 4.5 全局/穿透模式

全局模式用于回答“整体怎么样”。穿透模式用于回答“最差是谁、风险在哪里、最大缺口在哪里”。

必须支持：

- Pareto 贡献度分析。
- 风险节点 TopN。
- 高贡献低达成节点识别。
- 叶子节点异常反推上级链路。
- 组织分布热力视图，后续可扩展。

### 4.6 归因分析 Agent（Diagnostic Agent）

Diagnostic Agent 不直接凭空解释原因，而是基于可计算证据输出“根因候选”。

执行步骤：

1. **确定被解释指标**：例如达成率、销售金额、开单金额、剩余任务。
2. **建立基准**：目标值、同期值、上级均值、同级均值或历史均值。
3. **拆解贡献**：按下一层级计算差值贡献。
4. **识别异常**：低于阈值、环比下降、贡献占比异常、目标缺口异常。
5. **生成结论**：输出“谁拉低了多少、为什么值得关注、下一步看哪里”。

示例输出目标：

```text
东部分公司整体达成率偏低，主要由河南代表处和湖北代表处拉低。河南代表处任务 1380 万、开单 58.82 万、缺口 1321.18 万，对东部分公司缺口贡献最高；其下袁浩东达成率仅 0.30%，是当前最需要跟进的关键差值贡献者。
```

## 5. 模块二：配置驱动的零代码接入（The Skeleton）

### 5.1 Dataset Profile

Dataset Profile 是数据集的机器可读说明书，建议在现有 `bs_dataset_report_config.config_json` 基础上升级。

核心字段：

```json
{
  "version": "2.0",
  "datasetId": 1,
  "businessDomain": "商用事业部经营分析",
  "semanticLayer": {
    "entities": [],
    "metrics": [],
    "dimensions": [],
    "timePolicy": {}
  },
  "hierarchy": {
    "nameColumn": "节点名称",
    "parentColumn": "上级名称",
    "levelColumn": "层级",
    "trackColumn": "条线",
    "knownPaths": []
  },
  "report": {
    "kpiCards": [],
    "signalRules": [],
    "defaultExpandPolicy": "risk_and_top"
  },
  "security": {
    "permissionColumns": [],
    "maskingRules": []
  }
}
```

### 5.2 AI 辅助配置助手

管理员上传或选择数据样本后，AI 自动完成初稿：

1. 识别名称列、上级列、层级列、时间列、权限列。
2. 识别指标列和格式：金额、百分比、数量、枚举。
3. 推断指标语义：目标、完成、达成率、缺口、人数。
4. 推断层级路径：例如事业部 -> 分公司 -> 代表处 -> 业务代表。
5. 生成 Golden SQL 候选和常见问题候选。
6. 生成 Agent Prompt Pack 初稿。

人工确认方式必须是点选式：

- 下拉选择列名。
- 多选确认指标。
- 拖拽调整层级路径。
- 预览树结构和报告。
- 保存前跑配置校验。

### 5.3 语义层映射

报告层不直接消费数据库原始列名，而消费统一语义 key。

示例：

| 原始列 | 语义 key | 报告名称 | 格式 | 角色 |
|---|---|---|---|---|
| `sales_amt` | `actual` | 销售金额 | amount | bar_actual |
| `revenue` | `actual` | 销售金额 | amount | bar_actual |
| `年度开单金额` | `actual` | 年度开单金额 | amount | bar_actual |
| `达成率` | `rate` | 达成率 | percent | line_rate |

好处：

- 换数据集不改前端。
- Agent2 生成 SQL 时知道真实列名。
- ReportSpec 只使用语义 key。
- Agent4 看到的是业务名称，不需要理解数据库字段。

### 5.4 配置版本化与可恢复

每次保存配置都要生成版本：

| 表/对象 | 用途 |
|---|---|
| `bs_dataset_report_config` | 当前生效配置 |
| `bs_dataset_report_config_versions` | 历史版本 |
| `bs_dataset_config_audit` | 谁在何时改了什么 |
| JSON 导出 | 跨服务器迁移 |

必须支持：

- 一键回滚到上一版。
- 导出配置包。
- 导入配置包。
- 配置差异对比。
- 配置预览不影响线上生效版本。

## 6. 模块三：交互式可视化报表（The Face）

### 6.1 ReportSpec 统一协议

前端、PDF、飞书卡片都消费同一份 ReportSpec。

```json
{
  "version": "2.0",
  "question": "东部分公司业绩怎么样？",
  "analysisMode": "drill_down",
  "scope": {},
  "kpis": [],
  "sections": [],
  "charts": [],
  "accordions": [],
  "narrative": [],
  "provenance": []
}
```

### 6.2 左侧文字结论

左侧不应该堆执行过程，而是输出管理层能读的分层结论：

1. **整体判断**：一句话说明好坏和风险。
2. **关键指标**：任务、完成、达成率、缺口。
3. **主要驱动**：哪些下级节点拉高或拉低。
4. **异常节点**：风险对象、金额缺口、负责人。
5. **建议动作**：跟进方向、优先级、下一问建议。

异常数据要高亮，但高亮必须来自 `signalRules`，不能让前端随意判断。

### 6.3 右侧可视化视窗

右侧采用“先总览、再下钻”的 BI 产品结构：

- KPI 卡片阵列。
- 当前层级对比组合图。
- 手风琴下钻卡片。
- 点击展开子级组合图。
- 每个图配一段 AI 结论。
- 图表支持放大、数据表切换、来源查看。

不同模式对应不同视图：

| 模式 | 右侧默认图表 |
|---|---|
| 下钻 | 当前节点子级组合图 + 手风琴下钻 |
| 对比 | 分组柱状图 / 并列双轴图 / 差异贡献图 |
| 全局 | 分布图 / Pareto / 风险 TopN |
| 穿透 | 极值榜单 + 上级链路图 |
| 诊断 | 差值贡献瀑布图 + 根因列表 |

### 6.4 视觉预警系统

预警颜色、阈值、文案全部来自配置：

```json
{
  "signalRules": [
    { "metric": "rate", "op": ">=", "value": 100, "tone": "good", "label": "优秀" },
    { "metric": "rate", "op": ">=", "value": 80, "tone": "warn", "label": "关注" },
    { "metric": "rate", "op": "<", "value": 80, "tone": "danger", "label": "预警" }
  ]
}
```

应用范围：

- KPI 卡片。
- 图表数据点。
- 文本结论。
- 飞书卡片颜色。
- 风险列表排序。

## 7. 模块四：可靠性与可解释性（The Shield）

### 7.1 数据溯源

每个指标、图表、AI 结论旁边提供“查看来源”。点击后展示：

- SQL 语句。
- SQL 生成所用数据集配置版本。
- 参与计算的数据行。
- 指标公式。
- Agent3 审核结论。
- 数据权限过滤条件。

建议结构：

```json
{
  "provenanceId": "p_001",
  "metricKey": "rate",
  "sql": "...",
  "rows": [],
  "configVersion": "2026-05-01T02:00:00",
  "permissionFilter": "department in (...)"
}
```

### 7.2 可解释推理摘要

企业系统不建议展示完整模型私有思维链。应展示“可审计推理摘要”。

可展示内容：

- 本次识别为下钻/对比/诊断模式的原因。
- 使用了哪些指标和层级。
- 为什么判定某节点是风险。
- 归因计算的差值贡献。
- SQL 审核通过点。

不展示内容：

- 模型内部草稿。
- 不可验证的联想。
- 未经 SQL 或配置支持的推断。

### 7.3 99% 准确率策略

“99% 准确”不能承诺靠模型一次生成达到，必须用工程闭环逼近。

| 机制 | 作用 |
|---|---|
| Golden SQL | 固定高频问题正确写法 |
| 回归题库 | 每次改造后自动验证 |
| SQL AST 审核 | 防止危险 SQL 和权限绕过 |
| 结果剖析 | 检查空结果、异常列、层级缺失 |
| 配置校验 | 防止列名、指标、层级配置错误 |
| 数据溯源 | 让用户能核对每个结论 |
| 用户反馈 | 错误答案沉淀为失败样本 |
| 自动修复 | SQL 错误时查 schema、枚举、样本后重试 |

建议指标：

- 高频问题 SQL 通过率 >= 99%。
- 低频问题 SQL 可执行率 >= 95%。
- 报告结构渲染成功率 >= 99%。
- 权限过滤绕过率 = 0。
- 关键指标可溯源覆盖率 = 100%。

## 8. 数据权限与安全体系

### 8.1 权限模型

建议采用 RBAC + ABAC：

| 层级 | 说明 |
|---|---|
| RBAC | admin、leader、analyst、viewer |
| ABAC | 用户部门、组织范围、数据集范围、字段权限 |
| Row-level | 按组织、区域、部门、负责人过滤 |
| Column-level | 敏感字段脱敏或隐藏 |

### 8.2 数据权限注入位置

权限必须在后端强制执行，前端不可绕过。

推荐链路：

```text
JWT / 飞书用户 -> 用户权限上下文 -> Agent2 SQL -> Agent3 审核 -> 权限 SQL 改写 -> 只读执行
```

关键要求：

- admin 可配置权限，但所有操作审计。
- leader 只能看授权组织范围。
- SQL 执行前必须注入权限条件。
- Agent Prompt 里不能让模型自己决定权限。
- 数据溯源里展示权限过滤摘要。

### 8.3 审计日志

记录以下事件：

- 用户登录。
- 问数请求。
- 数据集配置变更。
- SQL 执行。
- 权限过滤。
- 导出报告。
- 飞书推送。
- 管理员操作。

## 9. 飞书打通方案

### 9.1 飞书能力范围

V2.0 飞书集成不只是同步，而是成为企业入口：

1. 飞书 OAuth 免登。
2. 飞书组织架构同步。
3. 飞书用户与系统用户绑定。
4. 飞书机器人推送分析结果。
5. 飞书卡片内查看摘要、跳转完整报告。
6. 后续支持飞书内发起问数。

### 9.2 飞书与权限联动

飞书部门和用户信息可以作为权限来源之一：

```text
Feishu Department -> 系统组织范围 -> 数据权限 -> SQL 权限过滤
```

需要注意：

- 飞书组织架构不一定等于业务数据组织架构。
- 必须提供映射表，而不是直接把飞书部门当业务部门。
- 映射关系需要可配置、可审计、可回滚。

### 9.3 飞书卡片体验

分析完成后推送卡片：

- 标题：问题摘要。
- 状态：绿/黄/红。
- 核心 KPI：最多 4 个。
- 关键结论：最多 3 条。
- 按钮：查看完整报告。
- 链接携带 `query_id`，系统恢复同一份 ReportSpec。

## 10. 配置、存储、恢复与迁移

### 10.1 哪些东西必须持久化

| 对象 | 是否必须持久化 | 原因 |
|---|---|---|
| 数据集资料 | 是 | LLD、DDL、Golden SQL、Prompt 是核心资产 |
| report_config | 是 | 报告渲染和语义层依赖 |
| 配置版本 | 是 | 支持回滚和审计 |
| 会话历史 | 是 | 支持恢复、飞书跳转、追问上下文 |
| ReportSpec | 是 | 保证报告可复现 |
| SQL 与结果摘要 | 是 | 数据溯源、审计、回归 |
| 用户反馈 | 是 | 准确率闭环 |
| 向量索引 | 可重建但建议备份 | 加速恢复 |
| 日志 | 建议保留周期 | 排障与审计 |

### 10.2 可恢复会话

每次问数完成后保存：

- `query_id`
- 用户信息
- 问题
- 路由结果
- SQL
- 数据集配置版本
- ReportSpec
- Agent 输出
- Provenance
- 飞书推送状态

这样用户点击飞书卡片或历史记录时，不需要重新跑模型，也能 100% 复刻当时报告。

### 10.3 快速迁移到其他服务器

目标：新服务器执行一套导入流程，即可复刻现有项目。

迁移包包含：

```text
source_code.zip / git repo
env.example
config_export.zip
postgres_dump.sql
report_config_export.json
dataset_profile_export.json
chroma_backup.zip
docker-compose.yml
restore.ps1 / restore.sh
```

恢复流程：

1. 拉取代码。
2. 复制 `.env`。
3. 启动 Docker Compose。
4. 导入 PostgreSQL dump。
5. 恢复配置与向量库。
6. 执行健康检查。
7. 执行标准问数回归。

## 12. Agent Prompt 与数据集资料打磨体系

### 12.1 Prompt Pack

每个数据集维护一套 Prompt Pack：

| Prompt | 作用 |
|---|---|
| Agent1 Prompt | 路由、歧义、模式识别 |
| Agent2 Prompt | SQL 生成、字段口径、Golden SQL 使用 |
| Agent3 Prompt | SQL 审核、权限、安全、口径检查 |
| Agent4 Prompt | 管理层洞察、归因、建议，不负责报表结构 |
| Diagnostic Prompt | 为什么、异常、差异驱动、根因候选 |

### 12.2 Prompt 质量评估

不能靠肉眼感觉，要建立评估集：

- 每个数据集至少 30 道标准题。
- 高频经营题至少 10 道。
- 对比题至少 5 道。
- 归因题至少 5 道。
- 权限边界题至少 5 道。

评估维度：

- 路由是否正确。
- SQL 是否可执行。
- 指标口径是否正确。
- 是否遵守权限。
- 报告结构是否正确。
- 结论是否可由数据支撑。

### 12.3 自动打磨流程

```text
失败问题 -> 失败分类 -> 修复 SQL/Prompt/配置 -> 加入回归题 -> 重新测试 -> 通过后发布
```

失败分类：

- 数据集路由错误。
- 字段名错误。
- 时间口径错误。
- 层级混淆。
- 权限缺失。
- 报告结构错误。
- 归因无数据支撑。

## 13. 人机确认策略

用户不能被频繁打断，但不确定时必须确认。

### 13.1 需要确认的情况

- 多个数据集得分接近。
- 同一个名词在多个层级出现。
- 时间范围缺失且影响很大。
- 指标口径存在多个版本。
- 用户权限导致结果被过滤。
- 诊断结论缺少必要对比基准。

### 13.2 确认方式

确认必须是少量、明确、可点击的：

```text
你说的“东部”可能有两个口径：
1. 东部分公司（区域经营口径）
2. 东部业务部（行业条线口径）
请选择本次分析口径。
```

系统应记住用户选择，下次优先使用。

## 15. 验收标准

### 15.1 产品体验验收

- 用户打开系统即可问数，无需理解数据集技术细节。
- 问单体对象时，自动下钻。
- 问多个对象时，自动对比差异和驱动因素。
- 问“为什么”时，输出可验证归因。
- 图表、文字、KPI、风险颜色一致。
- 不默认铺开思考过程和 SQL，详情通过“查看来源”进入。

### 15.2 准确性验收

- 高频标准题 SQL 正确率 >= 99%。
- 回归题全部自动执行。
- 所有关键指标可溯源。
- Agent4 结论必须引用已有指标或节点。
- 权限过滤不可绕过。

### 15.3 工程验收

- 前端 build 通过。
- 后端健康检查通过。
- Docker 启动通过。
- 配置可导入导出。
- PostgreSQL 可备份恢复。
- 飞书联调通过。

### 15.4 运维验收

- 一键备份。
- 一键恢复。
- 新服务器迁移手册可执行。
- 日志可查。
- 失败可定位。
- 发布可回滚。

## 16. 风险与控制

| 风险 | 控制措施 |
|---|---|
| LLM 幻觉 | ReportSpec 由程序生成，LLM 只补文字 |
| 新数据集配置错误 | AI 识别 + 人工点选 + 配置预览 + 回归题 |
| 权限绕过 | 后端 SQL 强制注入，前端不参与授权判断 |
| 报告结构失真 | Result Profiler 标准化，前端只消费协议 |
| 迁移失败 | Docker + 配置导出 + PostgreSQL dump + 恢复演练 |
| 飞书组织与业务组织不一致 | 建立映射表，不直接硬绑定 |
| Prompt 越改越乱 | Prompt Pack 版本化 + 失败样本回归 |

## 17. 下一步建议

建议下一步不要立刻写大段代码，而是先做 P1 的协议冻结：

1. 把当前商用事业部数据集映射成 Dataset Profile v2。
2. 用“东部分公司业绩怎么样？”手工产出一份目标 ReportSpec v2 样例。
3. 用“东分和南分哪个完成得更好？”产出对比模式 ReportSpec 样例。
4. 用“为什么东部分公司业绩低？”产出诊断模式 ReportSpec 样例。
5. 确认协议能覆盖你的真实管理诉求后，再进入代码改造。

这一步做扎实，后面所有 Agent、前端、飞书、权限、备份和测试都会有统一标准，不会再出现“修一个图表又误伤另一个报告”的问题。
