## 缺陷定位：报告"风险提醒"自相矛盾（问"山东分公司业绩"）

现象：同一份报告里写"淄博城市公司达成率7.72%"，紧接着"风险提醒：暂无低于10%风险线的明显节点"。

定位结论：**Agent4 LLM 幻觉，非规则代码 bug**。证据：
- 全项目 grep「风险线」只有 3 处：four_agent_ask.py:2216/2256（规则兜底模板，阈值写死 **20%**）、create_consumer_standard_dataset.py:570（示例问题文案）。**没有任何地方定义过 10% 风险线**——这个数字是 LLM 自己编的。
- 用户报告里的小节名「覆盖范围 / 重点发现 / 风险提醒」在规则模板中不存在（规则模板固定为 核心结论/亮点分析/问题诊断/改进建议，见 2198-2264），说明走的是 Agent4 LLM 自由生成路径，非 `_build_fallback_analysis`。
- 规则兜底只在 dataset_code ∈ {angel_business_2026, angel_business_2026_phase1} 时触发（four_agent_ask.py:9423）；其他数据集全部交给 LLM。
- 全局报告标准（four_agent_ask.py:9438-9449，共 9 条）第 5 条只约束"最优对象<60% 红线"，**没有定义风险阈值概念，也未要求 LLM 校验自述数字与结果表一致**。
- 后置校验也接不住：`self_check.py` 只查 dataset_results 空否/路由匹配/最优达成率<60，**不做报告文本与数据的一致性核对**；`conclusion_advice.py:39` 同样只有 60% 一条。且 advanced 引擎默认关闭（需 feature_flag advanced_ask_flow + super_admin），basic 路径下这些技能压根不跑 → Agent4 输出零校验直达前端。

结构性根因：**报告契约层缺「事实一致性校验器」**（数值断言 vs 结果行）。属随机复现的 LLM 幻觉，不稳定复现。

建议方向（未实施）：① 全局标准补一条"风险阈值必须来自报告配置，禁止自造数字"；② 新增 fact_check 后置技能，从报告 markdown 抽取数值断言与 dataset_results 逐条比对，矛盾即打回重写或降级为规则模板；③ 把风险阈值收敛到 dataset_report_config 单一来源（当前 20%/60% 两套并存且未下发给 LLM）。

## 缺陷定位：历史记录恢复后与实时问数界面不一致

复现方式：问「山东分公司的业绩」→ 刷新前后端 → 从历史记录恢复 → 界面不同。

**数据层清白（实测证实）**：用 token 直调 `/api/smart-chat` 与服务端 `config/smartask_report_history.json` 里同一问题的快照做字段级 diff —— result 顶层 21 字段全同、dataset_results[0] 字段全同、SQL 完全一致、rows 6 行内容完全一致。唯一"差异"是 `6105486.0` vs `6105486` 的 JSON 浮点序列化噪声（JS 中等价，不影响渲染）。analysis 文本不同属 LLM 每次重写，非快照问题。

**差异 100% 在前端渲染层，根因链**：
1. `useSmartAskReportHistory.js:175` `restoreHistory` 里 `session.state.logs = []`；而 `buildReportHistorySnapshot`(60-78) **从未持久化 session.state.logs**。
2. `SmartAsk.vue:3929-3942` 的 `isCurrentResult` 判定包含 `session.state.logs.length > 0` → 历史恢复后恒 false。
3. 于是步骤卡片走 3944-3980 的**硬编码伪步骤**分支（"已完成问题理解与执行规划 / 已完成数据检索 X / 已生成经营分析报告"），而实时显示的是真实 5 步 trace（Agent1 语义路由 / 规则 SQL 兜底生成 / Agent3 全量复核 / 系统执行 SQL / Agent4 业务解读，各带真实耗时）。
4. `isCurrentSessionMessage`(3983-3990) 同样恒 false，连带影响 currentSessionAiMessage 等分支。
5. 次要：AI 消息恢复只给 data 不给 content（130-135）；messages 上限 30；detailReportResult/startedAt/currentSessionId 全被清空。

**未提交改动（"完全保留快照"重构）引入的新风险**（改动已 build 进两个容器，正在生产运行）：
- `MAX_ITEMS_PER_SCOPE` 200→20：服务端只留 20 条，前端仍按 50 请求，超出部分静默永久丢失。
- 删除 `filterResultDatasets` / `isDatasetVisible` 校验（useSmartAskReportHistory.js）→ 历史恢复不再做数据集权限过滤，**越权风险**：权限回收后仍可从历史看到完整报告与 SQL；原有 ElMessage 提示也被删。
- `mergeHistoryItems` 改为服务端绝对优先（本地仅在服务端无同 ID 时补充）+ `pushHistoryToServer` 静默吞掉所有非 stale 错误 → 一旦某次 POST 失败，本地更新永远上不去，刷新即回退到服务端旧版本。**这是"刷新前后不一样"的机制性成因。**
- 取消 rows/report_spec/messages 裁剪 → 单条快照均 ~385KB，`smartask_report_history.json` 已达 **7.5MB / 11 条**，且为整文件读写（每次 upsert 全量重写）；前端本地 20 条约 7.5MB > localStorage 5MB 上限，**必然触发 quota 后降级 aggressive 强压缩**，"完全保留"在本地根本无法达成。
- 删除 `_has_self_parent_anomaly` 与 focusNodeIsLeaf 校验 + 删掉配套测试 `test_smartask_report_history_store_self_parent.py` → 之前修掉的"每个分公司下挂同名城市公司"脏数据快照会在历史里复现。
