## 真正根因：LLM(Agent1) 主体解析层级错误（用户报告"商用事业部丁杰的业绩"没解决）

用户反馈"商用事业部丁杰的业绩"仍然问不出来。排查发现前几轮修的 `_extract_followup_org_target` / `_extract_bare_org_subject_by_node_index` 都只是 **fallback**，真正主体解析走的是 `_agent1_resolve_org_subject`（line 8742），它**先调 LLM**(DeepSeek-V4-Pro)，fallback 仅在 LLM 返回空时才用。

**容器内真实 LLM 调用验证**：
- Q="商用事业部丁杰的业绩"
- LLM 返回: subject_name='商用事业部', rewritten='商用事业部的业绩'  ← 错（取了上层事业部）
- fallback(我修的): '丁杰'  ← 对，但没被用
- line 8802 `result.get("subject_name") or fallback_name` 直接采信 LLM 非空结果

**根因**：LLM 把"事业部+人名"误判为上层事业部，且结果未经层级校验直接采用。

**修复**（2 处编辑，全在 four_agent_ask.py）：
1. 新增 `_subject_node_level(name)` + `_pick_finer_subject(llm, fallback)`：比较两者节点层级，取更细的（业务代表>城市公司>分公司>事业部），层级相同尊重 LLM
2. `_agent1_resolve_org_subject` line 8802：`subject_name = self._pick_finer_subject(llm_subject, fallback_name)` + rewritten_question 一致性校验（subject 被纠正时同步重写）

**验证**（容器内真实 LLM，5/5 PASS）：
- "商用事业部丁杰的业绩" → 丁杰 ✓（之前 LLM 返回商用事业部）
- "消费者事业部万州的业绩" → 万州 ✓
- "商用事业部的业绩" → 商用事业部 ✓（纯事业部保留，不过度纠正）
- "丁杰的业绩" → 丁杰 ✓

**关键教训**：
1. 前几轮只测了 fallback 路径（regex），没测主路径（LLM），导致"修复了但没生效"。以后主体提取改动必须测真实 LLM 调用
2. LLM 非确定性，不能盲信——必须有确定性校验层（节点索引层级比较）兜底
3. 用户反馈"没解决"时，第一时间要在真实调用链里复现，不能只在打桩环境里验证

## 端到端完整测试找到真正的根因链（用户要求"自己测试别让我测"）

用户质疑前几轮修复没生效，要求我自己走完整调用链测试。通过 `svc.ask()` 直接调用（绕过 HTTP 鉴权）发现：

**根因链（三层串联）**：
1. `_agent1_resolve_org_subject` 主体纠正 → `subject_name='丁杰'` ✓
2. `rewritten_question='商用事业部丁杰的业绩'`（保留了原始组织前缀）→ effective_question 虽然对但路由层拿到原始问题
3. `ask()` line 10461: `route_question = question if _looks_like_org_subject_question(question) else effective_question` → 因为问题含"事业部"返回 True，route_question 用了原始问题
4. `route_with_agent1` line 5434: `org_source_question = current_question or question` → current_question=question（原始），路由层再次识别出 `商用事业部`
5. 路由层 `organization_mentions=[{'node_name':'商用事业部'}]` → 触发数据权限校验 → 当前账号无权限 → error

**修复（2 处）**：
1. `_agent1_resolve_org_subject` rewritten_question 重写逻辑：subject 被纠正时必须重写为 `f"{subject_name}的{metric}"`，不能保留原始组织前缀（"商用事业部丁杰的业绩"→"丁杰的业绩"）
2. `ask()` line 10461-10468: `route_question` 和 `current_question` 都改为 `effective_question or question`，不再用原始 question 做路由

**端到端验证（svc.ask 完整调用链）**：
```
effective_question: '丁杰的业绩'           ← 主体纠正 ✓
route.organization_mentions: None           ← 不再误识别商用事业部 ✓
route.refined_query: '丁杰的业绩'           ← 路由用纠正后问题 ✓
route.dataset_ids: [3]                      ← 正确路由
error: None                                  ← 不再报权限错误 ✓
SQL: WHERE 业务代表 IN ('丁杰')             ← SQL 正确过滤丁杰 ✓
```
（row_count=0 是因为测试用 fake_user 没真实数据权限，WHERE 1=0 是权限隔离层，真实用户有权限时不会清空）

**关键教训**：
1. 主体提取改了不够，必须改到路由层用纠正后的 effective_question，否则路由层会用原始问题再识别一遍组织
2. rewritten_question 不能保留原始组织前缀，必须重写为纯 subject
3. **必须走完整 svc.ask() 调用链测试**——只测 `_agent1_resolve_org_subject` 或 `_extract_followup_org_target` 单个方法，会漏掉路由层的二次识别
4. HTTP 鉴权绕过方法：直接在容器内 Python 实例化 FourAgentAskService，传 fake_user，走 svc.ask()
