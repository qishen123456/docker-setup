## 简介

主体提取是 SmartAsk 问数系统的第一步：从用户问句中识别出组织节点或人名（如 "迟昊"、"三明城市公司"、"商用事业部丁杰"），再交给 SQL 生成和报告渲染。

如果主体提取失败，后续整条链路都会返回「未查询到匹配数据」——即使用户问的节点在数据集里确实存在。

本文记录 2026-08-01 修复的 5 个 bug 类（共 7 个具体坑），以及排查方法和验证脚本。

## 两条提取路径

```
用户问句
  │
  ├─ _extract_followup_org_target(question)     ← 追问链路（优先）
  │    └─ 已委托 → _extract_bare_org_subject_by_node_index
  │
  └─ _extract_bare_org_subject_by_node_index(question)  ← 裸题器
       ├─ 1. _clean_org_subject_candidate → 精确匹配 alias
       ├─ 2. _contains_match_subject(cleaned) → contains + 层级优先
       └─ 3. _contains_match_subject(raw_question) → raw 兜底（倒桩）
```

**关键**：追问链路（`four_agent_ask.py` line ~8749: `followup or bare`）优先于裸题器。如果 followup 返回非空（即使错误），裸题器不跑。

## 常见故障与修复

### 故障 1：返回「未查询到匹配数据」（节点明明存在）

**最常见根因**：追问链路 `_extract_followup_org_target` 返回了错误非空值，阻断了裸题器。

**排查**：
```bash
docker exec smartask-backend python -c "
from four_agent_ask import FourAgentAskService
import json
with open('/app/config/dataset_node_index.json') as f:
    idx = json.load(f)
svc = FourAgentAskService.__new__(FourAgentAskService)
svc._dataset_node_index = idx
svc._GENERIC_LEVEL_ALIASES = FourAgentAskService._GENERIC_LEVEL_ALIASES
q = '迟昊看下这个人的业绩'
print('followup:', repr(svc._extract_followup_org_target(q)))
print('bare:    ', repr(svc._extract_bare_org_subject_by_node_index(q)))
"
```

如果 followup 返回非空但错误（如 "迟昊看下人"），裸题器被阻断。

**修复**：追问链路已委托裸题器（`return self._extract_bare_org_subject_by_node_index(question)`）。如果仍出现此问题，检查追问链路是否被改回旧实现。

### 故障 2：名字首字被吃掉

**现象**：`三明的业绩` → cleaned 变成 "明"，`四川代表处的业绩` → "川代表处"。

**根因**：`_clean_org_subject_candidate` 的去数量词正则把首字中文数字当数量词剥掉。

**修复**：计数词必须跟量词（个/位/名...）才剥。正则中量词后面的 `?` 不能加（必须是 mandatory）。

### 故障 3：事业部+人名取错

**现象**：`商用事业部丁杰的业绩` → 返回 "商用事业部" 而非 "丁杰"。

**根因**：旧前缀匹配（`startswith`）挑最长 alias，"商用事业部" 比 "丁杰" 长。

**修复**：`_contains_match_subject` 用 contains 匹配 + 层级优先（`_NODE_LEVEL_PRIORITY`：业务代表=1 > 事业部=6），取最细层级而非最长 alias。

### 故障 4：倒桩/名字在后半句

**现象**：`这个人的业绩丁杰` → 返回空。

**根因**：cleaner 的 `业绩.*` 正则把 "业绩丁杰" 整体吃掉。

**修复**：裸题器第 3 步对原始问句做 contains 匹配（raw 兜底），绕过 cleaner。

### 故障 5：口语前缀/指代/量词未覆盖

**现象**：`查询丁杰`、`看下这位丁杰的业绩`、`一位丁杰的业绩`、`我想知道丁杰的业绩` 全部失败。

**修复**：cleaner 正则补 `查询|我想知道|帮我看看|麻烦帮我查下`、`这位|那位`、`一|二`、`位|名`。

### 故障 6：LLM(Agent1) 主体解析层级错误（最隐蔽）

**现象**：fallback(regex) 全修好后，用户问 `商用事业部丁杰的业绩` 仍然查的是「商用事业部」而非「丁杰」。

**根因**：主体解析**主路径**是 `_agent1_resolve_org_subject`（先调 LLM），fallback 仅在 LLM 返回空时才用。LLM(DeepSeek-V4-Pro) 把"事业部+人名"误判为上层事业部（`subject_name='商用事业部'`），非空结果被直接采信，fallback 的 `丁杰` 没机会执行。

**验证**（必须走真实 LLM）：
```bash
docker exec smartask-backend python -c "
import sys; sys.path.insert(0, '/app/backend')
from four_agent_ask import FourAgentAskService
svc = FourAgentAskService()
trace = {'question': '商用事业部丁杰的业绩', 'steps': [], 'stage': 'test', 'live_callback': None}
r = svc._agent1_resolve_org_subject('商用事业部丁杰的业绩', conversation_context=[], trace=trace)
print('subject:', r.get('subject_name'), 'rewritten:', r.get('rewritten_question'))
# 期望：subject='丁杰', rewritten='丁杰的业绩'
"
```

**修复**：新增 `_pick_finer_subject(llm_subject, fallback_subject)`，按 `_NODE_LEVEL_PRIORITY`（业务代表=1 > 城市公司=3 > 分公司=4 > 事业部=6）比较两者层级，取更细的；层级相同尊重 LLM。`_agent1_resolve_org_subject` 用它替代直接采信 LLM，并加 rewritten_question 一致性校验。

**教训**：fallback 修好 ≠ 主路径修好。打桩（`__new__`）只测 fallback 不触发 LLM，必须在容器内走真实 LLM 验证。

## 快速验证脚本

```bash
cd smartask
docker exec smartask-backend python -c "
from four_agent_ask import FourAgentAskService
import json
with open('/app/config/dataset_node_index.json') as f:
    idx = json.load(f)
svc = FourAgentAskService.__new__(FourAgentAskService)
svc._dataset_node_index = idx
svc._GENERIC_LEVEL_ALIASES = FourAgentAskService._GENERIC_LEVEL_ALIASES
tests = [
    ('迟昊看下这个人的业绩', '迟昊'),
    ('商用事业部丁杰的业绩', '丁杰'),
    ('三明的业绩', '三明'),
    ('查询丁杰', '丁杰'),
    ('看下这位丁杰的业绩', '丁杰'),
    ('一位丁杰的业绩', '丁杰'),
    ('我想知道丁杰的业绩', '丁杰'),
    ('这个人的业绩丁杰', '丁杰'),
    ('四川代表处的业绩', '四川代表处'),
    ('消费者事业部万州的业绩', '万州'),
]
passed = 0
for q, expected in tests:
    got = svc._extract_followup_org_target(q)
    ok = got == expected
    if ok: passed += 1
    print(f'  {\"PASS\" if ok else \"FAIL\"}  Q={q!r:30} got={got!r:12} expected={expected!r}')
print(f'{passed}/{len(tests)} passed')
"
```

## 架构口径

主体提取的长期方向：

1. **cleaner 只负责剥口语前后缀**，不做主体识别
2. **主体识别交给提取器的 contains 匹配 + 层级优先**，不动 cleaned 字符串
3. **追问链路委托裸题器**，不再维护独立正则
4. **LLM(Agent1) 主路径必须经层级校验**——不能盲信 LLM 非空结果，用 `_pick_finer_subject` 与 fallback 做层级择优
5. 残留 ~0.4% 失败走 Layer 5 失败反问（不静默返回 0 行）
6. 测试集是活的：发现新问法 → 加模板 → 重跑

**关键教训**：
- cleaner 里做 org-prefix strip 有回归（会吃掉 "万州城市公司咋样了" 的主体）。主体识别必须在提取器层做，不能在 cleaner 层动 cleaned 字符串。
- **fallback 修好不等于主路径修好**。坑 1-7 全修了 fallback（regex）路径，但主路径（LLM Agent1）一直没动——`_agent1_resolve_org_subject` 先调 LLM，fallback 仅在 LLM 返回空时才用。LLM 返回错误非空结果时，fallback 根本没机会执行。修法：加 `_pick_finer_subject` 层级择优，LLM 返回上层组织单元而 fallback 提取到更细节点时取更细的。
- **打桩验证 ≠ 真实验证**。`__new__` 打桩只测 fallback，不触发 LLM。主体提取改动必须在容器内走真实 LLM 调用验证。
