## 二、架构分析

**技术栈与部署**：Flask 3.0 单体后端 + Vue3/Element Plus 前端 + PostgreSQL 16 + Chroma 向量库 + 多 LLM（通义千问/DeepSeek，OpenAI SDK 接入）。docker-compose 三服务编排（postgres/backend/frontend），健康检查与数据卷配置成熟，bootstrap.py 引导（等 DB→迁移→首导→起服务）是亮点。

**模块划分**：
- `app.py`（250 行）集中注册 18 个蓝图、约 122 条路由，划分按资源域基本合理；
- 核心链路 `four_agent_ask.py` 承载问数全流程（详见第六节）；
- 支撑模块：`ask_flow/`（引擎选择+降级）、`smartask_basic/`（薄封装）、`smartask_advanced/`（13 skill 编排，68KB）、`disambiguation/`（歧义仲裁三件套）、`dataset_copilot/`（数据集配置生成）、`agent_registry.py`（Agent prompt 注册表）、`datasource_router.py`（多数据源路由）、`organization_route_resolver.py`（组织树解析）；
- 前端：`views/`（SmartAsk.vue 8,682 行为主战场）+ `components/smartask/` + `composables.state` 轻量状态 + `api/` axios 封装，无 pinia 亦无前端测试。

**架构合理性判断**：
1. ✅ 蓝图分层、数据集隔离、Golden SQL 机制、行级权限子查询包裹是正确的设计选型；
2. ⚠️ "上帝文件"集中度过高是主要结构性风险——后端 43K 行中 1/4 集中在单个文件，前端 39K 行中 22% 集中在单个组件；局部修复易引发"时而有、时而没有"的回归（与既有诊断结论一致）；
3. ⚠️ 运行态双轨（PG 12 表 + JSON 5 类）撕裂了状态一致性边界；
4. ⚠️ 生产运行形态（开发服务器、单进程）与产品的企业内网定位不匹配。

## 四、性能与风险

**性能瓶颈**：
1. **运行形态**：Flask 开发服务器单进程（`app.py:250`，无 threaded），配合 LLM 同步调用 timeout=180s（`_chat :3625`）——一次慢查询即可阻塞全员；10 人并发场景必现排队。
2. **连接开销**：每查询新建 PG 连接（TCP+认证握手），并发下将打满 PG 连接上限。
3. **链路串行**：4-Agent 全同步串行（路由→生成→复核→执行→修复→解读），无阶段并行与提前流式输出。
4. **索引**：11 个索引集中在初始化脚本，后续迁移稀少；日志/历史类表增长后将全表扫描。

**风险清单（按等级）**：
- 🔴 **致命**：SQL 沙箱可绕过（写穿库/拖库）；JSON 运行态并发写损坏（权限/查询历史丢失）；匿名接口可访问。
- 🟠 **高**：XSS 会话劫持；弱散列+默认密码；单进程故障面；同步调度未运行致决策用旧数据；正确性无门禁持续退化。
- 🟡 **中**：依赖漂移；双轨 schema 漂移；三平台部署脚本（ps1/bat/sh）不同步；迁移漏 node_index。

**安全加分项**：`secret_codec.py` 实为 HMAC-SHA256 密钥流加密（非 README 所称"Base64 混淆"），主密钥文件未入 git，方向正确；建议后续替换为标准 AEAD（Fernet/KMS）。

## 五、数据库设计评估（数析产出）

- **Schema**：PG 仅 12 表（bs_* 元数据 10 张 + system_event_logs + angel_group_data），用户/RBAC/数据权限/查询历史/功能开关等核心对象游离在 JSON——DB 未覆盖业务全域，评级**高风险**。
- **数据访问**：裸 psycopg2 无 ORM 无池化；`system_log_store.py` 值全部参数化（安全）；`data_permission_store.py:347-514` 行级权限子查询为手工转义+字段白名单（非裸拼，风险中，但属脆弱模式，应改参数化）。
- **JSON 迁 PG 优先级**（并发写频率 × 损坏后果）：P0=query_history（北极星指标 WAU-Q 的数据源，数据源不可信则指标不可信）、data_permissions、rbac_permissions；P1=dataset_node_index（315KB 全量读写）；P2=feature_flags 可留文件但须原子写。
- **索引**：按查询模式补 (event_type, created_at) 类复合索引；迁移模板加索引评审 checklist。
- **迁移治理**：init 与 migrations 双轨收敛为单一来源；node_index 补入迁移并带一致性校验。

**工程健康指标看板（8 项）**：SQL 执行成功率、首答命中率（基线 38%）、结果采纳率（需新埋点）、P95 端到端延迟、LLM 失败/重试率、50 问回归通过率（CI 化）、单查询 DB 连接创建数（验证池化收益）、JSON 写冲突事件数（迁移期护栏）。其中 1/2/4/5/6 **第一周即可落地**（纯现有 system_event_logs + trace jsonl 数据源）。

## 六、核心功能链路评估（4-Agent 问数流水线）

**链路全貌**（`four_agent_ask.py` 10,748 行，单类 ~150 方法）：

```
ask() :10166（追问改写/记忆）
→ Agent1 路由中枢 route_with_agent1 :5405-6073（语义路由+歧义确认）
→ _run_pipeline :9520：
  行级权限注入 :9539-9585（子查询包裹 WHERE，机制 ✅）
  → Agent1.5 实体解析 :9596
  → SQL 三选一：Golden SQL 直执 / 规则兜底 :6144-7185（1,041 行硬编码）/ Agent2 生成 :8260
  → Agent3 全量复核 :9075 → 执行 :9926
  → 失败自动修复+复审+重跑 :9943-9971
→ Agent4 业务解读 :9414
```

**评估**：
1. **设计亮点**：复核（Agent3）+ 自动修复重跑 + Golden SQL 直执 + 行级权限前置注入，这套"可信流水线"理念与业界最佳实践同向，部分能力（行级权限）甚至领先开源底座 Vanna。
2. **核心病灶**：意图/组织范围/指标/TopN 等关键参数在 LLM、规则 SQL、数据集画像、报告生成之间**无单一事实源**，互相覆盖 → 38% 通过率的结构性根因。治疗处方是析客的 OPT-11：先定义不可变 **Query Contract**（输入/输出/错误契约），再动刀拆分——先契约、后外迁、再拆模块，全程门禁护航。
3. **知识沉淀错位**：1,041 行硬编码业务 SQL 把"业务知识"写成了"代码"，每加一个业务问题都要改核心文件——应外迁为 Golden SQL/同义词/口径配置（数据资产），与竞析"语义层收敛"建议一致。
4. **优化空间排序**：正确性（Query Contract + 门禁）> 速度（多 worker + 流式）> 可解释（provenance）。

## 八、用户视角影响评估（瑞思产出）

**信任链损伤地图**（3 类角色 × 4 个流失点）：对信任杀伤最大的三个工程问题——
1. **正确性（38%）**：唯一直接命中"答非所问+不敢信数字"两大流失点且覆盖全角色，是信任链第一断点；
2. **数据新鲜度（调度未启动）**：隐性杀手——答案"看起来对"但数据旧，事后发现会回溯性质疑所有历史答案，对管理层是决策级风险；
3. **权限安全（默认密码+守卫缺口）**：组织级一票否决，一次越权事件即可让管理层撤回背书。

**用户可感知验收锚点**（已映射进需求池验收标准）：① 同一问题连问 3 次结果一致；② 高频 20 问一次答对 ≥16；③ 10 秒内出结果且 10 人并发不排队；④ 答案页可见"数据更新至×时"；⑤ 跨数据集对比粒度与分析师手算一致。

**修复期沟通话术**：透明承认 + 锚定复核——"已定位根因，按月公布修复进展；修复期内关键数字以分析师复核为准，欢迎加入抽测群参与验收"，把等待期转化为参与感。
